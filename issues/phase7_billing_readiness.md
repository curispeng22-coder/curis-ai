# Phase-7 Billing Readiness

Status: Draft for gate review

Source review: `docs/release/phase7-demo-polish-commercial-readiness.md`

## Background

Curis is moving toward a commercial multi-tenant AI company system. Workspace now records usage_event and audit_event with tenant, task, workflow, step, employee, capability, model, token, estimated cost, status, timestamp, and credential digest attribution.

The product can show usage attribution, but it should not turn `estimated_cost` directly into invoices.

Phase-7.5 also introduces a Value Event contract in `docs/contracts/value-event-contract.md`. Value Event is commercial validation evidence, not billing authority.

Current strengths:

Current limits:

- No plan/quota lifecycle exists.
- No invoice lifecycle exists.
- No payment/subscription lifecycle exists.

## Is billing_event Needed?

Yes, for Billing MVP.

Reason:

- usage_event records runtime activity.
- billing_event should record billing interpretation of usage activity.
- billing_event can apply plan, quota, rating, rounding, period, credits, and invoice line-item mapping.
- This keeps runtime evidence separate from commercial settlement.

Recommended rule:

- usage_event remains immutable execution evidence.
- value_event remains value-estimate evidence.
- billing_event is generated by Admin-owned billing aggregation.
- Workspace does not write invoices.

## Usage Event vs Value Event vs Billing Event

| Event | Purpose | Owner | Billing Meaning |
| --- | --- | --- | --- |
| usage_event | Runtime usage and attribution evidence. | Workspace writes; Admin observes. | Input signal only. |
| value_event | Estimated value created or cost saved. | Future Workspace/Admin commercial validation layer. | Input signal only. |
| billing_event | Rated billable interpretation of usage/value signals. | Future Admin billing layer. | Billing preparation; still not payment by itself. |

Billing MVP should not charge directly from usage_event or value_event. It should generate billing_event through Admin-owned rating rules.

## estimated_cost Risk

`estimated_cost` must not be treated as authoritative invoice cost.

Reasons:

- It may be based on local env configuration.
- It may not match provider settlement.
- It may not include plan discounts, credits, free quotas, tax, exchange rate, or billing rules.
- It may be useful for analytics but insufficient for commercial settlement.

Recommended rule:

- Display `estimated_cost` as estimated usage signal.
- Billing MVP must use Admin-owned rating rules before producing invoice values.

## Admin / Workspace Boundary

Workspace owns:

- execution,
- workflow,
- employee/capability attribution,
- usage_event production,
- audit_event production,
- redacted credential attribution.

Admin owns:

- plan,
- quota,
- billing_event,
- invoice,
- payment/subscription integration,
- billing UI,
- tenant billing aggregation.

Workspace must not:

- implement invoice generation,
- own billing settlement,
- collect payment,
- call `/api/platform/*` at runtime,
- expose tenant_private plaintext credentials.

## Acceptance Criteria

- Billing MVP remains Admin-owned.
- Workspace usage_event fields are accepted as billing input evidence, not invoice authority.
- billing_event need is confirmed before implementation.
- plan / quota / invoice draft is accepted or revised.
- `estimated_cost` is explicitly marked non-authoritative.
- Admin / Workspace boundary is clear.
- No runtime behavior change is introduced by this readiness issue.
