## Autonomous Meeting Turn Orchestration Contract

This closure extends the existing Meeting row and reuses canonical Work, Responsibility, Employee execution, Result / Evidence, Knowledge, P7 Decision, Attention and Usage Attribution. It does not create a parallel Meeting Agent Runtime.

### Turn flow

`EVENT → TURN EVALUATION → SPEAKER CANDIDATES → SPEAKER SELECTION → RESPONSE → LEADER EVALUATION → CONTINUE / PROPOSAL / EVIDENCE / CEO DECISION / STOP`

- Events are persisted CEO / Employee messages, newly linked Knowledge / Evidence, Proposal changes, Work / Result return, leader requests, explicit `@Employee`, and legal re-entry into a discussable state.
- An event does not imply a response. `NO_RESPONSE_NEEDED` is legal for acknowledgement, duplicate content, sufficient discussion, `WAITING_CEO`, `WAITING_WORK`, or no participant able to add value.
- Candidate scoring is deterministic and explainable from direct mention, leader request, current Responsibility / Work ownership, selected Evidence / Knowledge provenance, and role / responsibility relevance. Model output does not choose its own speaker.
- One primary speaker is selected. One supplementary speaker is allowed only when the persisted event explicitly identifies two independently relevant employees. There is no round robin.
- Explicit CEO `@Employee` and persisted leader designation outrank automatic relevance.

### Context and response

- Speaker context is bounded to Meeting topic/background/scope, that Employee's role and Responsibility, recent messages, current Proposal, selected legal refs, relevant Work / Result, and current Decision state.
- Whole Company, whole Workspace, whole history, whole Knowledge and arbitrary hydration are forbidden.
- Employee output must add a fact, judgment, risk, disagreement, evidence request/reference, proposal change, or precise question. Exact duplicates and empty agreement are suppressed.
- Every model call runs through an existing canonical Work / Responsibility / Employee execution binding, verified callback and the one Usage ledger. Meeting never calls an unattributed Provider path.

### Leader and finite outcomes

The canonical leader performs a bounded evaluation after each accepted contribution. Outcomes are limited to:

- `CONTINUE_DISCUSSION`
- `REQUEST_SPECIFIC_EMPLOYEE`
- `REQUEST_EVIDENCE`
- `UPDATE_PROPOSAL`
- `WAIT_FOR_WORK`
- `NEEDS_CEO_DECISION`
- `DISCUSSION_SUFFICIENT`
- `BLOCKED` / `UNKNOWN`

Proposal truth is an existing ResultStore Artifact reference with Conversation / Evidence / owner provenance. `NEEDS_CEO_DECISION` creates one existing P7 `DECISION_PACKET`; automatic discussion then stops. Decision and Handoff remain distinct.

### Background, bounds and restart

- Current FastAPI `BackgroundTasks` owns accepted in-process continuation after the response; React polling only observes persisted truth.
- One persisted advancement claim is allowed per Meeting. Replay returns the existing claim; a stale claim after process loss becomes `BLOCKED / UNKNOWN` and is never presented as a live Agent.
- Default calibration is local Runtime configuration, not Product Authority: maximum 6 autonomous turns per advancement, 1 consecutive visible turn per Employee, 2 no-progress evaluations, 12 Provider calls, 8,000 confirmed tokens, 5 minutes elapsed time, and USD 1 confirmed cost.
- Unknown token/cost metering remains Unknown. Limits are enforced only from the canonical Usage ledger; unknown metering cannot be presented as measured cost safety.
- Decision, waiting Work, no progress, repeated state, failure limit, cancellation and close all stop continuation.
- Completed turns, messages, Proposal, Decision, Work refs and last processed event persist. Restart never replays a completed turn and never upgrades a persisted `RUNNING` claim into proof that an external Agent is still alive.

### Acceptance extension

- At least three canonical Employees / Roles participate in a real Provider-backed isolated Meeting.
- One participant stays silent because no new value is found; explicit `@Employee` wins the next selection.
- A legal Knowledge / Evidence gap and reference affect a later contribution.
- Proposal uses a real Artifact; P7 uses one shared Decision Packet and pauses discussion.
- Decision creates canonical Work, Result returns to the same Meeting, and triggers bounded re-evaluation.
- No-progress, failure, usage, concurrency, idempotency, restart and context isolation are exercised without touching active SQLite.
