## 1. 核心裁定（重申 + 三项新依据落地）

### 1.1 空间工程是交付型支持部门（不变）
- 工作单位是**建设任务**，生命周期在「交付（Build Team → Operating Team 的 Handoff）」处结束。
- 它不是 Content Growth 式持续经营 Dashboard；新办公室交付后转入**它自己的经营页**（属新业务，不属空间工程部）。

### 1.2 建设任务工作模型（修正：Result flow ≠ P5 Handoff）

> **关键语义修正**：当前责任员工完成 Result **不等于**每次都触发 P5 Handoff。正确链路 = 当前员工完成 Result → 进入下一 Responsibility → Organization Routing 解析下一 Employee → Main 切到下一 Employee Workstation。仅当发生**真实 Responsibility Holder 转移**时才触发 P5 Handoff（P4 自动触发，CEO 不点「下一步」）。Build Team → Operating Team 的最终交付也**先按真实责任语义判断**，不得为表现「交付」强行标 P5。

```
CEO / 空间工程 Leader 确认需求（目标·成功标准·范围·Non-goals）
  → 当前责任员工 以 Conversation 工作（消息流 + 工作状态 + Result/Artifact 卡）
  → 产出 Result / Artifact
  → 当前员工完成 → 进入下一 Responsibility → Organization Routing 解析下一 Employee
  → Main 切到下一 Employee Workstation（仅真实 Responsibility Holder 转移才触发 P5 Handoff）
  → 搭建完成、验收通过
  → 交付（Build Team → Operating Team 的 Handoff，按真实责任语义判断，不强行标 P5）
  → 建设任务结束（空间工程部退出日常经营）
```

### 1.3 三项新依据如何约束本 Closure
- **Frozen Shell 4 点**：Employee Presence/P2=入口、Workstation/§3.1=Main·Conversation-first、Detail/§3.14=Utility、Conversation 禁入 Context/Utility —— 本 Closure 七状态矩阵**逐条对齐**这 4 点，不再出现上一轮高保真的越界。
- **方法论 IA Composition / Retention**：本 Closure §2 长期信息架构 + §5 History/Asset/Config 归属，正是 Lifecycle 步骤 6 的产出要求（长期信息类别 + Shared 复用/Domain 专属 + 四栏归属 + 资产晋升 + Retention 边界 + Context Isolation 声明）。
- **WorkBuddy IA Review**：长期信息分层借鉴「容器/历史/资产/配置·活动」；但**配置/部门方法走 Nav 入口 + Main 专业面，不固定右栏**；**History/Knowledge 不自动全量注入进行中员工的 Workstation Context**（Context Isolation）。

## 2. 空间工程部最终信息架构（Final IA）

### 2.1 信息分层（借鉴 WorkBuddy 长期容器思想，按 Curis Shared/Domain 重新归属）

> 本节定义**分层**；各层的**入口与四栏归属明细见 §5**（两节互补不重复——§2.1 定层，§5 定长期保留与归属）。

| 层 | 内容 | 来源/归属 | 进入方式 |
|---|---|---|---|
| **当前工作（Current Work）** | 进行中建设任务、当前责任员工 Workstation、本次责任链 | Shared（Frozen Shell 四 Pane + P5） | Nav 选中建设项目 → Context（责任链）+ Main（Workstation） |
| **历史（History by Business Significance）** | 建设任务历史、已交付办公室、关键决策/责任轨迹 | Domain（空间工程专属长期信息） | Nav「历史建设任务」/「业务空间」；不自动注入 Context |
| **资产（Asset Library）** | 重要 Result / Artifact / Business Asset（研究报告、Operating Model、Design、Acceptance、交付物） | Shared（P6 Result Reference + 资产晋升规则） | Main 轻量引用 → Utility 全文；可晋升为长期资产 |
| **配置 / 方法（Configuration / Method）** | 当前建设方法、部门配置、责任链模板、验收标准、常用 Capability 连接、部门自身组织关系 | Domain（部门 Profile，非用户经营 Profile） | Nav「部门配置 / 建设方法」入口 → Main 专业面（**不固定右栏**） |
| **Knowledge** | 可复用领域知识、参考研究 | Shared（按需检索） | 按需检索注入，不自动全量注入员工 Session |

### 2.2 长期保留 vs 不保留（Retention 边界，来自方法论 Retention 三原则）

**保留（长期信息能力必须存在，Shared 只要求能力，具体呈现由 Domain 决定）：**
- 建设任务历史（只保留 Business-significant：交付了什么办公室、关键决策、责任轨迹）
- 已交付办公室（经 Lifecycle Handoff 进入「业务空间」，由新业务 Operating Team 承载）
- 重要 Result / Artifact / Business Asset（可经 P6 从 Conversation 轻量引用晋升为资产）
- 当前建设方法 / 部门配置（部门 Profile 长期真相源）
- Business-significant 方法变化（Change Log：成员 / 方法 / 配置的重要变更事件）

**不要求永久保留（Raw Trace by Retention，按 Retention 清理）：**
- 全部 Conversation 原始对话（压缩后仅保留 Learning · Decision · Responsibility · Evidence 事实）
- 普通配置修改（routine 操作变化不进 Change Log）
- Tool log / 运行日志
- 临时 Artifact（未晋升为长期资产者按 Retention 清理）

### 2.3 三者区分（方法论纪律）
- **Activity**：实时进行中的工作动态（当前责任、步骤、状态）—— 进 Context / Main。
- **History**：已结束、按业务意义归档的轨迹 —— 进 Nav 历史入口，不自动注入 Context。
- **Audit**：合规 / 安全审计轨迹（谁在何时改了什么）—— 独立 Audit 通道，不混入业务 History。

> **Audit 收窄边界（关键语义修正）**：Audit **只保留因安全、责任、权限、外部副作用、正式验收或合规要求必须留证的关键事件**。普通配置调整、普通 Conversation、routine operation **不因 Audit 而永久保存**。即：Audit ≠ 把所有操作都记成日志；只有具备「必须留证」属性的关键事件才进入 Audit 通道，其余按 Retention 规则清理，不长期驻留。

### 2.4 Context Isolation 声明
进入任何建设任务 / 员工 Workstation 时，**不自动全量注入**历史对话、Knowledge、部门配置全文。长期信息按需检索 + 轻量引用（P6）；当前工作上下文只承载「本次建设任务 + 责任链 + 团队 Presence 简要」。

## 3. 七种关键状态 · 四栏矩阵

> 约定：四 Pane 固定语义来自 Frozen Shell —— Nav=我在哪里 / Context=这次工作是什么上下文 / Main=当前责任员工怎么工作 / Utility=我当前选中的对象是什么。
> 每项含：**显示** / **为什么放这里** / **明确禁止**。

### 状态 1 · 空间工程部首页 / 历史建设任务

| Pane | 显示 | 为什么放这里 | 明确禁止 |
|---|---|---|---|
| **Nav** | 六区导航；Department=空间工程部（高亮）；「业务空间」分组（含已交付办公室）；「历史建设任务」入口；「部门配置 / 建设方法」入口 | 回答「我在哪个组织位置」；部门是真实核心 Department，不是后台功能 | 不放工作进度、不放员工详情、不做业务指标 |
| **Context** | 无进行中任务时收起或极简；若有进行中任务，显示其简要（名称 + 当前阶段） | 回答「这次工作上下文」；无进行中任务则无上下文可答 | 不放员工 Conversation、不放完整员工详情、不做长档案 |
| **Main** | 部门首页 = 轻量概览（进行中建设任务 / 近期交付 / 部门自身入口）+「发起新建设任务」入口（委托起点） | 部门是交付部门，首页只做轻量导航与发起，不承载经营 | **不画 Business Home 八问 / 指标卡 / Dashboard**；不把部门渲染成持续经营业务 |
| **Utility** | 收起；点击对象才展开 | 首页无选中对象 | 不放 Conversation；不常驻工具墙 |

> **状态 1 内部区分**：「空间工程部首页」Main 显示轻量概览（进行中 / 近期交付 / 部门入口 + 发起入口）；点击「历史建设任务」进入同一状态的**列表视图**，Main 切换为历史任务列表（可点选进入状态 6）。两者同属状态 1 的 Nav 位置，但 Main 内容按用户动作在「概览 / 列表」间切换，不混为一屏。

### 状态 2 · 一个正在进行的办公室建设任务（CORE）

| Pane | 显示 | 为什么放这里 | 明确禁止 |
|---|---|---|---|
| **Nav** | Department=空间工程部；**当前建设项目高亮**；Workspace 导航 | 锁定「我在这个建设项目里」 | 不放工作进度条 |
| **Context** | 当前 Thread；当前阶段；责任链 **已完成 / 当前 / 下一**；团队 Presence 简要（P2，可一键进 Workstation） | 回答「这次建设任务处于什么状态」；Presence 仅轻量呈现，不含详情/Conversation | **不放完整员工详情**；**不放员工 Conversation**；不做员工目录 |
| **Main** | **当前责任员工的 Workstation**（Conversation-first，见 §4）：消息流 + 工作状态 + Result/Artifact 卡（P6）+ Composer；顶部一条轻量建设进度 | Main = 当前责任员工「现在怎么和 CEO 一起工作」；遵循 RD Workstation 范式 | **不做 Dashboard**；**不堆 Timeline / 指标卡 / 多业务概览**；不画八问经营模型；不放无关业务 |
| **Utility** | 点击 Result/Artifact → 报告/策略/设计/验收全文（P6）；点击 Employee → Shared Employee Detail（§3.14，无 Conversation） | Utility = 选中对象的详情/预览 | 不常驻右侧工具墙；**点击员工不得把 Conversation 放进 Utility** |

> **委托草稿态 / 交付瞬间态说明**：CEO↔Leader 澄清意图的立项 Conversation（原 P-B）已吸收为状态 2 的 Context（委托方式 + 目标·成功标准·范围·Non-goals 摘要），不单列草稿态；Build Team → Operating Team 的 Handoff 完成确认（原 P-D）是状态 2 → 状态 6 的**真实过渡**，由 P5 自动触发，不单列瞬间态。两者均被 7 状态覆盖；未作为独立状态是为对齐用户指定的 7 状态清单，未来如需更细粒度可升为独立状态。

> **真实责任交接（P5，仅真实 Responsibility Holder 转移才触发，P4 自动触发）**：当前员工完成 → 进入下一 Responsibility → Organization Routing 解析下一 Employee → Main 自动切到下一责任员工 Workstation；Context「当前/下一」同步推进。CEO 不点「下一步」。注意：员工顺序推进（进入下一 Responsibility + Routing 解析下一 Employee）本身不必然每次都是 P5；只有真实责任 Holder 发生转移才标 P5。

## 4. 当前建设任务 Main Workstation 范式

### 4.1 范式（Conversation-first，普通 AI 工具，不过度设计）
```
┌─ 顶部轻量建设进度（当前阶段 + 责任链概览，一条，不展开）─────────┐
├─ 消息流（Message Stream）────────────────────────────────────┤
│   AI 工作状态（当前步骤 / 持有者 / 等待原因 / 下一步）           │
│   Result / Artifact 轻量引用卡（点击 → Utility 全文，P6）       │
│   ... 对话内容 ...                                             │
├─ Composer（自然语言输入 + 必要模式/模型/发送）──────────────────┤
└──────────────────────────────────────────────────────────────┘
```
- 遵循 ChatGPT / Codex 成熟范式，**不重新设计** Conversation。
- 责任未真变时不新建线程（RD Design Brief §10）。
- 建设阶段进度**最多作为顶部一条轻量信息**，不做大型 Timeline / Dashboard。
- 当前员工完成 → 进入下一 Responsibility → Organization Routing 解析下一 Employee → Main 切换到下一责任员工 Workstation（仅真实责任 Holder 转移触发 P5，不强行标）。

### 4.2 点击员工的两条路径（Frozen 三概念）
- **进入工作 → Main Workstation**：Main 切换到该员工 Conversation-first Workstation。
- **查看详情 → Utility Shared Employee Detail**（§3.14，六字段，**无 Conversation**）：
  1. 个人信息（姓名 / 头像 / 岗位）
  2. **组织关系**（Company → Organization → Department / Team / Leader）— 必含，不得只有名字/状态
  3. 长期责任（服务哪些 Office、承担哪些责任族）
  4. 当前 Responsibility（本次建设中的当前责任阶段，瞬时）
  5. 能力 / 工作方式（capability / specialty / platform_experience / style / 稳定工具绑定）
  6. 最近结果（近期 Result / Artifact 摘要，点进看全文走 P6）

> 铁律：Utility 里的 Employee 视图**永远只是 Detail**，绝不承载 Conversation；Conversation 一旦出现，它属于 Main 的 Workstation。
