## 0. 首次进入的设计哲学

用户第一次进入「内容增长」时，可能完全不懂：Office / 账号矩阵 / 内容策略 / 组织结构。他只知道：

> **「我想让 Curis 帮我做内容、运营账号。」**

设计目标：**用渐进式披露（Progressive Disclosure）把复杂度往后推**。
- 最简单的情况（1 个账号）→ 几乎零配置。
- 复杂的情况（多账号 / 跨平台）→ Curis 帮你理清，你只确认。

**绝不**为了统一架构，让单账号用户走一遍企业级配置。

---

## 1. 通用首跑骨架（所有 CASE 共用）

```
[1] 连接第一个账号        → 「添加你要经营的账号」（OAuth，非 OfficeAccountBinding）
[2] Curis 读账号基本信息  → 推测经营方向 / 定位（能力允许时）
[3] Curis 用自然语言建议   → 「看起来你在做『AI 科普』方向，我先帮你建一个经营方向？」
[4] 你确认 / 改名          → 进入日常使用
[5] 日常：AI 发现选题 → 你接受 → 制作 → 发 → 回流
```

> 第 [2] 步「读账号基本信息 / 历史内容」是**能力允许时**的行为（Capability Truth：VERIFIED / CONDITIONAL / UNKNOWN 合法）。能力不支持时，改为**向你提问几句**（轻量、白话），不卡流程。

## 2. CASE A — 只有 1 个小红书账号

**用户**：完全新手，一个小红书号，想发发笔记。

**应该多简单？**
- 不出现「经营方向 / 账号矩阵 / 绑定」任何词。
- 连接账号后，Curis 直接说：「好了，你的小红书已经连上了。我帮你盯着有什么值得做的选题。」

**首跑流程（极简）**：
1. 点「内容增长」→ 「添加账号」→ 选小红书 → 授权。
2. 授权成功 → 直接进入 Home（Attention + Light Ops）。3. Curis：「已连接你的小红书。我发现有几个选题值得做，点开看看？」
4. 用户点选题 → 接受 → Curis 制作笔记 → 发布。

**经营单元去哪了？**
- 底层仍有一个 Office（Frozen ①），但**用户面完全隐去**。Curis 内部把它当作「你的内容经营」，用户不需要知道这个词。
- 只有当用户**再加一个账号且定位不同**时，才引出「经营方向」概念（见 CASE B）。

> 这是「架构正确性」与「用户零负担」的共存：Frozen 语义完整，用户面按需披露。

## 3. CASE B — 2 个抖音账号，定位明显不同

**用户**：
- 抖音 A：AI 科普
- 抖音 B：个人 IP

两个账号定位不同，应分开经营。

**Curis 如何帮用户理解「这两个该分开」？**

首跑：
1. 连接抖音 A → 授权。
2. 连接抖音 B → 授权。
3. Curis 读两账号基本信息 / 历史内容（能力允许时）→ 发现定位差异。
4. Curis 用自然语言呈现（**不是**技术对比表）：
   > 「这两个账号看起来在做不同的事：
   > · 抖音 A 在讲 AI 科普（偏知识、干货）
   > · 抖音 B 更像你的个人日常（偏人设、生活）
   > 我建议把它们分成两个经营方向，这样内容策略和选题可以各管各的。你觉得呢？」
5. 用户：[分成两个不同的经营方向] [其实是一个，合并] [我再想想]
6. 选「分开」→ Curis 建两个经营方向（用户面主词；「经营单元」留作帮助/管理语境候选，见术语映射文档），各自有独立选题库 / 策略。

**关键**：Curis 把「分开经营」的**理由**讲成人话，用户做选择题，不学矩阵理论。

## 4. CASE C — 4 个账号，定位基本一致（跨平台同品牌）

**用户**：
- 抖音 · Curis AI
- 小红书 · Curis AI
- B站 · Curis AI
- TikTok · Curis AI

定位一致，想共享选题 / 资料 / 策略，需要时再分平台制作。

**Curis 如何建议「一起经营」？**

首跑（连接完 4 个账号后）：
1. Curis 识别四账号同品牌同定位 →
   > 「这四个账号看起来是同一个品牌（Curis AI）在不同平台。我建议放进**同一个经营方向**，这样：
   > · 选题和资料共享，不用每个平台各想一遍；
   > · 一条内容我会针对不同平台分别制作（能复用的自动复用）；
   > · 想单独给某个平台定制时，随时可以。」
2. 用户：[就放一起] [还是分开]
3. 选「放一起」→ 一个经营方向绑定 4 个账号（Frozen：Office 绑 1..N 账号；同平台不同定位才分 Office，这里同定位 → 同 Office）。

**后续制作**（体现 HIGH_REUSE / FULL_DIVERGENCE，但用户不见这词）：
- 用户接受一条选题 → Curis：「这条我准备发到 抖音 / 小红书 / B站 / TikTok，分别做成口播 / 图文 / 教程 / 英文短视频，可以吗？」
- 用户调整 → 制作 → 各账号独立发布。

## 5. CASE D — 很多账号，自己也不知道怎么分

**用户**：10+ 账号，混着各种定位，理不清。

**Curis 能否读取信息 → 给出建议分组 → 用户只确认 / 调整？**

首跑：
1. 用户批量连接账号（或逐个连）。
2. Curis 读各账号基本信息 / 历史内容（能力允许时；不支持则逐批轻问）。
3. Curis 生成**建议分组**（白话，非技术）：
   > 「我看了下你的 12 个账号，大概能归成 3 类：
   > ① 品牌官方号（5 个，同定位）→ 建议一个经营方向
   > ② 垂类测评号（4 个）→ 建议一个经营方向
   > ③ 员工个人号（3 个，定位杂）→ 建议先各自独立 or 合并到对应品牌
   > 你可以直接采用，或拖一拖调整。」
4. 用户可视化调整（拖拽分组 / 改名）→ 确认。
5. 进入日常。

**绝不要求用户先学「账号矩阵理论」**。Curis 把分类逻辑讲成人话，用户做的是「确认 / 微调」。

> 注意：这是**建议**，不是自动执行。分组涉及经营判断，属用户决策（可走 Frozen P-级白话确认，不强制 Needs CEO；除非涉及重大定位变化才升级）。

## 6. 连接与管理账号的日常面（Connected Accounts）

用户可见的「账号」面（不展示技术字段）：

| 用户看到 | 对应（用户不需知） |
|---|---|
| 平台（小红书 / 抖音 / B站 / TikTok） | Channel |
| 账号名 / 头像 | Channel Account |
| 连接状态（已连 / 失效需重连） | authorization_state |
| 经营定位（AI科普 / 个人IP） | Account positioning |
| 所属经营方向 | OfficeAccountBinding |

需解决的日常操作（首版遵循 1 Account : 1 Primary Office）：
- **新增账号**：「添加账号」→ 选平台 → 授权。
- **OAuth 失效**：账号保留、标「需重新授权」、历史内容保留、当前执行降级（Frozen `OAUTH_FAILURE_KEEPS_ACCOUNT`）；用户点「重新授权」即可。
- **重新授权**：同上。
- **账号移除**：确认后解除绑定，历史 Publication 保留（Frozen：不删账号不删历史）。
- **账号换经营定位**：在账号面改「定位」→ 若定位与现经营单元冲突，Curis 提示「要不要移到另一个经营方向 / 新建一个？」。
- **账号在经营方向间移动**：拖拽 / 选择目标经营方向（N:N 共享关系首版不强推，预留入口）。

> 首版**不为 N:N 做复杂 UX**，遵循 1 Account : 1 Primary Office（Frozen Domain §1.2）。

## 7. 首跑验收判据（自测）

- [ ] CASE A：单账号用户全程未见「经营方向 / 绑定 / 矩阵」原词，且底层 Office 语义完整。
- [ ] CASE B：Curis 用自然语言解释「为何分开」，用户做选择题。
- [ ] CASE C：Curis 建议「同品牌跨平台一起经营 + 分别制作」，用户确认。
- [ ] CASE D：Curis 读信息→给建议分组→用户只确认/微调，未要求学矩阵理论。
- [ ] 所有 CASE：OAuth 失效不丢账号 / 不丢历史；移除保留历史。
- [ ] 所有 CASE：未暴露 `OfficeAccountBinding` / `Target Account Set` / `Account Pool` 原词。
