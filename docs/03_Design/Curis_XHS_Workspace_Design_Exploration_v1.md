## 1. 探索约束回顾（来自冻结结论）

### 1.1 三表面骨架（Shell Contract）
```
Topbar（52px 固定）  +  Primary Nav（220px 固定）  +  Main（必有）
Context Surface（左 · Adaptive · 默认收起）
Utility Surface（右 · Adaptive · 默认收起）
```
- Main 必有；Context / Utility 默认不占空间。
- 本轮只讨论 **Main 内部的双主轴几何**，Context/Utility 仅作为"可唤出"的外部面提及。

### 1.2 Main 必须承载的双语义
| 语义轴 | 含义 | XHS 体现 |
|---|---|---|
| **时间轴（Time）** | 发布节奏 / 规划 / 排期 | Content Calendar、Publishing Queue |
| **内容对象（Object）** | 单篇笔记的生产 / 状态 / 数据 | Content Object / Note |

任何 Main 方案都必须在空间中给这两轴一个确定的"家"，只是比例与耦合方式不同。

### 1.3 共享 Pattern 的 Main 内呈现（按需）
- Result Reference（如 📊 数据看板 ▸）可出现在 Note 卡 / 日历格内；
- Needs CEO / Decision 以橙色 Banner 出现在 Main 顶部（不影响双轴几何）；
- Employee Workstation 仅在节点浮现（制作中 / 审核阻塞），**不进入 Main 常驻布局**——故以下方案均不在 Main 内预留员工位。

## 2. 方案 A — Calendar-Dominant（时间主轴为主视图）

### 2.1 空间结构
```
┌ Topbar 52px ───────────────────────────────────────────────┐
├ Primary Nav 220 │ Main Workspace（满宽 · 时间轴为主）        │
│                  │ [月视图▾] [周视图] [+ 新建笔记]            │
│                  │ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐      │
│                  │ │ 周一 │ │ 周二 │ │ 周三 │ │ 周四 │ ...   │
│                  │ │🟡制作│ │🟢已发│ │⚪待审│ │🔵复盘│      │
│                  │ │[封面]│ │[封面]│ │[封面]│ │[封面]│      │
│                  │ │ 标题 │ │ 标题 │ │ 标题 │ │ 标题 │      │
│                  │ └──────┘ └──────┘ └──────┘ └──────┘      │
│                  │  （选中某笔记 → 右开 Note 面板 / 下钻覆盖）│
└──────────────────┴──────────────────────────────────────────┘
```
- Main 满宽呈现 **Content Calendar**（月/周），每个时间格内放笔记卡片（状态色点 + 3:4 缩略 + 标题）。
- 选中某笔记 → 以 **瞬态 Note 面板**（右滑 Drawer / 覆盖层）展示 Content Object 详情与制作区；关闭后回到日历。
- 时间轴是主，内容对象是"被窥视"的从。

### 2.2 何时适用
- 运营重心在"**排期纪律**"：什么时间发什么、节奏是否健康；
- 单篇制作相对标准化，不需要长期把笔记摊在主区。

### 2.3 优点
- **第一眼极简**：满屏日历 + 卡片，认知负荷最低，完美符合 Low Surface Complexity；
- **节奏感最强**：发布分布、空档、密集日一眼可见；
- 与 Later 等成熟产品范式一致，用户预期对齐成本低；
- 笔记详情按需浮现，主区不被制作工具侵占。

### 2.4 缺点
- **内容对象"二等公民"**：深度制作（长正文、多图、标签精修）在瞬态面板里空间局促，易变成"窄抽屉里写长文"；
- 同时处理多篇 / 边看数据边改文案时，反复开关面板打断心流；
- 日历格密度受限：一张卡片塞不下封面+标题+状态+数据角标，信息需折叠。

### 2.5 自然复用的 Pattern
Context（选题库，创作时唤出）· Utility（图文预览/数据看板，点引用开）· Result Reference · Needs CEO Banner。

## 3. 方案 B — Split Dual-Pane（双轴并置）

### 3.1 空间结构
```
┌ Topbar 52px ───────────────────────────────────────────────┐
├ Primary Nav 220 │ Main Workspace（Split · 双轴并置）         │
│                  │ ┌─ 时间轴（压缩）──┐ ┌─ 内容对象（主）──┐ │
│                  │ │ [周]             │ │ 选中笔记工作台   │ │
│                  │ │ 周一 🟡         │ │ ┌────────────┐  │ │
│                  │ │ 周二 🟢         │ │ │ 封面 3:4   │  │ │
│                  │ │ 周三 ⚪         │ │ │ 标题输入   │  │ │
│                  │ │ 周四 🔵         │ │ │ 正文编辑   │  │ │
│                  │ │ (选日→过滤右)   │ │ │ 标签 / 状态│  │ │
│                  │ │                 │ │ └────────────┘  │ │
│                  │ └─────────────────┘ └────────────────┘ │
└──────────────────┴──────────────────────────────────────────┘
```
- Main 分为两栏：左 = **压缩时间轴**（周列表 / 迷你月历，选日过滤），右 = **内容对象工作台**（选中笔记的完整制作区）。
- 选日 → 右栏加载当日笔记；选笔记 → 右栏进入制作；时间轴始终可见作"导航/上下文"。

### 3.2 何时适用
- 用户既要**规划**又要**深度生产**，常在同一个工作段里"排期→写稿→看数据"来回切；
- 内容生产是重活（长文案、多图、A/B 标题），需要稳定工作台。

### 3.3 优点
- **两轴同时在线**：规划与制作不互相打断，心流连续；
- 内容对象得到充分工作台空间，制作体验最好；
- 时间轴作为持久上下文，降低"我在哪一篇 / 今天还要发什么"的认知成本；
- 最接近"双主轴语义"的字面并置，语义最忠实。

### 3.4 缺点
- **第一眼密度较高**：两栏同时呈现，初见不如方案 A 简单（Low Surface Complexity 打折）；
- 窄屏 / 小窗口下两栏挤压，需默认折叠一侧（如时间轴收为 Context）；
- 两栏"抢宽"：时间轴太宽则制作区局促，太窄则失语境，需精细默认比例；
- 有把 Context（选题库）与时间轴混淆的风险——须明确时间轴属 Main、选题库属 Context Surface。

### 3.5 自然复用的 Pattern
同 A，且因为右栏是稳定工作台，Utility（数据看板）可"贴附"右栏而非全屏覆盖，更顺。

## 4. 方案 C — Object-First / Focus（内容对象为主，时间可唤出）

### 4.1 空间结构
```
┌ Topbar 52px ───────────────────────────────────────────────┐
├ Primary Nav 220 │ Main Workspace（Object-First · 时间可唤出）│
│                  │ ┌─ 内容对象为主 ─────────────────────┐    │
│                  │ │ [画廊视图] 🟡🟢⚪🔵 或 [单笔记编辑]  │    │
│                  │ │ ┌──────────────┐                    │    │
│                  │ │ │ 封面 3:4 预览 │  标题 / 正文 / 标签 │    │
│                  │ │ │ 状态 · 数据角标│  制作区           │    │
│                  │ │ └──────────────┘                    │    │
│                  │ │ [📅 排期] → 唤出时间轴 overlay       │    │
│                  │ └────────────────────────────────────┘    │
└──────────────────┴──────────────────────────────────────────┘
```
- Main 以 **内容对象为主**：默认是笔记画廊（卡片墙）或当前单篇笔记工作台；
- **时间轴不上常驻主区**，而是作为可唤出的 overlay / Context Surface（点"排期"弹出日历用于定档），用完即收。

### 4.2 何时适用
- 运营重心在"**内容产能**"：今天就是猛写N篇、精修封面，排期是顺手定的附属动作；
- 团队已有强排期习惯，不需要日历天天挂脸上。

### 4.3 优点
- **第一眼最简单（Object-First）**：主区只谈内容，毫无规划噪音；
- 内容制作空间最大，长文/多图体验最佳；
- 时间轴按需唤出，不抢主区，完美符合"功能按需浮现"；
- 与"笔记是责任载体"的语义最贴合——员工卡、数据、制作都围着笔记转。

### 4.4 缺点
- **节奏感最弱**：没有常驻日历，容易"忘了今天该发什么 / 排期空档"；
- 排期变成"跳出当前语境去弹窗"，规划纪律弱，依赖用户自律；
- 多笔记横向浏览（画廊）与单篇纵深（编辑）需切换视图，增加一层视图状态；
- 时间轴作为 overlay 与 Context Surface（选题库）在左/右/覆盖层上的层级需谨慎设计，避免"两个左边面板"混乱。

### 4.5 自然复用的 Pattern
Context（选题库 + 时间轴均可走左 Context Surface，需区分"内容上下文"与"时间上下文"两种 Context 模式）· Utility（预览/数据）· Result Reference。

## 5. 三方案对比矩阵

| 维度 | A · Calendar-Dominant | B · Split Dual-Pane | C · Object-First |
|---|---|---|---|
| 第一眼复杂度 | ★☆☆ 最低 | ★★☆ 中 | ★☆☆ 最低 |
| 时间轴强度 | 最强（主） | 强（持久上下文） | 弱（按需唤出） |
| 内容对象强度 | 弱（瞬态） | 强（主工作台） | 最强（主） |
| 深度制作体验 | 局促 | 最佳 | 最佳 |
| 排期纪律 | 最强 | 强 | 弱（依赖自律） |
| 窄屏适应 | 好 | 需折叠一侧 | 好 |
| 语义忠实度（双轴） | 时间偏重 | 最平衡 | 对象偏重 |
| 适用人格 | 规划型运营 | 产规一体 | 产能型创作 |

## 6. 本轮未决 / 推荐（非定稿）

- **不在此轮定稿**：三方案均为候选，几何未冻结。
- **倾向建议（供下一轮讨论）**：
  - 若 XHS 首要价值是"帮 CEO 看清发布节奏与责任" → **方案 A**（Calendar-Dominant）最契合 Low Surface Complexity；
  - 若内容生产是日常重活、且希望规划/制作不断流 → **方案 B**（Split）最平衡，但需解决默认折叠与窄屏；
  - **方案 C** 适合作为"专注创作模式"而非默认主视图。
- **可混合方向（下一轮探索）**：默认 A（日历主视图，第一眼简单），选中笔记后**就地展开 Split 式右工作区**（即 A 的瞬态面板升级为可固定分栏），兼顾第一眼简单与深度制作——这可能是 Low Surface Complexity + High Functional Density 的最优解，留待 Round 2 低保真验证。
- **开放问题**：时间轴在 C 中与 Context Surface（选题库）的层级冲突如何解？Split 默认比例与折叠阈值？Need CEO Banner 与双轴如何共处（应为独立横幅，不占双轴空间）？
