## 1. Product Positioning

Curis 是面向一人公司创业者的 AI 公司经营系统。每个当前 Company Runtime
由一位真实 CEO 和多个 AI 员工组成。Curis 帮助 CEO 从零创建公司、选择或
设计业务、配置能力、运行 Workspace、获得真实世界结果，并持续经营、优化
和扩展。

Curis 不是任务管理器、工作流平台、Agent 集合、工具平台、BI 仪表盘、
CRM、ERP 或通用聊天机器人。

### 1.1 Canonical Business Spine（CEO Accepted 2026-08-20）

Company OS 的长期经营关系固定为 `Company → Department → Business → Workspace`。
Business 是唯一 canonical persisted product identity；Business 必须属于 Department，
长期 Business 至少拥有一个 Workspace，Workspace 必须引用真实 Business。Business Direction
是 Business 下的 Strategy / Direction supporting truth，Project 是 legacy compatibility
object，不替代 Business。Business 与 First Workspace 的成功创建必须保持原子语义；无法解析的
legacy Workspace 不得默认挂载，而应进入 `UNRESOLVED → QUARANTINED`。

CEO Assistant 是 Company Runtime 中的第一位 AI 员工和 Chief of Staff。它以
跨七区持续的全局入口协调 CEO Operating Day，负责汇报、准备、请求分流、召集专业 AI、
跟进交接、监测异常和跨日连续性；它不属于 CEO Desk 单页，也不替代专业 Leader / Employee。

### 1.1A Professional Workspace / Multi-Surface（CEO Accepted 2026-08-21）

Professional Workspace 不是一张页面，而是一个长期经营某项业务的完整专业环境。一个 Workspace 有一个 canonical Operating Team responsibility boundary、一个 Workspace Leader、多个 Responsibility；Employee 通过 Assignment 承责，并以同一身份在多个 Professional Surface 工作。

Professional Surface 只是该业务的一种专业观察与工作面。Surface 声明需要什么 Responsibility；Runtime 再经 `Responsibility Requirement → Organization Routing → Assignment → Employee` 决定由谁承担。Surface 不直接绑定 Employee ID，也不拥有 Team、Cycle、Result、Session 或独立 Runtime。

Workspace 内部的空间职责统一为：Global Navigation 负责公司级导航；Context 负责 Domain Navigation 与当前业务上下文；Main 显示当前选中的 Professional Surface；Utility 承载当前对象的 Detail / Editor / Evidence / Tool；CEO Assistant 是 Global Company Employee。Four-Pane 是职责模型，不是固定四根物理栏。

Team、Knowledge、Artifact、Work、Result 与 Evidence 继续复用 Company OS 共享 Truth。一个 Operating Cycle 可以跨多个 Surface，通过 `Work → Result → Evidence → Handoff / new Responsibility → next Work` 连续推进；Surface 只投影相关 Truth。

**Product → Implementation Gap**：Multi-Surface Workspace Package v2 foundation 已 `IMPLEMENTED / ACCEPTED / COMMITTED`；Canonical Child Work foundation 与 sequential cross-professional multi-Work proof 已由既有 commits 接受。仍未完成的是 parallel multi-Work、Surface/UI projection、Package ↔ Runtime Work mapping、多 Surface product integration、RD / XHS 最终迁移与最终 Package Schema。本次接受不授权新的 Runtime、Schema、DB、Frontend 或 Prototype 变更。

### 1.1B Professional Workspace Strategy（CEO Accepted 2026-08-22）

Curis 优先提供少而深、经过专业研究与真实验证的 Professional Workspace；相近业务优先通过配置、派生或安全组合适配。没有成熟专业环境时，Generic Workspace 仍是可真实经营、可恢复、缺口透明且尽量可升级的起点。Curis 不承诺“任何业务一句话自动生成专业级软件”。

专业环境解析顺序为：`Business Intent → Read Current Company Truth → Recognize Domain / Scope / Risk → Search Verified Match → Instance Configuration → Maintained Derived → Safe Composition → 判断 Domain Truth 是否足够支持 Generic → 必要时 bounded Domain / Risk Research → Generic / Derived / Composed / Professional Candidate 判断 → Generation only when necessary`。Research 按 Truth / Domain / Risk Gap 插入，Generation 是 last resort。

Product Form（Professional / Generic）、Provenance（Curis Official / Partner / Community / User or AI Generated）与 Assurance（Verified / Candidate / Unverified / Deprecated）三轴分离；Professional ≠ Verified，Official ≠ Verified，Generated 默认只能是 Candidate。XHS / RD 仍是专业形态验证案例，不自动获得 Verified 状态。

Business Configuration 继续存在：Business 页面承载身份 / 定位、Goal、Rules / Preferences、Team / Responsibility coverage、Capability / Connector 授权、automation boundary、optional module、通知与 operating cadence 等通用经营设置；它回答“这个业务怎么经营”，不是 Professional Workspace Builder、Low-code App Builder 或 Workflow Builder。Professional Workspace 回答“这个专业业务具体怎么工作”。

Workspace Engineering 负责 discovery、matching、configuration、composition、installation、validation 与 evolution first；研究按需插入，生成仅在没有更好路径时发生。Workspace Package 是 Domain Operating Capability Package，Professional UX / Interaction 属于 Package 一等资产，但不引入第二套 Runtime，也不授权 arbitrary HTML / React / JS。Official Professional Workspace Library、Professional Module、Verified Registry、Generic → Professional upgrade 与第三方 Package ecosystem 仍是后续方向；本节不改变现有 Package、Autonomous V1 或 Runtime 实现边界。

## 1.1 Leadership / Responsibility Assignment

Leader 是 Curis 定义的责任角色，不是 Employee Type，也不是 Admin 权限。Department Leader、Business Leader 与 Workspace Leader / Operating Owner 都由普通 Employee 通过 `Employee × Role × Scope` 的 Responsibility Assignment 承担；同一 Employee 可以兼任多个普通 Role、Leadership Role 或跨 Workspace 的 Assignment，身份不复制。

团队运转中的岗位责任必须经过 `Role Definition → Responsibility → Employee Binding → Responsibility Assignment` 落到真实 Employee。Conversation 默认以 Assignment 为上下文，而不是只按 Employee ID 路由；Employee Profile与Business / Workspace / Role入口可进入同一持久Conversation的合法上下文；按消息/引用隔离Scope并校验权限，不强制切断历史或新建Conversation。

Workspace Leader 对 Workspace 的 Goal、Rules、团队运转、团队、Result 与下一轮经营负责。一轮团队运转结束后 Result 回到 Workspace Truth 与 Leader 责任范围，由最低有效责任范围决定继续、调整、升级或等待新目标，进入 **Next Operating Cycle**；正常经营不要求 CEO 逐任务重新派发。责任升级链为 `Employee → Workspace Leader → Business Leader → Department Leader → CEO`，Leader 不绕过既有权限与 Decision Gate。

首次进入 Curis 时，用户可以开始初始化，也可以选择“先看看 Curis”并进入无虚构数据的 Empty Curis Shell。选择初始化时，先建立 CEO Display Identity 与 Company，再由同一 canonical CEO Assistant 协调经营意图、必要研究与 Operating Proposal，形成 Business、AI Team 和合法 Department / Workspace。长期 Business 必须归属一个 Department；新Company包含空间工程部/数据分析部及真实原装员工；其他Department随重复责任和共享能力按需扩展。Department不是Employee招聘前置，Company-level Employee可直属Company。公司空间、业务版图和部门工作面是全局体验的视觉基础，不是后续装饰。用户可见的专业空间统一称为“工作空间”；Office / “办公室”仅作历史与implementation / migration provenance，不作为当前用户身份。

业务空间正式是 **Operating Work Directory**：在同一 Company Truth 上提供 Department、Business、Workspace 三个直接入口。Department / Business Leader 不是新的 Employee 类型，而是普通 AI Employee 的 Responsibility Scope；持续领导工作进入业务空间对应的 Leader Work Surface。Organization Center 只负责公司结构、Role、Staffing 与 Leader assignment，不承载日常 Leader Conversation。

Business 与 Workspace 的目标语义分层：Business 持有 Business-level Goal / Strategy，负责该类业务的整体经营方向；每个 Workspace 持有自己的 Workspace-level Goal / Positioning / Strategy，负责独立工作空间的具体经营。同一 Business 下 Workspace 不默认共享彼此的 Workspace-level Goal / Strategy，但都属于并服务于所属 Business，受 Business-level Goal / Strategy 的整体方向约束；不创建 Default → Override 技术模型。

空间工程以 Operating Intent 与当前 Company Truth 为输入，遵循 **REUSE EXISTING STRUCTURE FIRST**，先做 Domain / Scope / Risk 识别与 Verified Match，再做配置、派生、组合、必要研究和最后手段的生成；组织结构仍按 `Department → Business → Workspace` 复用或按需调整。固定经营层级为 `Department → Business → Workspace`；每个 Business 至少拥有一个实际 Workspace，一个 Business 只有一个 Workspace 是正常状态。空间工程不拥有第二套 Organization Truth，简单组织操作仍可在 Organization Center 完成，不提供 Business-direct / Workspace 两套用户模式。

Business 是专业经营定义层和该业务的运行说明：承载 Business Introduction、Business-level Goal / Direction、通用 Rules / Configuration、整体经营状态、Workspace 目录和 Business Team 轻量投影。Rules / Configuration 使用通用 `Title / Name + Content` 项集合，不预先发明行业字段 Schema。Workflow / Team Operating 不属于 Business 统一模型；每个 Workspace 独立拥有自己的 Goal、Rules、Team Operating、Role / Responsibility Assignment、Operating State、Result 与 Domain Work Surface，Business 页面只提供 Workspace Directory / Portfolio List 与直接进入入口，不嵌入 Workspace 详细工作面。

Team Operating 的用户语言是“团队运转”，主区可显示“默认流程”。`A → B` 仅表示 A 产出 accepted Result 且没有更强的 Consult、Review、Return、Need、Leader、Decision、Wait 或 Domain rule 时，B 是默认下一 Responsibility；它不是强制运行序列，也不是任意可执行 DAG 边。Workflow / Router / DAG / State Machine 只属于内部 Runtime / Audit 语言。Workspace 内轻量编辑动作映射为 Reorder→Default Flow、Responsibility→Responsibility Contract、Employee Binding→scoped Assignment、Input→Context Contract、Output→Result Contract、Save→immutable Operating Definition Version；运行中的工作固定使用旧版本。

Goal、Rules、Business Definition 与 Workspace Definition 的主要创建路径是 CEO / User ↔ Assistant / Business Leader → Structured Proposal → 必要确认 → 写入 Business / Workspace Truth → 页面更新摘要；Panel / Modal 只负责查看、精确编辑和纠错。研发、内容增长、小红书、短视频只是 Professional Workspace 形态示例，不是 Curis 产品边界；未知 Domain 可以通过 Generic Business Definition、Generic Rules / Configuration、Workspace 团队运转、Role Structure 与 Workspace 使用真实开始，再按 Domain / Risk Gap 研究与演进。未知 Domain 的 Role Structure 由具有专业责任的 Leader / Workspace Engineering / Domain Expert 提出，经 CEO 预览确认后形成正式岗位；CEO Assistant 只负责协调、搜集、组织提案、跟进和升级，不作为未知行业 Role Structure / Operating Method 的默认专业 Owner。

AI 团队不是平级 Agent 列表：CEO 治理 CEO Assistant，Assistant 协调 Professional
AI Employees，Professional AI 负责专业结果，Workspace AI 在具体业务空间内执行。
Workspace 可由 CEO 直接创建，或在需要专业建设时交由 Workspace Engineering 复用、配置、组合、验证与建立；Workspace Studio 是按需演进入口，不是所有 Workspace 开始运行前的固定门禁。

### 1.1 业务工作台与 Work 来源及 CEO 介入边界

- **研发工作台**只是研发领域的一种 Professional Workspace 名称，不是所有业务或 Workspace 的正式名称；用户语言统一使用“工作空间”，Office / “办公室”仅作历史与implementation / migration provenance。
- 研发工作台不预置固定 Work；Work 默认从目标、策略、经营计划、团队运转、结果、触发器、日程或员工判断等真实经营上下文产生。CEO 可以主动提出、命名、调整、介入或接管 Work，但不承担逐项创建职责。
- 历史本机验证中使用过的“Curis 的自研发 / 完善 Curis”只是 CEO 创建的 dogfood
  工作项，不是产品定义、业务模板、Workspace 默认数据或 Blueprint 规则。

真实 CEO 用户界面统一使用简体中文；英文只作为内部对象名、开发标识或中文后的
括号说明，不作为独立导航、按钮、状态或错误提示。

产品结构：

- Company OS 固定：固定经营语义、生命周期、权限、证据、决策和交互规则。
- Workspace 开放：每种业务拥有自己的工作方式、布局、能力和外部数据组合。
- Project、Task、Workflow、Artifact 可以作为 Workspace 内部执行记录，但
  不是产品根或一级导航。

当前交付是 Local Desktop、单一 Owner 使用。未来商业化保留 Platform/Admin
与 Company Runtime 两个逻辑层，但当前不把租户、计费、模板市场或物理拆分
描述为已交付能力。

Local Desktop 是交付方式，不是功能裁剪。当前单一 CEO 仍需要完整使用模型、Skill、
Tool、连接器、知识、权限、AI 员工、Workspace、结果反馈和经营决策；实现上可以使用
本地数据、人工录入或本地模型替代云端服务，但不能因为用户只有一人而删除 CEO 完成
经营闭环所需的能力。

影响经营结果的核心对象和持续运行 Workspace 需要定义 Business Runtime：生命周期、状态、
阶段 Owner、Input/Output、反馈、异常和关闭；页面级展示对象不因治理要求被迫成为独立产品。

### 1.2 Autonomous Business Operation（CEO Accepted / Approved Candidate）

Operating Responsibility 是长期经营责任，默认持续；每个 Operating Cycle 是有界运行并正常 Close。Cycle Close 不等于 Business、Workspace 或 Responsibility 停止；PAUSE 暂停 Operating Series 并要求显式 Resume，STOP 终止当前 Operating Responsibility / Goal Series，只能由 CEO 或事先授权的 terminal policy 触发。CONTINUE / ADJUST 才能创建或安排 exactly one next Cycle，WAIT / ESCALATE 不创建未授权运行。

Workspace Leader 只能在 Approved Strategy Envelope 内调整 hypothesis、tactic、cadence、experiment、资源分配、Work priority、执行组合与 bounded Plan；Goal、Success Contract、Positioning、Target Audience、Business / Monetization Model、protected Strategy Boundary、material Budget 和高影响/不可逆外部承诺必须 CEO Gate。`ADJUST` 不等于可修改任意 Strategy。

该 Operating Lifecycle 是 Company OS 的薄 Control Plane，执行继续复用既有 Team Operating、Employee、Assignment、Provider Task / Session、Result、Evidence、Decision 与 Handoff。V1 先以 Workspace 为 Runtime Execution Scope；至少一个 Domain 必须完成连续两轮 Primary Autonomous E2E，第二个 Domain 完成 Cross-domain Contract Proof，不能以静态 UI、fake Result 或 fake Analytics 冒充完成。该段是已接受的产品候选合同，不是 Runtime / Schema / Code 已交付事实。

### 1.3 Three-Layer Operating Model（CEO Accepted 2026-08-20）

Curis 的经营产品分为三层：`User Surface → Employee Operating Layer → System Runtime`。User Surface 让 CEO 表达“把这件事交给 Curis”、查看公司/业务/Workspace、结果与证据、做必要决定；Employee Operating Layer 让 Leader / Employee 消费 Goal、Approved Strategy Envelope、Situation、Relevant Capability、Method / Package、Knowledge、Plan、Result、Review 与 Learning；System Runtime 只负责 Scope、责任、权限、版本、持久化、证据和恢复。固定的是经营责任、Truth、Evidence、Gate、Recovery Contract，不是所有行业共用的固定 Workflow。

陌生业务统一经过 `USE EXISTING / COMPOSE EXISTING / RESEARCH·ADAPT / BUILD·ACQUIRE / ESCALATE / REFUSE·CANNOT OPERATE YET`。Curis 不得假装拥有未验证的行业能力；缺口必须带 Owner、原因、恢复入口和返回位置。XHS、小红书、抖音、RD、宠物寄养只作为 Validation / Pressure-test Examples，不是 Core Domain 或默认模板。

当前不新增 Playbook canonical object。Methodology Handoff、Package method metadata、Skill composition、Operating Definition 与 Result / Evaluation / Review 分工承载 Playbook-like semantics。Package 的产品语义为 **Domain Operating Capability Package**；方法元数据的持久化/版本化仍是 Future Capability Architecture / Product → Implementation Gap，不得静默升级为 Autonomous V1 blocker。

### 1.4 Brand Neutrality（CEO Accepted 2026-08-20）

`Curis` 是当前产品品牌，不是 Company、Business、Workspace、Operating Lifecycle、Capability 或 Runtime 的 canonical semantic。User Surface 可以使用“交给 Curis”“Curis 正在研究”“Curis 助理”；Employee Operating Layer 与 System Runtime 使用品牌中立的 Company OS、Operating Responsibility、Package、Capability Provider 和稳定 canonical IDs。现有 `curis.*` / `curis_app` 等仅属技术 namespace，不进行机械重命名。未来 Brand Configuration（产品名、显示名、Assistant 名称、Logo/Icon refs）属于实现方向；本轮不设计 Schema、Brand Runtime、Frontend 或 Rebrand Initiative。

## 3. Core Value

- 让 CEO 从自然语言意图开始，建立第一个可运行的公司和业务。
- 让 AI Employee 通过责任契约、能力契约和证据要求真正承担工作。
- 让业务产生 API 或人工录入的真实世界反馈，而不是只记录内部完成。
- 让 CEO 通过 Decision Runtime 继续、暂停、扩大、调整或退出业务。
- 让 CEO 每天通过 Operating Day 知道公司发生了什么，由第一位 AI 员工推动
  AI 团队工作，并在高影响事项上保留最终决策。
- 让 Business Engineering 能将任意新业务装修成可模拟、可审批、可版本化的
  Workspace，而不是只创建一个空运行容器。
- 让 Company OS 保持固定经营语义，让不同业务在 Workspace 中表达差异。
- 让研发工作台承接产品研究、需求判断、架构、开发、测试、发布与反馈等真实经营上下文，并通过完整经营闭环沉淀可复用业务模式。
- 内容增长可经营不同Channel Account；互动/线索回流按各连接真实能力，由员工分流与准备，外部承诺/风险边界保留CEO Gate，不承诺所有平台已接通。
- 当前以研发及内容增长的不同Channel场景作为Workspace专业形态示例，用于验证不同业务工作面；它们不是 Curis 固定业务类型、V1 必选项或 Core Domain。其视觉、外部结果反馈和运行链路同步设计与验证，不使用固定演示数据替代真实业务。
- 让未来 Platform/Admin 能够提供能力、模式、版本和商业服务，同时隔离每个
  用户的一人公司数据和决策。

## 5. Product Relationship

~~~text
Current Local Desktop
├── Platform capability boundary
│   ├── capability definitions
│   ├── validated business patterns
│   └── version concepts
└── Company Runtime
    ├── one CEO
    ├── AI Employees
    ├── Business Bets / Outcomes
    ├── Workspace / Cycle / Commitment
    ├── Evidence / Acceptance
    └── Decision / Change
~~~

未来商业化后，上层能力可以由 Platform/Admin 提供；用户选择的业务模式
复制到自己的 Company Runtime 后独立运行、可修改、可版本化升级，平台不能
静默修改正在运行的用户公司。

核心经营链：

~~~text
Company
→ Business Bet
→ Outcome
→ Responsibility
→ Capability / Capacity
→ Workspace / Cycle
→ Commitment
→ Evidence
→ Acceptance
→ Decision
→ Company Change
~~~

## 6. Product Invariants

- 没有结果目标不能建立正式业务。
- 没有被接受的责任不能启动 Cycle。
- 有 Capability 不代表当前有 Capacity。
- 内部完成不等于外部结果。
- 没有证据不能标记 Verified。
- Unknown / Stale与需核实是合法表达；来源不一致、资源占用和责任冲突分别解释，不新增Global Conflict State或员工状态。
- 高影响变化必须经过 Impact Map、Simulation 和 CEO Approval。
- AI 可以在授权范围内独立执行，但不能静默改变高影响公司状态。
- 业务退出必须保护承诺、交接责任、释放资源并保留学习。
- 产品推导顺序为 CEO 经营场景 → 用户动线 → 产品形态 → Runtime 与 UI → Code；
  工程实现可以按纵向切片并行推进，不以治理顺序限制产品发现。
- 页面、按钮、API、测试和数据表本身不是产品完成标准，但页面、配置、运行、反馈和返回路径
  共同组成产品体验。
