## 0. 本次讨论解决了什么问题

旧的产品思路容易从页面、模块和软件行业惯例出发：CEO Office、Project、Task、Employee、Capability、Meeting、Knowledge。这样会得到一套看似完整的软件，却无法回答 CEO 每天如何建设和经营公司。

本次推导把起点改为真实经营问题：

> 如果今天是一家 AI 公司成立后的第一天，CEO 想让公司产生第一个结果，他必须做什么？Curis 如何让这些事情被设计、被委派、被执行、被验证并进入下一次经营决策？

因此，本记录不以“增加了哪些页面”为成果，而以“形成了哪些经营判断”为成果。

## 0.1 2026-08-10 重新校正：完整产品形态优先

后续复核发现，之前的产品推导把 Local Desktop、单一 CEO 和未来商业化边界写成了过强的
功能限制。产品身份应该先于部署方式：Curis 首先是一款完整 Desktop App，其核心用途是
帮助 CEO 创建、经营和扩展个人 AI 公司。

修正后的判断：

- 单机部署不代表低配产品。模型数量添加、Skill 接入、Tool 连接、能力分配、权限、成本、
  AI 员工、Workspace、外部结果和经营决策都属于 CEO 必需能力。
- 完整产品形态必须先被描述出来，再用实现阶段决定交付顺序；“暂未实现”不能被写成“不属于产品”。
- Blueprint 描述产品身份、CEO 生命周期、App 地图、用户动线和完成标准；CURRENT_STATE 描述
  当前交付事实；Runtime、Issue、Review 和 Simulation 描述实现保护措施。
- 经营逻辑仍然是产品内核，但用户使用 App 的入口、页面、配置、运行、反馈和返回路径同样是
  产品本体，不能让治理门禁替代用户体验。

本次重新推导的完整审计见：
`docs/reviews/20260810_product_rederivation_review.md`；唯一 Blueprint 已重构为 5.0。

## 1. 起点：CEO 到底要做什么

CEO 的经营问题被归纳为五层，但五层不是五个平行导航，而是五个持续出现的判断：

| CEO 问题 | 真实经营职责 | 产品需要提供的能力 |
| --- | --- | --- |
| 公司现在怎样？ | 发现变化、异常、约束和待处理事项 | 经营状态、证据、注意力排序、决策包 |
| 业务是否创造价值？ | 选择业务赌注、保护承诺、决定投入 | 业务、结果、客户/外部反馈、投资判断 |
| 公司能力够不够？ | 配置责任、人员、AI、能力、容量和资源 | 责任合同、能力契约、容量、分配和连续性 |
| 工作是否有效运行？ | 委派、协调、验收和恢复 | Workspace、Cycle、Commitment、Evidence |
| 共识和知识是否可复用？ | 保留事实、决议、来源、学习和历史 | Truth & Decision 控制面，而不是知识仓库 |

推导结果：一级导航应该表达 CEO 的经营视角；事实、证据、决议和学习贯穿所有视角，不能再被拆成一个孤立的“知识中心”。

## 2. 产品身份的收敛

### 2.1 当前产品定义

Curis 是一款面向一人公司创业者的 AI 公司经营系统，帮助一位 CEO：

```text
从零创建公司
→ 选择或设计业务
→ 配置 AI 员工与能力
→ 建立业务运行空间
→ 产生外部或真实世界结果
→ 根据结果持续经营、优化和扩展
```

它不是：

- 普通任务管理器
- 多人协作软件
- 通用工作流平台
- Agent 市场
- BI/KPI 仪表盘
- CRM、ERP 或聊天机器人

### 2.2 用户边界

当前每家公司只有：

```text
1 位真实 CEO
多个 AI 员工
若干业务
若干能力
若干 Workspace
```

暂不把多名真实员工协作作为 P0 前提。员工、AI 员工和未来协作模式仍应被抽象为责任主体，但当前真实操作人只有 CEO。

### 2.3 当前与未来的双层边界

商业化后会有两个逻辑层：

```text
Curis Platform / Admin
→ 能力、业务模板、版本、租户、计费和平台服务

User Company Runtime
→ 用户自己的公司、业务、AI 员工、Workspace、承诺、证据和决策
```

当前本机验证阶段把两个层次收在一个桌面应用中，但必须保留边界意识：平台能力不能和用户公司经营事实混成不可拆分的一套数据和权限。

商业化的计费、模板市场、租户后台和物理拆分不是当前交付范围；它们只作为未来边界被保留。

## 3. 从零创建公司的推导

CEO 第一天不应该先创建部门、项目和任务。最小创建路径是：

```text
CEO 意图
→ 公司理解
→ 第一个业务赌注
→ 第一个结果
→ 最小责任
→ 最小能力与资源
→ Cycle 或 Workspace
→ 第一个真实结果
```

### 3.1 Founding Brief 的职责

Founding Brief 不是注册流程、Onboarding 表单，也不是聊天窗口。它负责把自然语言意图变成一个可审批的最小公司方案：

- CEO 为什么创建公司
- 服务谁、解决什么问题
- 第一个业务赌注是什么
- 第一个可验证结果是什么
- 需要哪些最小责任和能力
- 哪些假设还未知
- 需要多少时间、注意力、资金或 AI 容量
- 哪些风险必须由 CEO 亲自决定

### 3.2 组织从责任中长出来

正确顺序是：

```text
结果缺口
→ 稳定责任
→ 所需能力
→ 多主体协作
→ 组织单元
→ 部门或共享服务
```

“创建部门”能力应该存在，但它不是简单的名称、负责人和成员 CRUD。一个部门必须有结果、责任、能力、容量、权限、依赖、服务承诺和退出条件。

## 4. 公司运行的两条循环

Curis 的产品真相不是四个页面，而是两条互相校正的经营循环。

### 4.1 价值循环

```text
市场信号
→ 业务机会
→ 业务赌注
→ 外部承诺
→ 内部交付
→ 外部验收 / 平台结果
→ 收入、留存或学习
→ 继续、扩大、调整或停止
```

它回答：

> 公司是否正在创造值得继续投入的真实价值？

### 4.2 公司循环

```text
公司意图
→ 公司设计
→ 责任分配
→ 能力配置
→ 资源分配
→ 委派执行
→ 观察组织状态
→ 调整公司结构
```

它回答：

> 公司是否具备持续创造这些价值的能力？

两条循环在 `Outcome` 与 `Decision` 处相交：业务结果会改变公司结构，公司能力又会限制业务选择。

## 5. 公司不是任务集合，而是承诺网络

公司本质上是一组对客户、平台、伙伴、员工、资金提供方、合规主体和公司自身作出的承诺。

### 5.1 三层对象

```text
Promise / Obligation
对外或对组织承担的结果承诺

Commitment
某个责任主体接受的交付责任

Task
为了完成责任而采取的内部动作
```

关系为：

```text
外部承诺
→ 内部责任承诺
→ Work Package
→ Task
→ Evidence
→ 外部验收
```

任务完成不代表公司完成了承诺；只有结果被接受或被明确标记为未知、失败、违约或关闭，经营循环才有结论。

### 5.2 承诺生命周期

```text
提出
→ 协商
→ 承诺
→ 执行中
→ 有风险
→ 已兑现 / 已违约
→ 关闭
→ 学习
```

每个承诺要有对象、内容、验收标准、负责人、时间范围、所需资源、当前证据、违约影响和变更方式。

### 5.3 为什么需要承诺网络

资源冲突本质上是承诺冲突。CEO 想新增一个业务时，系统必须告诉他：这个选择会占用哪些能力、影响哪些已有承诺、哪些业务可能延期，以及可选的缩小范围、延后、转移或拒绝方案。

## 6. 外部结果与价值反馈

### 6.1 外部结果的定义

“外部”不是只指付费客户，而是指结果来源于 Curis 自己无法单方面伪造的真实世界：

- 客户验收
- 平台数据
- 用户行为
- 收入与交易
- 产品真实使用
- CEO 手动确认的业务反馈

### 6.2 两类结果来源

| 来源 | 例子 | Curis 处理方式 |
| --- | --- | --- |
| API / 外部系统 | 抖音播放、点赞、下单；GitHub 构建和发布结果 | 读取原始事实，记录来源、时间和新鲜度，再解释为业务证据 |
| CEO 手动反馈 | 没有 API 授权时录入平台指标；软件可用性人工验收 | 记录录入人、时间范围、来源链接/截图、可信度和解释 |

手动反馈不是临时替代，而是外部系统不可直接连接时的正式证据入口。

### 6.3 Curis 与外部系统的分工

Curis 可以让 AI 员工执行工作，但不必复制每个外部平台的原始系统：

| 业务 | Curis 负责 | 外部系统可能负责 |
| --- | --- | --- |
| 软件开发 | 结果、责任、开发周期、验收、发布决策、反馈 | GitHub、CI、云平台、应用运行环境 |
| 内容增长 | 内容目标、创作责任、发布承诺、指标解释、下一轮决策 | 抖音/小红书发布、流量和交易数据 |

Curis 拥有经营事实、承诺、决策和解释；外部系统保有它产生的原始事实。

## 7. 能力、容量与资源

### 7.1 Capability 与 Capacity 的区别

```text
Capability = 公司是否具备某种能力
Capacity = 当前是否有可用余量
```

一家公司可能具备内容创作能力，但当前 AI 并发、CEO 注意力、预算、数据权限或发布时间窗口不足，因此不能继续承诺新业务。

### 7.2 资源生命周期

```text
需求估算
→ 提出分配
→ 预留
→ 承诺
→ 消耗
→ 释放
→ 评估价值
```

资源状态至少要区分 Planned、Reserved、Committed、Consumed、Released、Blocked 和 Overloaded。

### 7.3 AI 公司特有的资源

- CEO 的决策注意力
- 人员时间（未来扩展）
- AI 员工执行容量
- 模型调用、计算和成本预算
- 数据访问权限
- 专业能力
- 外部平台和账号权限
- 客户信任与可承诺空间

AI 成本最终要能够回答“一个已验证结果付出了多少 AI 成本”，而不是只展示调用次数。

## 8. AI 员工的真实职责

AI 员工不是聊天角色，而是被授权的责任主体。

每个 AI 员工都必须有：

- 角色和责任结果
- 业务范围
- 数据范围
- 可使用能力
- 可执行动作
- 质量标准
- 成本和延迟边界
- 升级条件
- 证据要求
- 失败和备用方案

AI 可以独立承担责任、执行工作和推动业务，但不能未经授权：

- 修改公司意图或战略重点
- 对外新增承诺
- 改变资源优先级
- 改变责任归属
- 修改公司结构
- 把未验证结果标记为完成

AI 员工生命周期：

```text
候选
→ 测试
→ 批准
→ 试运行
→ 正式运行
→ 降级
→ 暂停
→ 退休
```

CEO 负责意图、业务赌注、重大资源、权限和高影响决策；AI 员工负责边界内的理解、执行、证据和升级。

## 9. 工作空间的真实职责

不是所有业务都需要 Workspace。

### 9.1 直接运行 Cycle 的条件

- CEO 与一个 AI 员工协作
- 一次性验证
- 依赖少
- 没有独立权限和能力组合

### 9.2 建立 Workspace 的条件

- 多个 AI 员工持续协作
- 存在重复交付周期
- 需要独立能力、数据和权限
- 需要独立异常、验收和复盘
- CEO 无法继续亲自协调全部细节

### 9.3 Workspace 契约

- 业务和目标结果
- Owner 与参与 AI 员工
- 输入和输出
- 能力与资源组合
- 运行周期
- 证据与验收方式
- 异常和升级条件
- 关闭和退出条件

Workspace 是业务数字空间；Project、Task、Workflow、Artifact 只是其中可能使用的内部执行对象。

## 10. 失败、未知与恢复

真实经营的完整性取决于失败路径是否成立。

### 10.1 四类失败

| 失败类型 | CEO 需要判断 |
| --- | --- |
| 价值失败 | 需求、客户或业务假设是否不成立 |
| 交付失败 | 范围、周期、质量或依赖是否错误 |
| 供给失败 | 人、AI、能力、资源或权限是否失效 |
| 判断失败 | 事实、证据、来源或 AI 推断是否不可靠 |

### 10.2 异常生命周期

```text
发现
→ 识别范围
→ 临时控制
→ 选择恢复方案
→ 执行恢复
→ 验证恢复
→ 关闭
→ 学习
```

### 10.3 不允许假装正常

状态必须能够表达 On Track、Attention、At Risk、Blocked、Unknown、Stale、Conflict、Resolved 和 Verified。

没有证据不能自动变成绿色；证据冲突不能被平均；过期决策必须重新验证。

### 10.4 业务退出

Pause、Reduce、Transfer、Close、Merge、Split 是不同经营动作。退出前要保护未完成承诺、交接责任、释放资源、保存历史和沉淀学习，不能用 Delete 消除经营事实。

## 11. 公司复杂度的渐进式激活

Curis 不应在第一天展示完整企业软件，而应由真实经营触发复杂度。

| 阶段 | 触发事实 | 新增能力 | 阶段完成判断 |
| --- | --- | --- | --- |
| 创始 | 只有 CEO 意图 | Founding Brief、最小公司方案 | 第一个结果和责任获 CEO 批准 |
| 首次价值 | 开始面对真实世界 | 外部结果、验收、反馈 | 获得一次真实结果或明确失败 |
| 可重复运行 | 同类工作重复、多 AI 协作 | Workspace、Cycle、责任合同 | 结果可重复且不依赖 CEO 逐步推动 |
| 委派经营 | CEO 无法覆盖全部细节 | AI 权限、升级、节奏、连续性 | AI 在边界内可靠决策并交证据 |
| 业务组合 | 多个业务争夺资源 | 组合、战略重点、投资和退出 | 资源分配由价值和优先级驱动 |
| 重构扩展 | 重复异常、能力瓶颈或新业务 | 组织重构、共享服务、版本迁移 | 结构变化被真实运行验证 |

业务成熟度和公司成熟度可以不同；一个公司可以同时运行成熟业务和新实验业务。

## 12. 导航与页面是如何反推出来的

四个 CEO 入口不是四个独立产品，而是同一套经营对象的投影：

| 入口 | CEO 问题 | 页面职责 |
| --- | --- | --- |
| 经营 | 现在发生了什么，什么需要我处理？ | 状态、约束、决策、异常、经营简报 |
| 业务 | 我们为谁创造什么价值，是否值得继续？ | 业务赌注、客户/外部结果、承诺、投入和阶段 |
| 公司 | 公司是否有能力兑现当前承诺？ | 责任、AI 员工、能力、容量、资源和治理 |
| 工作空间 | 业务如何被交付，结果是否正在形成？ | Cycle、Commitment、执行、证据、验收和关闭 |

“建设”是状态模式，不是永久一级导航。会议、知识、助手、分析是跨切机制。部门是责任聚合，Project/Task 是 Workspace 内部执行记录。

### 12.1 默认交互

CEO 不应该浏览页面寻找问题，而应该进入：

```text
经营简报
→ 识别事项
→ 理解影响
→ 做出决策或委派
→ 等待证据
→ 验证结果
```

经营事项只有三类投影：决策、异常、机会。它们来自正式 Runtime 对象，不建立第二套通知或任务系统。

### 12.2 页面通用语法

```text
对象是什么
→ 当前状态
→ 为什么重要
→ 阻碍结果的约束
→ 谁能处理
→ 证据是什么
→ 下一检查点
→ 完成、暂停、退出或进入下一阶段
```

## 13. 研发工作台的第一个真实任务：Curis 的自研发（完善 Curis）

### 13.1 业务赌注

假设：如果 CEO 能够通过研发工作台表达产品意图，并由 AI 员工完成理解、设计、开发、验证和反馈闭环，那么一人公司可以持续建设自己的软件产品。这里的“Curis 的自研发”是第一个研发任务，具体工作项名为“完善 Curis”，不是业务名称。

### 13.2 最小 AI workforce

初始责任可以由以下角色覆盖，数量不预先固定：

- 产品与业务 AI：理解 CEO 意图、定义结果、准备决策包
- 软件工程 AI：在批准范围内修改代码和运行工程能力
- 质量验证 AI：验证真实用户流程和结果证据
- 运行与反馈 AI：观察运行状态、收集反馈、准备下一周期

### 13.3 软件开发 Workspace

输入是 CEO 的产品意图或经营问题；输出是可以被 CEO 真实使用并验收的软件增量。

完整周期：

```text
提出经营问题
→ 定义软件结果
→ 澄清未知
→ 生成方案
→ CEO 批准
→ 配置责任与能力
→ AI 执行
→ 质量验证
→ CEO 验收
→ 发布或回退
→ 收集使用反馈
→ 关闭周期
→ 形成下一轮决策
```

### 13.4 业务跑通的验收

至少要证明：

1. CEO 能表达并批准一个有限的软件结果。
2. AI 员工能够接受清晰责任，而不是只接收任务文本。
3. AI 员工在真实 Curis 代码和运行环境中工作。
4. 代码、构建、测试、真实用户流程和运行反馈形成证据。
5. CEO 能够验收、退回、暂停或进入下一周期。
6. 失败、未知、回滚、资源冲突和责任升级不会丢失经营事实。
7. 周期关闭后，下一次产品决策能够由结果和学习产生。

代码提交、测试通过或 AI 输出“完成”都不能单独证明业务跑通。

## 14. 当前范围与未来商业化

### 当前单机验证阶段

保留：

- 一个 Local Desktop
- 一个 CEO
- AI 员工和能力配置
- 任意业务创建
- 业务运行和外部结果反馈
- API 或 CEO 手动证据
- 内部可复用业务模式
- 研发工作台；第一个真实研发任务为“Curis 的自研发”（工作项名：完善 Curis）

暂不建设：

- 独立 Admin 产品
- 多租户商业后台
- 计费和订阅
- 模板商城
- 多真实员工协作
- 完整 CRM/ERP
- 所有外部平台的深度集成

### 未来拆分方向

当 Curis 自己的业务运行方式被验证后，再拆分：

```text
Curis Platform / Admin
→ 提供能力、模板、版本、租户和商业服务

Curis Company Runtime
→ 每个一人公司独立创建和经营自己的业务
```

业务模板采用独立复制、用户可修改、版本化升级；平台不能静默改变用户已经运行的公司。

## 15. 本次推导的最终结论

Curis 不是帮助 CEO 管理工作，而是帮助 CEO 建立一家公司，使这家公司能够：

```text
产生承诺
→ 配置兑现能力
→ 委派 AI 员工
→ 运行真实业务
→ 获得外部或真实世界结果
→ 根据证据做出决策
→ 调整公司结构
→ 承担更多、更复杂的承诺
```

产品是否完成，不由页面数量、任务数量、AI 调用次数或生成文档数量判断，而由下面这条闭环判断：

> CEO 的意图是否能够被转化为可接受、可执行、可验证、可交接的 AI 责任网络，并持续产生下一次经营决策。

这条闭环是后续所有 Blueprint、设计、开发和验收的共同起点。

## 16. CEO Operating Experience：把经营内核变成 CEO 身边的 AI 团队

### 为什么需要补这一层

原有 Blueprint 已能描述公司如何创建、运行、反馈和扩展，但仍可能让 CEO 感到自己是在操作一个经营系统，而不是在和一支 AI 团队一起工作。问题不在于少一个页面，而在于缺少一个最靠近 CEO 的责任主体。

### 新产品定义

CEO Assistant 是 Company Runtime 中的第一位 AI 员工，承担 Chief of Staff、Concierge、Coordinator、Decision Partner、Watchdog 和 Memory 的职责。Global Assistant Runtime 只提供身份、通知、查询和命令等承载能力；它不能替代 Assistant 的角色契约。

### CEO Operating Day

`CEO Operating Day` 是已建立公司的默认经营入口，也是验证产品是否真的像 AI 公司的最小体验单位。它持久化一天的 Brief、Matters、Handoffs、Decisions、Exceptions、Evidence、Learning 和 Closeout，状态从 Preparing 到 Closed，并把未完成责任承接到下一天。

### 请求分流原则

CEO 的每个需求不都需要 Outcome 或 Business Bet。Assistant 先将请求分为 Assistive / Ad hoc、Operating、Decision、Coordination、External Commitment；小型辅助保持轻量，会改变公司状态的请求才进入正式 Runtime。

### UI 推导结果

CEO Desk 由 Brief Header、Assistant Brief、Matters、Operating Timeline、Company Pulse、Handoffs / Closeout 组成。左侧为紧凑的 CEO Desk、经营、业务、公司、工作空间导航；Assistant 不占固定第三栏，而在 CEO Desk 主内容、上下文抽屉和统一浮层中出现。聊天只是输入方式，汇报、证据、决策和交接才是结构。

### 行为边界

Assistant 可在授权范围内主动汇报、准备、调查、召集、委派、跟进和执行可逆动作；面对外部承诺、业务启动、责任/结构/高影响资源变化和不可逆发布，必须提交 Decision Packet 并等待 CEO 决定。证据不足、事项已有人负责或没有行动价值时，应聚合、延后或静默。

### Blueprint 更新依据

这一层不是为了扩充 Blueprint 内容，而是因为它回答了一个之前无法回答的经营问题：CEO 每天第一次进入 Curis 后，谁告诉他发生了什么，谁替他准备，谁召集 AI 员工，谁跟进决定，谁把一天收束为下一次经营？因此 Blueprint 由 4.0 更新为 4.1，并新增 CEO Operating Experience 作为产品真相的一部分。

## 17. CEO UI Blueprint：把产品变成可使用的界面

### 之前为什么仍然不够

CEO Operating Day 解决了“CEO 一天如何运行”的问题，但还没有回答“用户打开后具体看到什么”。如果没有屏幕级定义，设计师会重新猜测首页，开发会重新决定导航，测试也无法验证从零创建到持续经营是否走通。

### 全局壳层

Curis 采用 Desktop First CEO 工作台：左侧紧凑导航（CEO Desk、经营、业务、公司、工作空间），顶部上下文栏（公司、业务 / Workspace、同步、Assistant 状态），中间全宽主内容，右侧 Assistant 抽屉按需出现。Assistant 不占固定第三栏；CEO Desk 是它的主界面。

### 从零创建的真实页面

```text
Welcome
→ Founding Brief
→ Company Design
→ First Business
→ AI Team & Capability
→ Launch Check
→ CEO Desk
```

每一页都必须有明确的经营输出：Founding Brief 产生意图和草案，Company Design 产生 Company，First Business 产生 Outcome 和反馈路径，AI Team 产生责任与能力绑定，Launch Check 产生模拟证据和启动批准。不能用空 Dashboard 或纯表单代替。

### 经营阶段的五个一级页面

| 页面 | 首屏问题 | 主要内容 |
| --- | --- | --- |
| CEO Desk / Operating Day | 现在发生了什么，什么需要我？ | Assistant Brief、Matters、Timeline、Company Pulse、Handoffs、Closeout |
| 经营 | 公司是否健康，哪里需要干预？ | 六维脉搏、异常、决策到期、公司约束 |
| 业务 | 哪些业务创造价值，是否继续？ | Outcome、外部结果、投入产出、业务阶段 |
| 公司 | 公司有没有能力兑现承诺？ | AI Workforce、责任、Capability、Capacity、权限 |
| 工作空间 | 业务如何交付，结果是否形成？ | Cycle、Commitment、Evidence、Acceptance、Insight |

Meeting、Decision、Evidence Review、Change 是上下文模式，不是新的一级导航。它们完成后必须回到原页面位置，并留下决策、证据或交接。

### 交互设计原则

- 先显示状态和为什么，再显示证据和动作。
- 每个动作都显示责任人、来源、置信度、影响和下一检查点。
- CEO 的动作是决定、调查、委派、召集、等待、静默，而不是逐一管理 Task。
- 空、阻塞、Unknown、Stale、Conflict 都是正式页面状态，不能只设计成功状态。
- 设计验收必须走通“表达意图 → 创建公司 → 配置业务 → 批准 AI 团队 → 启动 Workspace → 查看外部结果 → 做决定 → 回到下一天”。

因此 Blueprint 由 4.1 更新为 4.2：CEO Operating Experience 现在不仅描述角色和日程，也描述用户真正看到的页面和交互。

## 18. CEO Assistant Runtime、AI 组织与 Workspace Studio

### CEO Assistant 是独立对象

CEO Assistant 不是 CEO Desk 的视觉组件，而是 Company Runtime 中每家公司唯一的 Company-level AI Employee。它拥有稳定身份、责任契约、能力、权限、上下文、质量证据和生命周期。当前生命周期为：

```text
Created → Configured → Learning Context → Operating
→ Evaluating → Upgraded / Reassigned
```

Learning Context 不是模型私自训练，而是对 Company Charter、CEO 偏好、有效决议、业务状态和当天工作记忆的可追溯上下文版本。

### AI 团队不是平级列表

组织关系收敛为：

```text
CEO
└── CEO Assistant
    ├── Business Analysis AI
    ├── Business Engineering AI
    ├── Engineering AI
    ├── Growth / Marketing AI
    └── Finance / Operations AI
        └── Workspace AI（按业务 Workspace 实例化）
```

Assistant 对 CEO 汇报并协调专业 AI；专业 AI 向 Assistant 汇报运行状态，但对自己的专业结果负责；Workspace AI 向所属专业 AI / Workspace Owner 汇报。高影响、跨业务或越权问题沿链路向上升级到 CEO。

### Workspace 是装修后才交付的空间

Workspace 分为 Studio 和 Runtime 两种模式。Business Engineering 在 Studio 中完成：

```text
Discover → Blueprint → Compose → Bind → Staff → Simulate → Approve → Operate
```

Studio 不是自由摆放的画布，而是受业务语义约束的组装器。它必须让设计者把 Stage、Role Slot、Agent、Capability、Tool、Knowledge、External System、Evidence 和 Acceptance 连接成可运行结构，并显示缺口、过载、权限、授权、冲突和失败出口。

只有 CEO 批准了 Blueprint 版本和影响分析，才创建或升级 Workspace Runtime。运行中的 Workspace 不被 Studio 草稿静默改变；新版本必须经过差异、模拟、回滚和采用复盘。

### 这次更新解决的问题

- Assistant 从“体验角色”变成了可创建、配置、运行、评估和升级的对象。
- AI 团队从平级 Agent 集合变成有汇报、授权和升级路径的组织。
- Workspace 从“业务运行容器”变成 Business Engineering 可以持续装修和交付的核心产品能力。

因此 Blueprint 由 4.2 更新为 4.3。

## 19. 中文 CEO 界面规则

产品逻辑中的 Company、Workspace、Outcome、Evidence 等英文可以作为内部对象名或开发标识，但真实 CEO 使用的导航、按钮、状态、提示、表单、错误信息和 Assistant 回复必须统一使用简体中文。英文仅在中文后作为括号注释出现，不能单独成为用户操作词。

这不是翻译偏好，而是用户边界：当前 Curis 的第一个真实用户是中文 CEO，设计团队不应在实现阶段再次决定界面语言。UI Blueprint 已补充中文标签映射，并更新关键线框。

## 20. 内容发布 Agent 与布局参考：从外部机制回到 Curis

### 20.1 为什么要参考

小红书与抖音工作台不是简单的“内容列表”。它们需要持续处理外部信号、平台差异、发布授权、互动反馈和结果复盘。仅凭通用 Agent 目录或项目看板，无法回答 CEO 最关心的三个问题：现在要创造什么结果、谁正在承担责任、外部结果是否值得继续投入。

因此参考 Buffer、Hootsuite、Predis 和 Later，不是为了复制它们的后台，而是为了验证内容团队中哪些机制已经被真实业务反复证明：平台适配、信号监听、审批、排期、版本审计和发布后反馈。

### 20.2 机制到 Curis 的收敛

| 外部机制 | 说明 | Curis 的产品结论 |
| --- | --- | --- |
| 平台感知创作 | 同一个意图在不同平台需要不同格式、长度和表达 | `ContentIntent → platformVariant`；小红书与抖音独立检查、独立审批 |
| Agent 监听与简报 | Agent 不只生成文本，还要从实时信号中找出值得 CEO 关注的变化，并附来源与行动建议 | 研究 AI 提交带证据的选题假设；Assistant 只在影响决策时汇报 |
| 自动节奏 + 人工排期 | 自动发布可以维持节奏，但高影响内容仍需要人工确认 | `Cadence` 负责检查点和提醒；日历只是节奏投影，不能绕过 CEO 门禁 |
| 版本审批与回执 | 审核意见必须绑定版本，实际发布版本必须可追溯 | `versionId`、`reviewComments[]`、`publishedVersionId` 进入 ContentItem 审计 |
| 发布后互动分流 | 评论、私信、提及和咨询会产生线索、风险或外部承诺 | `InteractionItem` 进入内容结果链，不新增 CRM；ReplyPolicy 决定自动回复或升级 CEO |

### 20.3 布局结论

内容工作台的首屏顺序收敛为：

```text
业务目标 / 当前周期 / 本周期承诺
→ 外部信号摘要（来源、新鲜度、置信度）
→ 内容运行队列（当前状态与唯一主动作）
→ 按需 Assistant 上下文抽屉
→ 发布回执与外部结果窗口
→ 复盘结论与下一轮 Decision
```

对公开的 Hootsuite Publisher 视觉布局做了补充核对：日历网格适合观察节奏，筛选器适合切换账号 / 状态，右侧详情面板适合查看单条内容的版本与排期；它验证了“队列 / 节奏视图 + 上下文详情”的组合有价值，但也验证了日历不应成为 CEO 的主经营面。因此 Curis 将日历保留为次级节奏视图，主面仍以结果、责任、证据和 Assistant 上下文为中心。[Hootsuite Publishing](https://www.hootsuite.com/platform/publishing)

AI 团队状态以一条状态带存在于队列上方，不增加第三栏。每个岗位显示当前责任、状态、容量、最近交接和下一检查点。CEO 处理的是责任、证据和决策，不是逐个阅读 Agent 聊天记录。

### 20.4 明确拒绝的方向

- 不建立“内容超级 Agent”，由多个有责任边界的岗位协同完成结果。
- 不把日历、素材库、社交收件箱或互动数量提升为产品根。
- 不让 Agent 自动发布、自动报价或自动承诺外部结果。
- 不把 Hootsuite 式监听、Predis 式排期或 Later 式审批复制成第二套后台；它们必须进入 Company OS / Workspace Runtime 的统一状态、证据和决策链。

这次推导的最终落点不是新增一个内容模块，而是为运营 Workspace 确认了一套可装修、可模拟、可审批、可运行的 AI 团队结构。相关外部参考：[Buffer AI Assistant](https://support.buffer.com/article/583-using-buffers-ai-assistant)、[Hootsuite AI](https://www.hootsuite.com/platform/ai)、[Predis 内容日历与自动发布](https://help.predis.ai/en/article/content-calendar-vs-autp-posting-on-predis-7hcauc/)、[Later 团队审批](https://later.com/blog/social-media-management-for-teams/)。
