# Curis 产品开发队列 v2.0

Status: Review

日期：2026-08-14

本队列以 `docs/01_Product/Curis_Product_Master_Map.md`、`Curis_Product_Page_Map_v1.0.md` 和
`Curis_Current_State_and_Product_Drift_Audit.md` 为输入。它取代旧的“模型准备→逐页
补模块”顺序；模型、Agent、Skill、Tool、知识和连接器是支撑能力，不是用户的产品主线。

## 一、唯一用户主线

```text
打开 Curis
→ 认识用户
→ Assistant 了解想做什么
→ 生成最小业务方案
→ 用户确认第一步
→ 看见首个可感知结果
→ 进入 CEO 工作台
→ 进入业务空间
→ 业务拥有独立 Workspace
→ 组织中心 / 人才市场补齐承担者与能力
→ Workspace 持续工作
→ 结果 / 证据 / 反馈
→ CEO 决定
→ 公司、业务、员工、能力和 Workspace 进入下一轮
```

### 不得再出现的主线倒置

- 不要求用户先理解 Blueprint、Role Slot、Capability Binding、Simulation 或 Operating Version。
- 不把模型目录、人才市场、设置或 Runtime 状态做成第一次打开的首页。
- 不把“公司已创建、员工已生成、Draft 已保存”当作首个价值。
- 不把 Runtime 门禁直接变成业务办公室的首屏语言。

## 二、交付顺序

### P0 · 产品母版与壳层收敛

目标：让所有开发先对齐一个产品形态。

交付：

- 六个主工作区域：CEO 工作台、业务空间、组织中心、人才市场、资料库、会议。
- 左下角用户头像菜单承载个人、公司、资源、通知、帮助和数据维护。
- 全局 Assistant、搜索、最近工作、通知和上下文返回不增加一级导航。
- 页面共同契约：主工作区 + 上下文侧栏 + 按需右侧检查器；每页具备空态、等待、异常、恢复、结果。
- 清理当前导航中旧 Project/Task-first 入口对普通用户的主导地位，但保留兼容入口。

验收：普通用户能说出“我在哪里、这页要做什么、完成后回哪里”；不会先看到 Runtime 术语。

### P1 · First Value：首次打开到首个可感知结果

目标：用户不必先设计公司，先完成一件真实小事。

路径：

```text
认识用户
→ Assistant 对话
→ 识别意图
→ 业务 / 第一 Workspace 预览
→ 少量关键确认
→ 运行第一项可检查工作，或给出真实阻塞和下一步
→ CEO 工作台
```

要求：

- 模型仅作为 Assistant 的最小运行准备；能力详情按需展开。
- Assistant 是第一位 AI 员工，但第一次体验表现为伙伴，不是配置表。
- 预览必须告诉用户：要做什么、谁来做、会产出什么、哪些动作需要确认。
- 失败必须可解释、可恢复，不能生成假公司或假结果。

### P2 · CEO 工作台：公司今天发生了什么

目标：把 CEO Desk、经营、Assistant 简报和待处理收敛成一个可行动首页。

首屏内容：

1. 公司简报与今日变化。
2. 需要 CEO 处理的问题和决定。
3. 当前正在运行的工作。
4. 结果、风险、来源和下一检查点。
5. Assistant 对话与“继续今天最重要的事”。

不做：数据大屏、全量 Task/Run 列表、固定秘书侧栏、未经证实的指标。

### P3 · 业务空间与 Workspace Portal

目标：用户先理解“我在经营什么”，再进入独立办公室。

- 业务空间展示业务目标、投入、结果、负责人和健康，不把所有业务压成同一种看板。
- Workspace Portal 展示可开始的业务方向和已建办公室；模板不等于已拥有业务。
- Workspace Studio 以办公室预览为中心：目标、团队、工作方式、能力缺口和首个结果。
- 缺能力时可以保存、浏览和继续定义；只在真实运行或外部发布前检查可执行性。

### P4 · 人才市场与组织中心

目标：把成熟 AI 能力引入公司，但不把普通用户变成 Agent 管理员。

人才市场负责：发现专家、Skill、Connector、Tool、Agent、工作方法和职业模板。

组织中心负责：公司已有谁、谁负责什么、谁正在工作、怎样招募、组队和调整。

头像菜单设置负责：连接、授权、维护、撤销、成本、权限、主题和数据。

硬边界：

- 市场项目在未招聘、未安装或未授权前，不出现在公司可运行资源中。
- 岗位是责任契约，AI 员工是当前承担者，Model/Agent 是可替换实现。
- 招募与组队不同：招募形成公司员工；组队把已有员工放入某个 Workspace。
- 缺能力形成责任卡，明确缺什么、负责人、影响、恢复入口，不阻断普通浏览和搭建。

### P5 · 第一条完整 Workspace 结果链

先选一条最能证明 Workspace 独立性的业务做完整纵向闭环；研发、小红书、抖音仍是首批模板，
不是三个固定演示实例。

通用验收链：

```text
目标
→ 业务办公室首页
→ 专家团队 / 岗位责任
→ 真实工作对象
→ 成熟执行能力接入
→ 正常运行
→ 等待 / 失败 / 局部介入 / 恢复
→ Evidence / 外部结果或 CEO 手动回填
→ Acceptance
→ Decision
→ 下一周期 / 公司变化
```

Workspace 必须拥有自己的布局、工作对象、员工职责、输入输出、结果区和用户介入点，
不能只是统一 Runtime 页面换标题。

### P6 · 资料库、会议与决策回流

目标：让结果真的回到公司经营。

- 资料库：资料来源、权限、引用、过期和结果沉淀。
- Workspace Meeting：解决局部方案、质量、交接和阻塞。
- Company Meeting：处理跨业务资源、公司方向和外部承诺。
- DecisionPacket 是 Assistant 准备的判断材料，Decision 才是 CEO 的正式选择。
- 会议和结果必须回到原 Workspace、CEO 工作台、资料库或下一周期。

### P7 · 其他 Workspace 模板

在共享 Workspace 契约和第一条结果链稳定后，分别完成：

- 研发工作台：代码、终端、测试、变更、Review 和交付。
- 小红书运营工作台：受众、选题、图文、发布、评论/私信、线索和平台回流。
- 抖音 / TikTok 运营工作台：趋势、脚本、素材、成片、发布、观看/互动/成交回流。

三者可以由三个开发会话并行，但必须共享同一 Company OS、员工/能力/结果契约；每条线独立验收，
不拼隔离数据库、不把一个模板的证据冒充另一个模板。

### P8 · 自动运行、成本、健康与发布

最后完善：

- 工作流从办公室路径生成，不做顶层 Workflow 平台。
- 日历 / 定时用经营语言创建，支持暂停、错过、重试和下一次时间。
- 成本和健康服务于 CEO 判断，不做后台指标墙。
- Local Desktop 打包、签名、公证、安装、升级、数据迁移和反馈闭环。

## 三、每条开发任务的统一交付合同

每个 Issue 必须同时写清：

1. 用户目标和进入路径。
2. 页面主工作区、上下文侧栏、检查器和主动作。
3. 真实对象及其来源、Owner、状态和下一步。
4. 正常、空、等待、失败、恢复和返回原工作的路径。
5. AI、用户、外部系统分别做什么。
6. 结果如何形成 Evidence、Acceptance 和 Decision。
7. Browser、SQLite、重载、重启和 Packaged Desktop 证据。
8. 未完成项、环境阻塞和禁止宣称的范围。

页面、路由、接口、Draft、目录可见、focused test 或静态 build 都不能单独构成完成。

## 四、并行规则

- P0–P4 的 Company OS、Assistant、壳层、人才市场和共享契约由主线统一维护。
- P5 之后，研发 / 小红书 / 抖音可以并行，但每条线必须使用独立 worktree、Allowed Files、Issue 和 Review。
- 任何产品研究先进入 Master Map / Page Map / 研究报告；不直接派发代码。
- 主开发按本队列顺序自动领取下一项；完成一项必须回交证据并进入下一项，不以“有代码”停下。

## 五、当前明确不做

- 不建立第二套 Blueprint。
- 不把人才市场做成计费市场或公开评分系统。
- 不复制竞品私有 Agent、Cookie、知识或内部配置。
- 不把成熟外部 Agent 的工作界面全部重写成 Curis 控制台。
- 不在研发工作台预置“完善 Curis”或任何固定 CEO 任务。
- 不以门禁和 Runtime 术语替代普通用户的业务语言。
