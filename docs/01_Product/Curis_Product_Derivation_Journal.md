# Curis 产品推导日志

Status: Review

记录类型：按对话顺序的产品推导过程 / Derivation Journal  
记录日期：2026-07-31  
对应产品结果：Curis Product Blueprint 5.0
说明：本日志记录从截图所示起点开始，如何一步一步从 CEO 经营场景推导产品结构。每一阶段记录的是可复盘的产品判断、反思和取舍，不是页面实现记录，也不是把最终结论倒推成一篇产品说明书。

## 2026-08-10 · 重新校正：App 完整性不能被部署方式削弱

### 触发问题

复核 Blueprint 时发现，Local Desktop、单一 CEO、未来暂不商业化等条件逐渐变成了产品层面的
“不做”规则，导致模型添加、Skill 接入、能力分配、会议、日历和完整业务动线被推迟或省略。

### 反思

这混淆了两个问题：

```text
产品应该是什么
实现当前如何交付
```

Local Desktop 只是交付方式；CEO 自己使用时仍然需要完整经营公司所需的能力。否则 Curis 只能
验证一套经营概念，不能验证真实产品。

### 新的推导顺序

```text
完整 App 身份
→ CEO 经营生命周期
→ 用户使用动线
→ 产品地图和导航
→ 模型 / Skill / Tool / AI 团队 / Workspace 等能力
→ Runtime 与 UI 实现
→ 分阶段交付
```

### 收敛结果

Blueprint 5.0 不再以“当前做什么、不做什么”为主，而是完整描述：

- 首次进入和公司创建
- CEO Operating Day 与 CEO Assistant
- 业务版图、AI 团队和组织关系
- 能力中心和能力分配
- Workspace Studio 与业务办公室
- 研发、小红书、抖音三条业务
- 外部结果、证据、验收和决策
- 会议、日历、知识、成果、成本和扩展

实现状态单独用“已有运行基础、建设中、待接入、人工回退、未来商业化”标记，不从产品形态
中删除未完成能力。

## 0. 推导起点：不要先写 Blueprint

### 截图所示的第一真实场景

CEO 第一次打开 Curis 时，系统状态是：

~~~text
Company：未建立
Business：未建立
Organization：未建立
Capacity：未配置
Workspace：未建立
~~~

这时不能展示一组空的 Dashboard、项目、任务或组织模块。产品必须把 CEO
带入一个真实的建设动作：从一句经营意图开始，逐步形成第一家公司、第一项
业务和第一个可运行周期。

所以本次推导的起点不是“已有公司如何查看状态”，而是：

> CEO 第一次打开 Curis，如何从一句经营意图走到一家已经可以开始第一个业务周期的公司？

### 触发问题

最初的要求不是“补充 Blueprint 章节”，而是：

> 不要把 Blueprint 当成目标；先不断理解产品、质疑旧方案、从 CEO 如何经营一家公司重新推导。

当时已有的 Blueprint 已经有页面、模块、Runtime 和导航，但它仍然可能是在旧框架内完善，而不是重新理解 Curis。

### 初始假设

- Curis 可以继续沿着已有模块补齐。
- Blueprint 只要写得更完整，设计和开发就能继续。
- 页面和模块已经大致代表产品结构。

### 第一次反思

这些假设没有回答最重要的问题：

- CEO 为什么需要 Curis？
- 公司第一天还没有任何业务时，Curis 应该做什么？
- 哪些工作属于 CEO，哪些属于 AI？
- 如果没有 Project、Task、Meeting，公司的经营链还能否成立？
- 如果业务失败，系统如何帮助公司继续经营？

### 第一条推导规则

从此以后，推导顺序固定为：

~~~text
真实经营场景
→ CEO 要完成的经营动作
→ 公司需要承担的职责
→ 业务运行过程
→ 角色、对象和状态
→ 产品入口与页面
→ Blueprint
~~~

而不是：

~~~text
已有页面
→ 补模块
→ 补字段
→ 补 API
~~~

## 1. 第一步：重新定义自己的身份

### 用户要求

不要把自己当开发者，也不要把自己当需求执行者，而要像长期服务 CEO 的产品规划师。

### 当时的产品问题

如果 Curis 是 CEO 经营一家 AI 公司的数字世界，那么产品规划的起点应该是什么？

### 反思

页面、按钮、数据结构都只是实现手段。真正需要规划的是：

- CEO 如何建立公司
- 公司如何选择业务
- 公司如何配置能力
- AI 如何承担责任
- 结果如何被验证
- CEO 如何根据结果继续经营

### 推导结论

Curis 的产品单位不是页面，而是：

> CEO 的经营意图经过公司结构、责任、能力和 Workspace 运行，最终产生可验证结果并回到 CEO 决策的闭环。

### 对后续的影响

后续任何模块都必须回答：

1. 它解决哪一个经营问题？
2. 它在真实公司里承担什么职责？
3. 它的上下游是谁？
4. 它如何从开始运行到关闭？
5. CEO、AI 和员工分别做什么？
6. 它如何产生结果和下一次决策？

---

## 2. 第二步：先从 CEO 的五个问题出发

### 用户提出的五层

CEO 会持续关心：

1. 公司现在是什么情况，哪些需要我知道和处理？
2. 业务如何运转，产生什么价值，要不要扩大？
3. 公司能力是否足够，人员有没有过载？
4. 员工的工作安排是否合理，是否需要 CEO 干预？
5. 共识产出的结果集合和知识引用在哪里？

### 初始产品映射

最初容易把五层直接做成五个中心页面：

~~~text
状态中心
业务中心
能力中心
员工工作中心
知识中心
~~~

### 反思

五层不是五个产品模块，而是 CEO 的五种经营视角。

如果直接做成五个中心，会产生问题：

- 经营状态与业务结果被拆开
- 能力与工作承诺无法关联
- 知识变成资料仓库
- 员工页面重新变成任务管理
- CEO 仍然需要自己在页面之间拼接公司状态

### 推导结论

五层应该被重新组织为：

~~~text
经营：现在发生了什么？
业务：是否创造外部价值？
公司：是否具备兑现能力？
工作空间：如何交付结果？
Truth / Decision：事实、共识和学习如何支撑所有判断？
~~~

其中第五层不做独立导航，而做跨切真相层。

---

## 3. 第三步：加入“从零创建公司”视角

### 用户提出的新问题

之前的五层是“公司已经在运行”的视角，但 CEO 也可能：

- 从零创建一家公司
- 扩展一个新业务
- 创建新的部门
- 配置新的能力

### 初始假设

可以先让 CEO 创建：

~~~text
Company
→ Department
→ Employee
→ Capability
→ Business
→ Project
→ Task
~~~

### 反思

这仍然是软件配置顺序，不是真实公司的形成顺序。

CEO 第一天通常不会先拥有完整组织。他需要先回答：

- 为什么创建公司？
- 服务谁？
- 第一个业务是什么？
- 第一个结果是什么？
- 谁能承担责任？
- 缺什么能力？
- 多少资源够开始？

### 推导结论

从零创建公司的路径应是：

~~~text
CEO 意图
→ 公司理解
→ 第一个业务赌注
→ 第一个结果
→ 最小责任
→ 最小能力与资源
→ Cycle 或 Workspace
→ 第一个真实结果
~~~

### 关于部门能力的重新判断

“创建部门”能力需要存在，但部门不是第一天的默认步骤。

部门只有在出现以下事实后才成立：

- 责任重复出现
- 需要稳定协作
- 多个业务共享同一能力
- 需要独立容量、权限和服务承诺
- CEO 已经无法亲自协调全部细节

于是组织形成顺序变成：

~~~text
结果缺口
→ 稳定责任
→ 所需能力
→ 多主体协作
→ 部门或共享服务
~~~

## 4. 第四步：确认 Curis 到底是什么公司

### 用户确认

Curis 本身就是帮助一位 CEO：

~~~text
从 0 搭建公司
→ 配置公司
→ 开始业务
→ 招聘员工
→ 配置能力
→ 持续运行
→ 结果反馈
→ 跟进
→ 优化
→ 扩展业务
→ 拓展工作空间
~~~

### 初始理解

Curis 可能是一套帮助普通企业经营的 AI Company OS。

### 继续追问

但如果 Curis 只是一个工具，它自己是否也应该按照同样的方式被建立和经营？

### 推导结论

Curis 不是描述一家公司的软件，而是：

> 帮助 CEO 真实建立、运行、优化和扩展一家 AI 公司的数字经营系统。

因此 Curis 自己也必须能够成为第一个被创建和经营的公司。

## 5. 第五步：把生命周期变成产品主线

### 用户给出的链路

~~~text
从 0 开始搭建公司
→ 配置公司
→ 开始业务
→ 招聘员工
→ 配置能力
→ 持续运行
→ 结果反馈
→ 跟进
→ 优化
→ 扩展业务
→ 拓展工作区
~~~

### 初始产品表达

可能把每一步做成一个功能模块或向导步骤。

### 反思

这些步骤不是一次性向导，而是会循环发生：

- 公司不是配置一次就结束
- 员工不是招聘后就永远合适
- 能力会降级
- 业务会暂停、转移或关闭
- Workspace 会扩展、重构或归档
- 每一个结果都会改变下一步经营

### 推导出的生命周期

~~~text
Company Intent
→ Company Design
→ Business Bet
→ Responsibility & Capability
→ Cycle / Workspace Launch
→ Operate
→ Evidence & Acceptance
→ Decision
→ Reconfigure
→ Expand / Exit
→ Next Cycle
~~~

### 生命周期的产品意义

每个阶段必须拥有：

- 进入条件
- Owner
- Input
- Runtime Action
- Output
- Exit Condition
- 下一阶段
- 失败路径
- 反馈和关闭方式

这也成为后续 Blueprint 的 Runtime 基础。

## 6. 第六步：反推产品结构，而不是反推页面目录

### 用户要求

业务逻辑已经理清，开始反推产品设计：

> 为了完成持续经营，产品上应该如何设计？

### 初始候选导航

当时曾考虑：

~~~text
经营
业务
公司
工作
~~~

以及 Meeting、Knowledge、Assistant、Capability 等中心。

### 反思

导航不应该照搬生命周期。

生命周期是时间和状态；导航应该对应 CEO 反复提出的经营问题。

### 推导出的四个稳定入口

| 入口 | CEO 问题 |
| --- | --- |
| 经营 | 现在发生了什么，什么需要我处理？ |
| 业务 | 公司为谁创造什么价值，是否值得继续？ |
| 公司 | 公司是否有能力兑现当前承诺？ |
| 工作空间 | 业务如何被交付，结果是否正在形成？ |

### 为什么保留四个而不是合并

- 经营和业务不能合并：一个是当前控制，一个是外部价值和投资判断。
- 业务和公司不能合并：一个是价值需求，一个是能力供给。
- 公司和工作空间不能合并：一个是组织能力，一个是具体交付。
- 不能省略经营：CEO 必须有一个当前控制面。

### 再次反思：四个入口仍然可能是页面思维

因此最终判断变成：

> 四个入口不是四个独立产品，而是同一套经营对象在不同 CEO 问题下的投影。

---

## 7. 第七步：从时间尺度继续挑战导航

### 新问题

CEO 看同一家公司时，至少有三个时间尺度：

~~~text
即时控制：今天哪里异常？
运行周期：这一轮业务是否产生结果？
经营地平线：下一阶段押注、扩展还是重构？
~~~

### 反思

如果没有时间尺度：

- 经营会退化为 Dashboard
- 业务会退化为静态列表
- 工作空间会退化为 Task Board
- 公司会退化为通讯录

### 推导结论

Curis 需要：

~~~text
四个经营视角
×
三个时间尺度
×
一个 Decision Control Plane
~~~

首页因此不能永远是固定 Dashboard，而应该根据公司状态打开：

- 公司为空：Founding Brief
- 公司配置中：Company Design
- 业务验证中：First Value
- 业务运行中：Company Now
- 公司变化中：Reconfiguration

---

## 8. 第八步：发现“承诺”比“任务”更接近公司现实

### 新问题

如果 CEO 同时接了两个业务，资源不足时，他真正需要知道什么？

不是“哪些任务延期”，而是：

- 已经答应了谁什么
- 哪些承诺会受影响
- 哪些承诺必须保护
- 哪些承诺可以重新协商

### 反思

项目系统把计划当成核心，真实公司却由一组承诺组成。

### 推导出的三层对象

~~~text
Promise / Obligation
→ 对外或对组织的结果承诺

Commitment
→ 某个责任主体接受的交付责任

Task
→ 为完成责任而采取的内部动作
~~~

关系为：

~~~text
外部承诺
→ 内部责任承诺
→ Work Package
→ Task
→ Evidence
→ Acceptance
~~~

### 承诺生命周期

~~~text
提出
→ 协商
→ 承诺
→ 执行中
→ 有风险
→ 已兑现 / 已违约
→ 关闭
→ 学习
~~~

### 得出的产品原则

内部完成不等于客户结果完成。没有验收或真实反馈，不能自动关闭经营目标。

---

## 9. 第九步：明确外部结果和外部系统

### 用户提出的问题

“客户承诺、客户验收和外部结果具体指什么？”

用户给出了两个业务例子：

- 软件开发：客户要的是完全可用的软件交付，由 CEO 接待客户，再把判断反馈给 AI 员工。
- 内容增长：需要抖音数据，例如播放、点赞、收藏、吸粉、下单和成交。

### 初始误解

容易把“外部结果”理解成必须有一个付费客户或必须有完整 CRM。

### 用户补充

外部结果可能来自：

- 客户验收
- 平台数据
- 用户行为
- 交易结果
- CEO 手动反馈

平台 API 可能有授权限制，因此没有 API 时必须允许 CEO 手动填入价值反馈。

### 推导结论

外部结果的关键不在于是否付费客户，而在于：

> 结果来自 Curis 之外的真实世界，不能只由 Curis 内部任务状态伪造。

Evidence 支持两条输入路径：

~~~text
API / 外部系统自动回传
+
CEO 手动录入并附来源、时间窗口、证据和可信度
~~~

### “外部系统负责原始执行”的澄清

这不是说 Curis 不执行工作，而是分工不同：

| 场景 | Curis | 外部系统 |
| --- | --- | --- |
| 软件开发 | 结果、责任、周期、验收和发布决策 | GitHub、CI、云平台和运行环境产生原始事实 |
| 内容增长 | 内容目标、创作责任、结果解释和下一轮决策 | 抖音/小红书发布及流量、交易数据 |

Curis 拥有经营事实、承诺、决策和解释；外部系统保有它产生的原始事实。

## 10. 第十步：能力和容量必须分开

### 新问题

公司拥有某种能力，是否就代表可以继续接业务？

### 反思

不一定：

- 员工已经过载
- AI 并发受限
- 预算不足
- 数据权限未开通
- 时间窗口冲突
- 共享能力已被其他业务占用

### 推导结论

~~~text
Capability = 能不能做
Capacity = 现在能做多少
Allocation = 当前给谁使用
~~~

资源生命周期：

~~~text
需求估算
→ 提出分配
→ 预留
→ 承诺
→ 消耗
→ 释放
→ 评估价值
~~~

CEO 扩展新业务前，系统必须先模拟：

~~~text
新业务需要什么
→ 占用哪些能力
→ 消耗多少容量
→ 影响哪些现有承诺
→ 有哪些缩小、延后、转移或拒绝方案
~~~

因此，资源不是设置页面，而是承诺兑现能力的约束。

## 11. 第十一步：把 AI 员工从“聊天角色”提升为责任主体

### 初始想法

AI 可能只是：

- 聊天助手
- 任务执行器
- 工作流节点
- 生成内容的工具

### 反思

如果 Curis 要真正经营一人公司，AI 必须能够：

- 接受责任
- 执行工作
- 产生证据
- 推动业务
- 发现风险
- 在边界处升级
- 持续被评价和调整

### AI 员工契约

每个 AI 员工必须明确：

- 结果
- 业务范围
- 数据范围
- 能力
- 行动权限
- 质量标准
- 成本和延迟边界
- 证据要求
- 升级条件
- 失败和备用方案

### AI 不得静默完成的事情

- 修改公司意图
- 改变战略重点
- 对外新增承诺
- 改变资源优先级
- 改变责任归属
- 修改公司结构
- 把没有证据的结果标记为完成

这使 AI 成为真正的责任主体，而不是拥有无限权限的自动化脚本。

---

## 12. 第十二步：员工端也必须围绕责任，而不是任务

### 新问题

如果真实人类只有 CEO，为什么仍然要设计员工模型？

### 反思

因为 AI 员工仍然需要被创建、配置、授权、评估、暂停和替换；未来商业化也可能扩展到其他主体。

员工或 AI 员工进入系统时，第一眼应该看到：

~~~text
我承担什么结果
为什么重要
拥有什么权限
可以使用哪些能力
什么时候提交证据
遇到什么情况升级
~~~

### 责任运行过程

~~~text
提出责任
→ 接受 / 协商 / 拒绝
→ 使用能力和资源
→ 执行
→ 提交证据
→ 报告风险
→ 交接或关闭
~~~

拒绝和协商不是异常，而是公司判断能力的一部分。

### 得出的组织原则

组织不是先建好再分任务，而是从真实责任和能力缺口中长出来。

## 13. 第十三步：失败路径不能被最后补上

### 反思

如果只设计：

~~~text
创建 → 运行 → 成功 → 扩展
~~~

这仍然不是一家真实公司的经营系统。

真实公司会遇到：

- 客户拒绝
- AI 失败
- 责任人拒绝
- 能力降级
- 资源冲突
- 证据过期
- 判断错误
- CEO 暂时无法参与
- 业务必须暂停或关闭

### 四类失败

| 类型 | CEO 要判断 |
| --- | --- |
| 价值失败 | 客户、需求或假设是否不成立 |
| 交付失败 | 范围、周期、质量或依赖是否错误 |
| 供给失败 | 人、AI、能力、资源或权限是否失效 |
| 判断失败 | 事实、证据、来源或推断是否不可靠 |

### 异常生命周期

~~~text
发现
→ 识别范围
→ 临时控制
→ 选择恢复方案
→ 执行恢复
→ 验证恢复
→ 关闭
→ 学习
~~~

### 必须存在的真实状态

~~~text
On Track
Attention
At Risk
Blocked
Unknown
Stale
Conflict
Resolved
Verified
~~~

没有证据不能自动显示正常；冲突不能被平均；过期决策必须重新验证。

### 业务退出

~~~text
Pause / Reduce / Transfer / Close / Merge / Split
~~~

退出前必须保护承诺、交接责任、释放资源、保留历史和学习，不能用 Delete 消除经营事实。

## 14. 第十四步：公司复杂度应该渐进式激活

### 新问题

如果 Curis 需要支持从零到规模化，是否第一天就展示所有企业能力？

### 反思

第一天展示完整部门、权限、报表、工作流和知识库，会把 CEO 推入配置软件，而不是开始经营。

### 推导出的成熟度

| 阶段 | 真实触发 | 系统激活 |
| --- | --- | --- |
| 创始 | 只有 CEO 意图 | Founding Brief、最小公司方案 |
| 首次价值 | 面对真实世界 | 外部结果、验收和反馈 |
| 可重复运行 | 同类工作重复、多 AI 协作 | Workspace、Cycle、责任合同 |
| 委派经营 | CEO 无法覆盖全部细节 | AI 权限、升级、连续性 |
| 业务组合 | 多业务争夺资源 | 组合、战略重点、投资和退出 |
| 重构扩展 | 重复异常、能力瓶颈、新业务 | 组织重构、共享服务、迁移 |

### 得出的原则

> 公司结构、页面复杂度和 AI 能力，都必须由真实经营事实逐步激活。

## 15. 第十五步：确认平台层与用户公司层

Curis Company Runtime

## 20. 新的质疑：公司经营内核仍然不等于 CEO 身边的 AI 团队

在前面的推导完成后，新的检验问题出现了：如果 CEO 打开 Curis，只能看到公司、业务、能力、Workspace 和结果，他看到的是一个合理的经营内核，但是否真的像一个团队在陪他工作？

这个问题不能用再增加一个“Assistant 页面”来回答。现实里的 CEO 助理不是一个按钮，也不是一个聊天侧栏。他是最靠近 CEO 的角色：每天主动汇报，知道哪些事项应该打扰 CEO，提前准备会议和决策，协调其他人，追踪承诺，并把一天的经营连续起来。

因此新的判断是：

> CEO Assistant 必须从“全局入口”升级为 Company Runtime 中真实存在的第一位 AI 员工；Global Assistant Runtime 只是它的基础设施，而不是它的产品定位。

这不是为了增加一个角色，而是为了补足 CEO 与 AI 团队之间缺失的责任主体。没有这个主体，CEO 必须自己从各个模块拼出公司状态、自己召集 AI 员工、自己记住未完成事项，Curis 仍然像一个等待 CEO 操作的软件。

## 21. 重新选择产品验证单位：从模块改为 CEO Operating Day

如果从模块出发，会继续问“Assistant 页面在哪里”“Meeting 页面怎么做”。这些问题会把设计带回页面中心。更可靠的验证单位是 CEO 的一天：从第一次进入 Curis，到知道公司发生了什么、提出新想法、召开会议、接收结果、做决定并结束一天。

一天的场景推导如下：

| 时刻 | CEO 真实问题 | Assistant 应承担的工作 | 专业 AI 的工作 | CEO 必须保留的决定 |
| --- | --- | --- | --- | --- |
| 08:30 | 昨天发生了什么，今天最重要的是什么？ | 汇报变化、收入/价值、风险、待决策和机会，排序注意力 | 从 Workspace、Evidence、Insight、Decision Runtime 取证 | 接受处理顺序、委派、调查、等待或静默 |
| 09:00 | 这个机会值得研究吗？ | 把自然请求分类为 Opportunity / Analysis Request，补齐最少上下文 | Business Analysis 调查市场、证据和选项 | 是否投入调查、何时形成决策 |
| 10:30 | 如果值得做，怎样建立业务？ | 整理 Decision Packet，跟踪从分析到建设的交接 | Business Engineering 设计 Workspace；Workspace AI 负责运行 | 是否下注、定义 Outcome、批准资源和承诺边界 |
| 14:00 | 会议要讨论什么，结论是什么？ | 会前准备、会中按需辅助、会后分离事实/决议/承诺 | Meeting AI 记录并让相关 AI 员工接受责任 | 确认决议和外部承诺 |
| 17:00 | 运行结果是否正常，是否出现异常？ | 先定界影响、来源、置信度，再按影响打扰 CEO | Insight 找模式；Workspace AI 提交证据或执行可逆止损 | 扩大、修正、暂停、回滚或继续验证 |
| 18:00 | 现在要改变什么？ | 形成 Decision Runtime，写清生效、责任、检查点和回滚 | 把批准动作派回业务、Workspace 或能力配置 | 最终批准/拒绝/延后高影响变化 |
| 18:30 | 今天结束后，明天从哪里继续？ | Closeout：变化、决定、未解决、学习、明日优先级 | 保留责任、状态和下一检查点 | 确认明日承接 |

由此得到 `CEO Operating Day`：它不是日历，也不是 Dashboard，而是一个持久化的日经营运行对象，承接 Assistant 的汇报、事项、交接、决策、异常、证据和收束。

## 22. 处理“并非所有 CEO 需求都是目标”的反思

此前的业务推导强调 Outcome，这是保证经营闭环的必要条件，但如果把它机械地用于 CEO 的每一条请求，就会把真实助理变成流程审查员。CEO 可能只想让 Assistant 草拟一封邮件、整理一次谈话、查一个事实、准备一个会面，这些请求没有必要强行生成 Business Bet。

因此必须建立请求分类，而不是建立第二个任务系统：

1. **Assistive / Ad hoc**：一次性辅助，Assistant 直接处理或给出草稿。
2. **Operating**：会改变公司、业务、能力、责任或 Workspace，进入正式 Runtime。
3. **Decision**：需要 CEO 判断，Assistant 准备 Decision Packet。
4. **Coordination**：需要召集专业 AI 或追踪交接，Assistant 负责编排。
5. **External Commitment**：会对外承诺结果，必须经过 CEO 授权和证据标准确认。

这个分流解决了两个相反的问题：不把小事流程化，也不让会改变公司的事停留在聊天里。

## 23. 从“会出现”推导 Assistant 的真实行为

Assistant 的出现不是固定侧栏，而是三种触发的组合：

- **节律触发**：早报、会前、周期检查点、日末收束。
- **事件触发**：风险、异常、承诺到期、外部结果变化、能力过载、机会信号。
- **请求触发**：CEO 直接表达需要，Assistant 先分类再决定是否委派。

每次主动出现都必须回答四件事：为什么现在、依据什么、影响多大、CEO 最小需要做什么。证据不足、事项已有人负责、重复提醒、超出当前关注窗口或没有可行动价值时，Assistant 应聚合、延后或静默，而不是制造噪声。

Assistant 可以自动执行的范围是可逆且授权明确的动作：收集事实、准备摘要、询问专业 AI、建立分析请求、草拟内容、设置检查点、在边界内止损。以下动作必须回到 CEO 决策：新增外部承诺、启动或扩大业务、改变责任或公司结构、重新分配高影响资源、发布不可逆结果、关闭业务。

## 24. 从角色契约推导 AI 团队协作

Assistant 不是所有专业工作的替代者，而是 CEO 与专业 AI 团队之间的 Chief of Staff：

~~~text
CEO 请求
→ Assistant 分类与最小澄清
→ 直接辅助 / Business Analysis / Business Engineering / Workspace AI / Insight / Meeting
→ 专业 AI 执行并提交证据
→ Assistant 回收、解释、排序和升级
→ CEO 决策
→ 批准动作派回相应责任主体
→ Assistant 追踪检查点和日末承接
~~~

这条链明确了上下游：Company OS 提供事实、状态、责任和决策治理；Workspace 提供业务执行和反馈；专业 AI 负责深度工作；CEO Assistant 把它们翻译成 CEO 能在一天中理解、决定和推动的连续体验。

## 25. 从一天反推 UI，而不是从页面反推一天

CEO 第一次进入已在运行的公司时，默认进入 `CEO Desk / Operating Day`。第一屏必须先回答“现在是什么情况、什么需要我、AI 团队正在做什么”，而不是显示全部模块入口。

页面结构由信息责任推导：

1. **Brief Header**：日期、公司、Day State、Assistant 身份和最后同步时间。
2. **Assistant Brief**：自然语言汇报，展开可见来源、新鲜度、置信度、影响和建议动作。
3. **Matters**：Decision、Exception、Opportunity 三类卡片，每张显示为什么现在、谁负责、证据、最小动作和检查点。
4. **Operating Timeline**：当天的交接、会议、分析和 Workspace 检查点；不是复制日历。
5. **Company Pulse**：价值、执行、供给、风险、方向、连续性六个维度，并允许 Unknown、Stale、Conflict。
6. **Handoffs / Closeout**：显示 AI 团队正在承担什么，日末收束决定、学习和明日承接。

左侧仍保留紧凑的 CEO Desk、经营、业务、公司、工作空间导航；主区域全宽。Assistant 不占固定第三栏，而是以 CEO Desk 主内容、上下文抽屉和统一浮层出现。聊天只是表达方式，汇报、证据、决策和交接才是 UI 骨架。

## 26. 新的产品判断

补充 CEO Operating Experience 后，Curis 的产品真相不再只是“帮助 CEO 经营一家公司”，而是：

> Curis 让一位真实 CEO 拥有一位第一 AI 员工和一支可被召集、被授权、能提交证据并持续工作的 AI 团队；CEO 通过 Operating Day 感知公司，通过 Assistant 推动团队，通过 Company OS 和 Workspace 让决定变成业务结果。

因此 Blueprint 需要同时描述两个层面：Company OS 是经营内核，CEO Operating Experience 是 CEO 与这套内核及 AI 团队相处的日常入口。前者保证公司不会失控，后者保证 CEO 真正愿意、能够持续经营它。

## 27. 再次质疑：有一天剧本仍然不等于产品设计

新的反馈指出，前面的 Blueprint 依然停留在“应该有 CEO Desk、经营、业务、公司、Workspace”这样的结构描述，没有回答用户打开软件以后看到的真实画面、页面之间怎么走、每个按钮完成什么经营动作。

这说明还缺一层：不是模块 Blueprint，而是 CEO UI Blueprint。它必须从首次打开开始，描述每一个屏幕的目的、信息层级、交互、状态和出口。

## 28. 从首次打开反推产品壳层

第一天没有 Company、Business、Organization、Capacity 和 Workspace。此时如果出现空 Dashboard，CEO 不知道从哪里开始。因此首次体验不能使用经营阶段的壳层，必须是一个无侧栏的 Founding Flow：

```text
Welcome → Founding Brief → Company Design → First Business → AI Team & Capability → Launch Check → CEO Desk
```

当 Launch Check 通过后，才进入固定的 Desktop Shell：左侧 CEO Desk / 经营 / 业务 / 公司 / 工作空间，顶部公司与当前业务上下文，中间全宽主内容，Assistant 在 CEO Desk 主内容和按需上下文抽屉中出现。这样“创建公司”和“经营公司”是两个有明确状态差异的体验，而不是同一个 Dashboard 的空状态。

## 29. 从每个创建页面的经营输出反推交互

| 页面 | 不能只显示什么 | 必须产出什么 | CEO 的完成动作 |
| --- | --- | --- | --- |
| Welcome | 产品宣传和空入口 | 创建方式选择 | 从零创建或复用业务模式 |
| Founding Brief | 多个字段表单 | 意图、价值对象、第一阶段证明结果 | 接受 / 修改 Assistant 草案 |
| Company Design | 公司资料编辑 | Company 边界、使命、决策范围、约束 | 创建 Company |
| First Business | 业务名称和描述 | Outcome、外部结果、证据来源、周期 | 定义最小业务周期 |
| AI Team | 员工列表 | 责任、能力、容量、权限和缺口 | 接受或调整最小 AI 团队 |
| Launch Check | 绿色检查图标 | 正常 / 缺席 / 失败模拟、验收、回滚 | 批准启动或退回修改 |

所以每个“下一步”按钮都必须推进一个真实经营对象，而不是推进一个 UI 表单步骤。

## 30. 从运行阶段反推五个一级页面

进入经营阶段后，CEO 需要五个稳定视角，而不是十几个工具页面：

1. **CEO Desk / Operating Day**：今天发生了什么，什么需要我。
2. **经营**：公司是否健康，哪里需要干预。
3. **业务**：业务是否产生外部价值，是否继续投入。
4. **公司**：AI 团队是否有能力兑现承诺，哪里过载或缺口。
5. **工作空间**：具体业务如何执行，结果和证据如何形成。

Meeting、Decision、Evidence Review、Change 都是上下文模式：从事项进入，完成后回到原页面位置。这样导航表达 CEO 的经营问题，而不是表达技术对象。

## 31. 从屏幕骨架反推页面布局

统一壳层如下：

```text
┌ 左侧 224px ┐ ┌──────── 顶部上下文栏 ──────────────────────┐
│ CEO Desk   │ │ Company · Business / Workspace · Assistant │
│ 经营       │ ├───────────────────────────────────────────┤
│ 业务       │ │ 主叙事：状态 → 证据 → 动作                  │
│ 公司       │ │                                             │
│ 工作空间   │ │                        Assistant 按需抽屉  │
└────────────┘ └───────────────────────────────────────────┘
```

这个布局保留 CEO 的空间感和上下文连续性：左侧导航不变，主区域不被固定 Assistant 栏切窄，Assistant 在 CEO Desk 作为主内容，在其他页面作为上下文抽屉或事件卡出现。

## 32. 从 CEO 行动反推交互语言

CEO 不应该面对“创建 Task、运行 Workflow、打开 Agent”这样的技术动作，而应该看到：

```text
决定 · 调查 · 委派 · 召集 · 等待 · 静默 · 验证 · 扩大 · 暂停 · 回滚
```

每一张事项卡都必须显示“为什么现在、证据是什么、影响多大、谁负责、下一检查点”。点击事项后，Assistant 先解释，再让 CEO 选择动作；动作完成后生成交接或 Decision，并回到原页面锚点。

## 33. 从异常反推状态设计

真实产品不能只有正常态。首次创建要有 Empty；能力不足要有 Blocked；证据不足要有 Unknown；数据过期要有 Stale；来源冲突要有 Conflict；影响可控但需要注意要有 Attention。每种状态都必须给出原因、责任人、最小解法和下一检查点。

## 34. 新的收敛结果

本轮推导把 Curis 的产品形态收敛为两段体验：

```text
Founding Flow
→ 用 Assistant 把一句经营意图变成一家可启动的公司

CEO Operating Shell
→ 用 CEO Desk 作为每天入口，用经营 / 业务 / 公司 / Workspace 四个视角持续经营
```

这才回答了“产品到底长什么样”：它不是把 Company OS 的对象放到几张页面上，而是让每个页面承担一个 CEO 问题，让每个交互产生一个经营结果，让所有上下文模式都回到 CEO 的一天。

## 35. 新问题一：CEO Assistant 真的只是体验，还是公司对象？

如果 Assistant 只存在于 CEO Desk 和抽屉中，它就没有自己的责任、能力、质量和生命周期，也无法回答“它是否在工作”“它是否需要升级”“它能否被重新分配”。这与一位真实 CEO 助理的性质不符。

因此把 Assistant 提升为 Company Runtime 的独立对象：每个 Company 在当前阶段只有一个 CEO Assistant，它是 Company-level AI Employee，负责 CEO Operating Day 和跨业务协调。CEO Desk 只是它的主界面，不是它的存在本身。

对象关系被重新写成：

```text
Company
├── CEO
├── CEO Assistant
├── Professional AI Employees
└── Workspace AI
```

Assistant 必须像员工一样拥有角色契约、职责、输入输出、授权范围、能力绑定、升级规则、质量证据、运行记录和版本历史。否则它仍然只是一个漂亮的按钮。

## 36. 从“上下文”推导 Assistant Runtime 生命周期

CEO 助理不会在创建后立即假装理解公司。它需要经过明确的生命周期：

```text
Created
→ Configured
→ Learning Context
→ Operating
→ Evaluating
→ Upgraded / Reassigned
```

- **Created**：Company 建立时生成对象。
- **Configured**：CEO 确认服务范围、汇报节律、权限和升级边界。
- **Learning Context**：Assistant 整理 Company Charter、CEO 偏好、有效决议、业务状态和日常记忆，所有关键假设由 CEO 接受或拒绝。
- **Operating**：开始汇报、分流、协调、准备、跟进和授权内执行。
- **Evaluating**：根据准确性、遗漏、误报、交接完成率、采纳率和成本评估。
- **Upgraded / Reassigned**：变更角色、能力、版本或责任时保留旧版本证据，并重新验证。

这里的 Learning Context 不是不可控的模型训练，而是可查看、可拒绝、可回滚的 Company Context 版本。

## 37. 新问题二：AI 员工之间到底谁向谁汇报？

一人公司不需要复制几十层组织，但也不能把所有 AI 做成平级列表。平级列表会把协调责任重新推回 CEO；过度层级又会让 Assistant 变成审批瓶颈。

最终采用“治理、协调、专业结果、业务执行”四层关系：

```text
CEO
↓ 最终治理与重大决策
CEO Assistant
↓ 运营协调与注意力排序
Professional AI Employees
↓ 专业结果与能力负责
Workspace AI
↓ 具体 Workspace 阶段执行与证据
```

这不是人类组织的职位等级，而是授权与责任图：

- Assistant 对 CEO 汇报，接受 CEO 授权和纠偏。
- Professional AI 对 Assistant 汇报运行状态，但对自己的专业 Outcome 负责。
- Workspace AI 对所属 Professional AI / Workspace Owner 汇报。
- Workspace AI 遇到跨业务、高影响、越权或无法恢复的问题，逐级升级到 Assistant，再到 CEO。
- 专业 AI 可以在授权范围内自主工作，不需要 Assistant 介入每个领域判断。

这样 CEO 只管理第一层经营关系，Assistant 管理跨专业协调，专业 AI 管理深度工作，Workspace AI 管理具体执行。

## 38. 新问题三：Workspace 为什么是 Curis 的最大差异？

如果 Workspace 只是一个已经建好的运行空间，Curis 与普通工作台的差异会缩小。真正的差异在于：Curis 能否把一个陌生业务从理解变成一套可运行、可模拟、可交付的 AI 工作空间。

因此新增 `Workspace Studio`，并把它与 Runtime 严格分开：

```text
Studio：装修、组装、模拟、审批、版本升级
Runtime：执行 Cycle、提交证据、验收、反馈、复盘
```

## 39. 从 Business Engineering 推导 Workspace Studio

Business Engineering 的完整工作不再是“创建 Workspace”，而是：

1. **Discover**：理解业务、目标客户、外部结果、周期、约束和失败方式。
2. **Blueprint**：把业务拆成 Stage、输入、输出、岗位、证据和验收关系。
3. **Compose**：从 Agent、Capability、Tool、Knowledge、External System 中组装结构。
4. **Bind**：绑定具体能力、数据源、权限、容量、外部授权和人工备用路径。
5. **Staff**：安排 Professional AI 和 Workspace AI 到岗位，定义汇报和升级。
6. **Simulate**：运行正常、Agent 缺席、工具失败、结果延迟、证据冲突、CEO 拒绝等场景。
7. **Approve**：生成影响图、版本差异、回滚方式，由 CEO 批准。
8. **Operate**：创建 Runtime 版本，运行 Cycle，并根据反馈产生下一版 Draft。

## 40. “拖入 Agent”为什么不能只是自由画布

拖拽是视觉操作，不是产品逻辑。一个 Agent 被拖入 Workspace 后，系统必须继续询问：

- 它承担哪个 Stage 和 Role Slot？
- 输入和输出是什么？
- 它需要哪些 Capability、Tool、Knowledge 和 External System？
- 当前 Capacity 是否足够？
- 谁验收它的结果？
- 失败、缺席、超时和证据冲突如何处理？
- 它向谁汇报，什么情况升级？

因此 Studio Canvas 的每个节点都不是装饰卡片，而是一个带有 Owner、Input、Output、Evidence、Acceptance、Escalation 和 Failure Exit 的 Runtime 结构节点。

## 41. 新的收敛结果

这一轮之后，Curis 的产品差异不再只来自“有一个 CEO Desk”，而来自三件事同时成立：

```text
CEO Assistant Runtime
→ 让 CEO 真正拥有第一位 AI 员工

AI Organization Graph
→ 让专业 AI 与 Workspace AI 形成可授权、可汇报、可升级的团队

Workspace Studio
→ 让 Business Engineering 能把新业务装修成可运行、可模拟、可交付的空间
```

Blueprint 由 4.2 更新为 4.3，产品从“CEO 可以使用的经营系统”进一步成为“CEO 可以建设、指挥和升级的 AI 公司”。
