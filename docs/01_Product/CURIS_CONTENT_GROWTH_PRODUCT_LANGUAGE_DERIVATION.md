# P1. 完整产品概念模型（用户语言词汇表）

## 1.1 十二个用户概念（全部用白话命名，不用系统术语）

| 概念 | 用户语言 | 一句话定义 | 来自 |
|---|---|---|---|
| Business | 生意 | 我经营的一门真实生意（如"烘焙工作室内容获客"） | BL V2 |
| Platform | 平台 | 生意在哪个平台上经营（抖音/小红书/…） | PC-113 |
| Account | 账号 | 平台上的一个长期经营单元，有身份、历史、粉丝、资格 | 消息 10 修正 |
| Goal | 赚钱方式 | 这个账号靠什么创造价值（带货/商单/任务/直播…） | PC-096 |
| Strategy | 打法 | 怎么经营的计划，有版本，改了要留痕 | PC-003 |
| Stage | 阶段 | 账号处在起号/成长/变现/成熟的哪一步，锚定平台资格节点 | M12 |
| Qualification | 资格 | 平台允许这个账号赚哪些钱、每样还差什么 | M11 |
| Opportunity | 机会 | 平台上出现的具体赚钱机会（任务/商品/商单/团购/活动） | PC-099 |
| Work | 工作包 | AI 团队为一次生产/执行干的活（选题→内容→发布） | BL V2 |
| Result | 结果 | 发布回执、数据反馈 | PC-052 |
| Revenue | 收益 | 真实的钱及其结算状态 | M18 |
| Learning | 经验 | 复盘得出的结论，改变下一轮打法 | PC-080 |

辅助概念：**Cycle（周期）**=规划→生产→发布→反馈→复盘的滚动节奏；**Team（分工）**=哪个员工对这个账号/机会负责；**Needs You（需要你）**=必须 CEO 亲自完成的平台动作。

## 1.2 概念关系（一段话说清）

```
公司
└─ 生意（Content Growth）
   ├─ 平台档案（抖音：规则/资格/变现渠道/自动化覆盖）
   └─ 账号 A（抖音·熙熙壤壤）
      ├─ 赚钱方式 + 打法 + 阶段 + 资格地图
      ├─ 机会（进来的每一单赚钱机会）
      ├─ 工作包（AI 团队的工作）→ 结果（回执/数据）
      ├─ 收益（结算状态机）→ 经验（复盘）
      └─ 分工（员工 A 负责、员工 B 协作）
   └─ 账号 B（抖音·旧号）…
```

关键定位（继承基线，不新造）：**Account 不是 Workspace**——Workspace 是 AI 团队的工作空间，Account 是被经营的对象；Account 挂在 Business 之下，通过 Business Usage Binding 可服务多个 Business。**Platform 不是容器而是事实档案**——账号才是经营单元。

## 1.3 概念间切换规则（产品原则）

1. **一个能力一个正式归属地，多处可进**（ONE CAPABILITY OWNER—MULTIPLE CONTEXTUAL ENTRY POINTS）：例如"收益"的正式家在账号面的收益区，但业务首屏的收益数字、机会卡的预估收益、通知里的到账提醒都链接到它。
2. **上下文链自带**：从机会进入生产，自动带上"哪个账号"；从收益明细回溯，自动带上"哪个机会→哪个工作包"。用户不需要重新选择。
3. **上钻下钻**：业务（聚合）→ 平台（对比）→ 账号（单体）→ 对象（机会/工作/收益明细），任何一层都能下钻和返回，面包屑常在。
4. **外部动作一律交接卡**：凡是要去抖音 App/官网做的事，产品语言统一为"交给你的平台动作"，不伪装成站内功能。

# P2. CEO 进入 Content Growth：第一屏回答十个问题（业务首屏）

## 2.1 表达方案比较

| 方案 | 适合 | 优点 | 缺点 | 多账号规模 |
|---|---|---|---|---|
| A 仪表盘（卡片墙） | 数据概览 | 一眼全览 | 堆砌、无主次、回答不了"该干嘛" | 差——卡片越堆越多 |
| B 时间线（Feed） | 追进展 | 有叙事感 | 重要的事被时间冲走，CEO 要翻 | 差 |

| **D Hybrid（推荐）** | — | 简报定调 + 固定分区兜底 | 需要克制 | 好 |

**推荐 D：经营简报 + 固定分区**。首屏从上到下：
1. **经营简报**（AI 生成三句白话）："本周生意正常。最大的一件事：旧号首单佣金 ¥86 已到账。有 2 件事需要你：新号直播资格已达成待开播确认；星图入驻材料待提交。"
2. **需要你**（Needs You 队列，0~N 条）：每条=平台动作交接卡（见 P5）。没有则显示"没有需要你的事"。
3. **账号行**（每个账号一行状态条）：健康徽章（正常/异常/待处理）+ 阶段 + 本周净增 + 收益状态色 + 正在做什么（一句话）。点击→进账号面。
4. **机会区**：当前进行中机会 + 新发现机会（按适配排序，最多 5 条）+ "去机会库"。
5. **收益条**：已到账 / 可提现 / 在途（结算中）/ 应计 四个数字 + 到账日历入口。
6. **团队正在做**：运行中的 Work（哪个员工、做什么、进度一句话）。
7. **下一步**：本周期剩余计划（AI 团队的下一批动作）。

# P4. Opportunity 成为正式经营能力

## 4.1 Opportunity 统一状态机（无论从哪进来）

```
发现 Discovered → 评估 Fit → 决定 Decided（参与/不参与/收藏）
→ 干活 In Work（选题→生产→审核）→ 交接 Platform Action（报名/挂车/投稿）
→ 已发布 Published → 等结果 Awaiting Result → 有收益 Revenue → 关闭 Closed（+经验）
```
任何来源进来都先落"发现"，走同一条路；来源只作为属性（Intake Channel + 证据 + 抓取时间）。

## 4.2 Intake 五通道的进入体验（逐一具体）

| 通道 | 用户动作 | 产品行为 | 状态 |
|---|---|---|---|
| 截图识别 | 把任务卡截图拖进 Curis（对话/机会库/全局） | 识别字段（任务名/类目/结算方式/收益上限——L1 已证字段规整）→ 出确认卡 → 确认后入机会库 | 可用（识别准确度依赖模型，确认步兜底） |
| 分享/链接 | 从抖音分享商品/任务，粘贴给 Curis | 解析链接 → 能取则取 → 确认卡入库 | 可用（部分链接开放性 UNKNOWN，失败自动降级为手填） |
| 快速手填 | 点"记个机会" | 四字段迷你表单：名称/链接/预期收益/截止 | 可用（兜底，永远可用） |
| 深链/二维码 | 机会卡上"在抖音打开" | 打开 App 对应位置（扫码或系统深链） | 可用（导航） |
| 自动获取 | — | Web 星图任务大厅/活动中心定期获取；数据导出导入 | CANDIDATE（FUTURE Connector） |

## 4.3 机会库列表方案比较

| 方案 | 优点 | 缺点 | 判定 |
|---|---|---|---|
| List（按截止+适配排序） | 扫一眼知道先做什么 | 大量时需筛选 | **推荐默认** |
| Kanban（按状态拖动） | 流程感 | 机会不是任务，状态推进由经营决定非拖拽 | 不推荐 |
| Calendar（按截止） | 截止密度直观 | 看不到适配 | 辅助视图 |
| 卡片墙 | 视觉丰富 | 信息密度低 | 不推荐 |

机会卡内容（白话）：名称/平台/类型（任务/商品/商单/团购）/预期收益/截止/适配结论一句（"和账号定位匹配，但需要真人探店"）/状态。点击→机会详情：**Fit 对照卡**（要求什么 vs 账号有什么 vs 差什么）+ 决定按钮（参与/不参与/收藏+理由）。参与→自动创建工作包（带账号上下文），进入生产链。

# P5. Human-in-the-loop：平台动作交接卡（核心复用模式）

## 5.1 统一模式（一套组件复用所有场景）

**交接卡 = 为什么（上下文一句）+ 做什么（App 步骤清单，精确可跟）+ 入口（深链/二维码/复制字段）+ 回执（贴链接/传截图/点"已完成"）+ 超时提醒策略。**

状态流：`AI 就绪 → 等待你 → 你完成+回执 → AI 继续（回收数据/进入下一步）`。

## 5.2 复用场景表

| 场景 | 步骤清单要点 | 回执方式 | AI 交接后做什么 |
|---|---|---|---|
| 授权连接 | 打开创作者中心→扫码 | 系统检测连接成功 | 拉初始数据建档案 |
| 任务报名 | 打开任务→立即参与 | 截图/确认 | 开始该机会的生产 |
| 投稿发布 | 复制标题/话题/文案→上传→发布 | 贴视频链接 | 登记回执，进入数据观察期 |
| 挂车/选品 | 打开选品→搜商品→加橱窗 | 确认 | 记录商品与佣金率 |
| 保证金缴纳 | 电商带货→缴纳 ¥500 | 确认（金额入成本） | 更新资格地图 |
| 提现 | 收入页→去提现 | 确认 | 状态机：已提现 |
| 申诉 | 违规通知→申诉入口 | 确认/截图 | 记录事件，观察账号状态 |
| 直播 | 开播前清单（标题/商品排期/话术） | 播后确认 | 拉直播数据，复盘 |

## 5.3 表达位置与归属

- **正式归属**：全局"需要你"队列（跨账号/跨工作统一，因为 CEO 的注意力是全局的）。
- **投影**：业务首屏"需要你"区（当前业务 scope）、账号面"需要你"、工作包内的步骤位、通知中心。
- 方案比较：只做内嵌（找不齐）✗；只做全局列表（脱离上下文）✗；**owner=全局队列+处处投影（推荐）**。
- 到期策略：有截止的（任务报名/活动）按截止前提醒；无截止的（提现）按周提醒；可在卡上"稍后"（不得静默吞掉）。

# P6. Qualification：让普通人看懂"我能怎么赚钱"

三问三答的落位：
1. **"我现在能通过这个账号做什么赚钱？"** → 资格地图首屏：每个变现方式一行，三态：`✅ 可用（点击→Curis 已准备的用法）`、`🔶 差一点（差多少+怎么补）`、`⬜ 不可用（远期，折叠）`。
2. **"下一种还差什么？"** → 每个🔶行展开：差距白话（"有效粉丝 304/500，还差 196"）+ 差距来源（数据实测）+ **补法**（Curis 正在做什么：如"互动唤醒计划：回访老粉内容每周 2 条"）+ 预计时间。
3. **"达到以后 Curis 准备怎么经营？"** → 每个资格行挂"达成后动作"（预置计划）：达到 500 有效粉 → 自动提议"挂车开通包"（步骤清单+首批选品建议+3 条带货选题）。

规则表达纪律：门槛数字永远带 **Rule Version + Last Verified**（详情展开处显示，如"2025-02 新规：按有效粉丝计"，首屏不打扰）；平台改规则 → 受影响资格行标记"规则已变化，待复确认"，不得静默更新数字。

方案比较：进度条列表（推荐，扫读快）／卡片墙（密度低）／里程碑地图（好看但难维护）——**推荐列表行+展开详情**。

# P7. Revenue：真实经营结果的表达

## 7.1 账号收益汇总（四数字+一句话）

`已到账 ¥86 · 可提现 ¥0 · 在途 ¥214（3 笔结算中）· 应计 ¥50`；下方一句白话："下一笔 ¥120 预计 9 月 28 日到账（确认收货+15 天）。"

## 7.2 结算漏斗（每笔钱的旅程，逐笔可见）

每笔收益一行：来源（机会/商品/任务）→ 状态（应计/待结算/可提现/已提现/已到账/被扣减）→ 金额 → 预计日期。状态白话：应计="已经赚到还没落袋"；待结算="平台走流程"；扣减="售后退回了 ¥12"。

## 7.3 追溯链（点任何金额）

`金额 → 订单/任务/商单 → 机会（哪次机会）→ 工作包（哪条内容）→ 打法版本（当时策略）`。反向也成立：内容→它带来的收益。归因假设诚实标注（一内容多单=按平台订单归因；跨内容归因 CANDIDATE）。

## 7.4 成本与利润

成本登记三类（保证金/DOU+ 上热门/制作相关）+ 与收益对齐出 **Profit** 与 **ROI**；到账日历（未来 45 天预计到账流水）回答"钱什么时候来"。

方案比较：纯表格（准确但冷）／时间线（直观）／**汇总卡+漏斗+明细追溯（推荐）**——汇总答"多少"，漏斗答"在哪一步"，追溯答"为什么"。

# P8. 多 Platform / 多 Account：Context 模型

原则：**一套产品，多处投影**（ONE TRUTH—MULTIPLE CONTEXTUAL PROJECTIONS）。不复制日历/数据/机会/收益/对话——同一能力按所选范围（业务→平台→账号）投影。

- **Context Selector**（全局，Navigation+现场面包屑双表达）：业务 > 平台 > 账号。切换后：首屏、机会库、收益、日历、对话全部随范围变化。
- **聚合规则**：业务级=跨账号聚合+账号对比；平台级=同平台对比；账号级=单体。跨账号对比是一等视图（不是跳出到另一个页面，而是范围上钻一层）。
- **对话跟随 Context**：在账号 A 面发起的对话默认绑定账号 A；换 Context 时对话提示"这条对话属于账号 A，要切换话题吗"。
- 方案比较：Context Selector（推荐）／每账号独立工作区（重复产品，10 账号=10 套，✗）／树形导航承载一切（Navigation 变成文件管理器，✗）——**推荐 Context Selector+升降钻**；10 账号规模下成立（列表+分组+筛选，PC-027 在此规模升 OPERATING）。

# P9. Employee / Leader / Conversation 进入经营

1. **随处可问负责人**：账号面/机会卡/收益明细/工作包旁都有"问负责人"→ 右侧 Context pane 打开对话，自动带上对象上下文（不用用户解释背景）。CEO 问"这个机会要不要接"，员工看到的是同一张 Fit 对照卡。
2. **对话头显示经营上下文**：`烘焙工作室 > 抖音·熙熙壤壤 > 机会：欣活任务`。切换话题=换 context，产品提示确认。
3. **责任身份表达**：同一员工在不同生意任不同职；对话与产出标注"以什么责任身份"（经营责任分配模型的产品化）。
4. **Leader 的位置**：账号面"和负责人聊经营"=找 Leader；周期复盘由 Leader 主持（复盘报告+调整建议+CEO 确认）。
5. **Composer**：基础合同不变（Text/Context/Reference/Attachment/Send+状态）；扩展=可把机会卡/收益行/数据图作为 Reference 附进对话。

# P15. Four-Pane 兼容性检查（对照 Frozen Structure Baseline）

基线定义：App 空间由 **Navigation / Context / Main / Utility** 四种职责组成；默认 Navigation+Main，Context/Utility 按需出现；CEO Assistant 是全局浮动、不占四 Pane；Conversation Sidebar 是全局 Quick Access；Navigation 承载七区+对象导航/搜索+utility。

## 15.1 逐区判定

| 区 | 经营模型的要求 | 判定 |
|---|---|---|
| Navigation（左，可折叠） | 承载七区；业务空间下要有 生意→平台→账号 的对象导航与"需要你"入口 | **兼容**。基线明确 Navigation 含 Company object navigation/search；账号树属于对象导航，不违反七区结构 |
| Main（主区） | 业务首屏/账号面/机会库/收益/工作现场，随 Context 投影 | **兼容**。全部是业务空间（七区之一）内的现场，无新一级区 |
| Right Context pane（按需） | 现场经营对话（问负责人）、对象详情卡、交接卡展开 | **兼容**。正是基线"Context 按需出现"的用途 |
| Utility（按需） | 通知/待处理（"需要你"提醒）、搜索、设置 | **兼容**。基线把通知/待处理列为全局 utility |
| CEO Assistant（全局浮动） | 跨区协助、消费当前 context、把意图转给团队 | **兼容但需定义边界**（见冲突 2） |

## 15.2 冲突与张力点（诚实指出，供 CEO 判断）

1. **导航双入口主从未定义（张力，非冲突）**：账号/对象既会在 Navigation 树出现，又会在 Main 的 Context Selector/面包屑出现。建议后续冻结：Navigation=结构级导航（业务→账号清单+需要你），面包屑=现场位置；两处同源同状态。
2. **CEO Assistant vs Right pane 对话的边界（必须定义）**：两者都是对话。建议：Right pane=对象现场的负责人对话（scoped、持久属于该对象）；Assistant=全局跨区、转译意图、找负责人；同一话题不得两处分裂（Assistant 可把话题移交 Right pane 并留痕）。基线已隐含此分工（Assistant"把专业责任交给合法 Leader"），需在实现期明确。
3. **CEO 工作台（一级区 1）与业务首屏简报的重复风险**：同一数据两层简报。建议：CEO 工作台=跨业务聚合+公司级例外；业务首屏=单业务现场。同一 Truth 两投影，不得两套计算。
4. **"需要你"队列不占一级区**：符合基线（全局能力不占第八区）；入口=通知/待处理 utility+各现场投影。无冲突，但需防止被实现成隐藏功能——业务首屏第一位呈现。
5. **交接卡的外部跳转**：四 Pane Shell 无法承载抖音 App 操作——这不是结构缺陷而是 Human-in-the-loop 的本质；深链/二维码模式与 Shell 兼容。
6. **Mobile-only 数据的呈现**：截图识别、手工回填在 Shell 内完成（拖拽/表单/确认卡），无冲突。

**结论：Frozen Four-Pane 能够完整承载 Human-in-the-loop 经营模型，无结构性冲突；有 2 个定义点（导航主从、Assistant/现场对话边界）+1 个投影关系（两层简报）需要在实现前冻结。**

# P17. 仍然存在的产品问题（诚实清单）

1. 截图识别准确度未证——确认卡兜底，但字段错认的纠错体验需设计验证。
2. 数据手工/导出回填的长期摩擦：导出文件格式 UNKNOWN，导入自动化 FUTURE；手工档的"提醒节奏"需拿捏（过频=骚扰）。
3. 收益→内容归因：一内容多订单可归因，多内容共推一商品归因假设未定（CANDIDATE）。
4. 一个账号双 Goal（带货+商单并行）时资格地图与简报的表达未定稿。
5. 10+ 账号时 Navigation 账号树的层级深度与分组交互（滚动/折叠）未定。
6. 机会去重/过期/同质合并规则未定（同一商品多次发现）。
7. Browser 档位（Web 数据自动采集）的平台风控边界 UNKNOWN，影响数据档位承诺。
8. 直播实时环节完全人工，直播中 CEO 在 App 里——Curis 的"直播中支持"形态（第二设备看板？）未定，本轮不展开。
