## 1. 一句话讲清楚整条推导

> 一开始想的是「把已有页面补完整」，最后收敛成「让 CEO 的一句话长成一家能自己产生结果的 AI 公司」。
> 中间**推翻了 13 个旧假设**，产品的定义单位从「页面」→「模块」→「生命周期」→「承诺」→「一天」→「一间办公室」，一路往「更像真实经营」的方向走。

整个推导只守一条规则：

```text
真实经营场景 → CEO 要做的动作 → 公司职责 → 业务运行 → 对象和状态 → 页面 → Blueprint
```

而**不是**：

```text
已有页面 → 补模块 → 补字段 → 补 API
```

这条规则是第一天定下的，后面每一次推翻都是因为「又不小心退回到页面思维了」。

## 2. 白话版推导全程（16 幕）

### 第 0 幕 · 起点：不要先写 Blueprint

**当时的诱惑**：已经有 Blueprint 了，有页面、模块、Runtime、导航，看起来只要写得更完整就能开工。

**捅破的问题**：这些东西回答不了最基本的几件事——CEO 为什么需要 Curis？公司第一天什么都没有时，软件该干什么？如果把 Project、Task、Meeting 全删掉，公司还能不能经营？

**结论**：Blueprint 不是目标，是经营理解的沉淀。先理解，再写。

---

### 第 1 幕 · 从 CEO 的五个问题，到四个入口

CEO 每天反复问五件事：公司现在怎样？业务赚不赚？能力够不够？活干得顺不顺？共识和知识在哪？

**第一反应**（错的）：做五个中心页面——状态中心、业务中心、能力中心、员工中心、知识中心。

**为什么错**：五层不是五个模块，是 CEO 的五种**视角**。硬做成五个中心，会导致经营状态和业务结果被切开、能力和承诺连不上、知识退化成资料仓库、员工页面又变回任务管理——CEO 还是得自己在页面之间拼公司状态。

**收敛结果**：四个一级入口 + 一个跨切层。

| 入口 | CEO 问题 |
| --- | --- |
| 经营 | 现在发生了什么，什么需要我处理？ |
| 业务 | 我们为谁创造价值，值不值得继续？ |
| 公司 | 公司有没有能力兑现已经答应的事？ |
| 工作空间 | 活怎么干，结果有没有在形成？ |

第五层（事实 / 决议 / 学习）**不做导航**，做贯穿所有页面的真相层。知识中心被取消，就是这一步的结果。

---

### 第 2 幕 · 从零创建公司：组织是长出来的，不是先建好的

**第一反应**（错的）：Company → Department → Employee → Capability → Business → Project → Task，一路建下去。

**为什么错**：这是软件的配置顺序，不是公司的形成顺序。真实 CEO 第一天不会先画组织架构图。

**收敛结果**：

```text
CEO 意图 → 公司理解 → 第一个业务方向 → 第一个结果
→ 最小责任 → 最小能力与资源 → Cycle 或 Workspace → 第一个真实结果
```

**部门什么时候才出现？** 不是第一天。要等到「同一类责任反复出现 + 需要稳定协作 + 多个业务共享同一能力 + 需要独立容量和权限」这些事实都成立了，部门才成立。而且部门不是「名字 + 负责人 + 成员」的 CRUD，它必须有结果、责任、能力、容量、权限、依赖、服务承诺和退出条件。

一句话：**组织从结果缺口里长出来。**

---

### 第 3 幕 · 最关键的一次翻转：从「任务」到「承诺」

**触发问题**：CEO 同时接了两个业务，资源不够时，他真正想知道什么？

不是「哪些任务延期了」，而是：**我答应了谁什么？哪些承诺会受影响？哪些必须保住？哪些可以重新谈？**

**收敛结果**：公司不是任务集合，是**承诺网络**。三层对象：

```text
Promise / Obligation   对外或对组织的结果承诺
Commitment             某个责任主体接下的交付责任
Task                   为完成责任采取的内部动作
```

链路是：外部承诺 → 内部责任承诺 → Work Package → Task → Evidence → 外部验收。

**由此得出一条铁律**：**任务做完 ≠ 承诺完成。** 没有验收或真实反馈，经营目标不能自动关闭。

这一幕直接决定了 Project/Task 被降级——它们从「产品中心」变成「Workspace 内部的执行记录」。

---

### 第 4 幕 · 结果必须来自外部世界

**一开始的误解**：「外部结果」= 必须有付费客户，必须接 CRM。

**澄清后**：外部结果的关键不是有没有客户，而是——**结果来自 Curis 自己伪造不了的真实世界**。客户验收、平台数据、用户行为、收入交易、CEO 手动确认，都算。

两条证据入口都是**正式**的：

| 来源 | 例子 | 怎么处理 |
| --- | --- | --- |
| API / 外部系统 | 抖音播放点赞下单、GitHub 构建发布 | 读原始事实，记来源/时间/新鲜度，再解释成业务证据 |
| CEO 手动录入 | 没 API 授权时录入平台指标、人工验收软件 | 记录录入人、时间窗口、来源链接/截图、可信度 |

手动录入不是临时凑合，是**正式证据通道**。

**分工也定了**：Curis 拥有经营事实、承诺、决策和解释；GitHub / CI / 抖音这些外部系统保有它们产生的原始事实。Curis 不复制外部平台。

---

### 第 5 幕 · 能力 ≠ 容量

**问题**：公司有内容创作能力，是不是就能再接一单？

不一定——AI 并发满了、CEO 注意力不够、预算没了、数据权限没开、发布窗口撞车、共享能力被别的业务占了。

**收敛结果**：

```text
Capability = 能不能做
Capacity   = 现在还能做多少
Allocation = 现在给谁在用
```

CEO 要新增业务前，系统必须先模拟：会占用哪些能力、消耗多少容量、影响哪些已有承诺、有哪些缩小/延后/转移/拒绝的备选方案。

**所以资源不是一个设置页面，是承诺兑现能力的约束条件。**

---

### 第 6 幕 · AI 从「聊天角色」升级为「责任主体」

**一开始的想法**：AI 是聊天助手 / 任务执行器 / 工作流节点 / 内容生成工具。

**推翻理由**：要真正经营一人公司，AI 必须能接受责任、执行工作、产生证据、推动业务、发现风险、在边界处升级、被持续评价和调整。

**AI 员工契约**（每个都必须写清楚）：结果、业务范围、数据范围、能力、动作权限、质量标准、成本和延迟边界、证据要求、升级条件、失败与备用方案。

**AI 绝不能静默做的六件事**：改公司意图 / 改战略重点 / 对外新增承诺 / 改资源优先级 / 改责任归属 / 把没有证据的结果标成完成。

生命周期：候选 → 测试 → 批准 → 试运行 → 正式运行 → 降级 → 暂停 → 退休。

---

### 第 7 幕 · 失败路径不能最后再补

**推翻的做法**：先设计「创建 → 运行 → 成功 → 扩展」，失败以后再说。

**为什么不行**：真实公司天天遇到客户拒绝、AI 失败、能力降级、资源冲突、证据过期、判断错误、CEO 缺席、业务必须关停。

**四类失败**（CEO 要分清楚）：价值失败（假设不成立）、交付失败（范围周期质量错）、供给失败（人/AI/能力/权限失效）、判断失败（事实证据不可靠）。

**必须存在的真实状态**：On Track / Attention / At Risk / Blocked / **Unknown** / **Stale** / **Conflict** / Resolved / Verified。

三条硬规则：
- 没有证据 **不能**自动显示为正常（绿色）
- 证据冲突 **不能**被平均掉
- 过期决策 **必须**重新验证

**业务退出**分 Pause / Reduce / Transfer / Close / Merge / Split，各不相同。退出前要保护未完成承诺、交接责任、释放资源、保存历史、沉淀学习——**不能用 Delete 抹掉经营事实**。

---

### 第 8 幕 · 复杂度渐进激活

**问题**：要支持从零到规模化，是不是第一天就把企业级功能全摆出来？

**不行**——第一天就给完整部门、权限、报表、工作流、知识库，CEO 就从「开始经营」掉进了「配置软件」。

**六个成熟度阶段**，由真实经营事实触发：

| 阶段 | 触发事实 | 才激活 |
| --- | --- | --- |
| 创始 | 只有 CEO 意图 | Founding Brief、最小公司方案 |
| 首次价值 | 开始面对真实世界 | 外部结果、验收、反馈 |
| 可重复运行 | 同类工作重复、多 AI 协作 | Workspace、Cycle、责任合同 |
| 委派经营 | CEO 覆盖不过来 | AI 权限、升级、节奏、连续性 |
| 业务组合 | 多业务抢资源 | 组合、战略重点、投资与退出 |
| 重构扩展 | 反复异常、能力瓶颈 | 组织重构、共享服务、版本迁移 |

---

### 第 9 幕 · 4.0 → 4.1：CEO 助理是第一位 AI 员工

**新的质疑**：公司、业务、能力、Workspace 都有了，这是个合理的经营内核——**但 CEO 打开它，会觉得「有一支团队在陪我工作」吗？**

不会。他还是得自己从各模块拼状态、自己召集 AI、自己记未完成的事。

**这个问题不能靠加一个「Assistant 页面」解决。** 现实里的 CEO 助理不是按钮，也不是聊天侧栏，而是最靠近 CEO 的角色：主动汇报、判断什么该打扰、提前准备、协调他人、追踪承诺、把一天连起来。

**收敛结果**：CEO Assistant 从「全局入口」升级为 **Company Runtime 里真实存在的第一位 AI 员工**（Chief of Staff）。Global Assistant Runtime 只是它的基础设施，不是它的产品定位。

同时确定了**验证单位从「模块」改成「CEO 的一天」**——`CEO Operating Day`，一个持久化的日经营对象，从 Preparing 到 Closed，未完成的责任承接到明天。

**还有一条重要的克制**：不是 CEO 的每个需求都要变成 Outcome。请求先分五类——辅助/临时、经营、决策、协调、外部承诺。小事保持轻量，只有会改变公司状态的才进正式 Runtime。**既不把小事流程化，也不让大事停留在聊天里。**

### 第 10 幕 · 4.1 → 4.2：从一天反推 UI，而不是从页面反推一天

**又一次质疑**：有了「CEO 的一天」剧本，还是没回答**用户打开后到底看到什么**。没有屏幕级定义，设计师会重新猜首页，开发会重新决定导航。

**收敛结果**：两段体验，状态明确分开。

```text
Founding Flow（无侧栏）
Welcome → Founding Brief → Company Design → First Business → AI Team & Capability → Launch Check

CEO Operating Shell（固定壳层）
左侧 CEO Desk / 经营 / 业务 / 公司 / 工作空间 · 顶部上下文栏 · 中间全宽主内容 · Assistant 按需抽屉
```

关键判断：
- **创建公司和经营公司是两种体验**，不是同一个 Dashboard 的空状态。
- **每个「下一步」按钮必须推进一个真实经营对象**，不是推进一个表单步骤。
- **Assistant 不占固定第三栏**——CEO Desk 是它的主界面，其他页面它以抽屉和事件卡出现。
- **聊天只是输入方式**；汇报、证据、决策、交接才是 UI 骨架。
- Meeting / Decision / Evidence Review / Change 都是**上下文模式**，不是新导航；完成后回到原位置并留下痕迹。

CEO 的动作词也定了：**决定 · 调查 · 委派 · 召集 · 等待 · 静默 · 验证 · 扩大 · 暂停 · 回滚**——而不是「创建 Task、运行 Workflow、打开 Agent」。

### 第 11 幕 · 4.2 → 4.3：Assistant Runtime、AI 组织图、Workspace Studio

三个新质疑同时出现：

**质疑一：Assistant 只是体验，还是公司对象？**
如果它只活在 CEO Desk 和抽屉里，就没有责任、能力、质量和生命周期，也回答不了「它是否在工作、要不要升级、能不能重新分配」。
→ 升级为独立对象，生命周期：`Created → Configured → Learning Context → Operating → Evaluating → Upgraded/Reassigned`。
→ Learning Context **不是**模型偷偷训练，而是可查看、可拒绝、可回滚的 Company Context 版本。

**质疑二：AI 员工之间谁向谁汇报？**
平级列表会把协调责任推回 CEO；层级太多又让 Assistant 变审批瓶颈。
→ 四层**授权与责任图**（不是人事职级）：

```text
CEO              最终治理与重大决策
└── CEO Assistant        运营协调与注意力排序
    └── Professional AI  专业结果与能力负责
        └── Workspace AI Workspace 阶段执行与证据
```

专业 AI 在授权内自主工作，不需要 Assistant 介入每个领域判断；跨业务、高影响、越权的问题逐级升级。

**质疑三：Workspace 凭什么是 Curis 的最大差异？**
如果 Workspace 只是「已经建好的运行空间」，Curis 和普通工作台就没差别了。真正的差异是：**能不能把一个陌生业务，从理解变成一套可运行、可模拟、可交付的 AI 工作空间。**
→ 新增 `Workspace Studio`，与 Runtime 严格分开：

```text
Studio ：Discover → Blueprint → Compose → Bind → Staff → Simulate → Approve → Operate
Runtime：执行 Cycle → 提交证据 → 验收 → 反馈 → 复盘
```

**「拖入一个 Agent」为什么不能只是自由画布**：拖拽是视觉操作，不是产品逻辑。Agent 被拖进来后系统必须继续追问——它负责哪个 Stage？输入输出是什么？需要哪些能力和权限？容量够吗？谁验收？失败超时怎么办？向谁升级？
→ 所以 Canvas 的每个节点都是带 Owner / Input / Output / Evidence / Acceptance / Escalation / Failure Exit 的**结构节点**，不是装饰卡片。

**还有一条**：运行中的 Workspace **不被 Studio 草稿静默改变**，新版本必须走差异、模拟、回滚和采用复盘。

### 第 12 幕 · 中文界面规则（07-31）

Company / Workspace / Outcome / Evidence 这些英文可以做内部对象名和开发标识，但**真实 CEO 看到的导航、按钮、状态、提示、表单、错误信息和 Assistant 回复，必须统一简体中文**。英文只能在中文后面加括号注释。

这不是翻译偏好，是**用户边界**：Curis 的第一个真实用户是中文 CEO，界面语言不能留给实现阶段猜。

### 第 13 幕 · 4.3 → 4.4：First Arrival —— 空白但不空旷【补记】

> 以下三幕是本次补记的内容，来源为 ADR-0042/0043/0044 与 08-01～08-02 变更日志，尚未回写进正式推导记录。

**新的质疑**：Blueprint 4.3 已经有完整的创建流程和经营页面了，但 CEO **第一眼**看到的还是一个「流程入口」。他感受不到公司空间，感受不到 Assistant 在陪着他，感受不到 AI 员工存在。

**核心判断**：第一印象决定 CEO 愿不愿意留下来。**产品需要先像一家正在形成的 AI 公司，再像一套经营软件。**

**收敛结果**：`First Arrival / Company Space Seed`。CEO 进入的不是空 Dashboard，也不是注册表单或功能导览，而是**一间尚未布置完成、但已经有人在等他的 CEO 办公室**——空间是空的，Assistant 在场，下一步清楚，未来的公司结构已有轮廓。

三条气质原则：

| 原则 | 含义 |
| --- | --- |
| **空白但不空旷** | 没业务时不摆假数据、不摆空列表；保留公司空间、Assistant 位置、创建提示和第一步行动。空白代表「尚未建立」，不是「什么都没有」 |
| **介绍而不是教学** | Assistant 先介绍自己能替 CEO 做什么，再用一两个问题让 CEO 表达意图。是一次真实对话，不是功能 tour |
| **有温度但不游戏化** | 靠语气、头像、工作状态、渐进出现建立陪伴感；二维办公室表达组织关系，但不用游戏化装饰替代经营语义 |

空间是**沿着真实经营对象长出来的**：

```text
经营意图 → Company 牌匾 → CEO 办公室 → Business 版图
→ Department Office / Workspace → AI Team → 第一个可运行业务周期
```

**第一眼验收标准**（写死了）：10 秒知道这是什么，30 秒知道 Assistant 是谁，2 分钟完成第一句经营意图，离开引导前看到自己的公司空间正在形成。

参考了 StaffDeck 首屏（欢迎语 + 角色身份 + 能力概览 + 建议问题 + 自然输入同时出现），但 Curis 必须把它转化成「创建公司的第一步」，而不是产品介绍页。

→ 对应 **ADR-0044**，Blueprint 升 **4.4**，UI Blueprint 升 v1.2。

---

### 第 14 幕 · 视觉语言与主题：Calm Executive【补记】

**问题**：页面把事实、观点、决议、承诺、状态分别做成彩色容器，结果是视觉噪音 + 后台操作台感。

**判断**：Curis 服务的是需要**阅读、判断、决策**的 CEO，不是需要操作大量控件的后台管理员。

**收敛结果**：全局视觉语言冻结为 **Calm Executive Workspace（安静的 CEO 工作空间）**

```text
内容与经营语义优先 → 中性纯色表面 → 单一主强调色
→ 低对比边界 → 对话流与上下文抽屉 → 结构化结果在需要时才出现
```

明确不采用：多彩 Dashboard、控制台式卡片堆叠、渐变霓虹。Workspace 可以改布局，但不能绕过中性表面、克制颜色、内容优先和可访问性。

新页面评审必须回答三个问题：**主叙事是什么？唯一的主要行动是什么？哪些颜色是 CEO 必须关注的？**

**主题只有三种**：系统（默认）/ 浅色 / 深色。三者共用同一套布局、组件、间距、字体、交互和语义色，**主题只切换表面、文字、边界和对比度，不改变结构和经营语义**。

- 深色用 Codex 风格深灰 `#1a1c1f`，**不用纯黑**（降低对比刺点，保留层次）
- 深色主按钮用品牌绿 `#32f08c`——让 CEO 一眼认出「现在可以执行的动作」
- 浅色主按钮用深色 `#30333a`——保持克制，避免白界面被绿色大面积占据
- 蓝色只保留给「决策 / 信息」语义，**不再当全局主按钮色**
- 禁止旧版主题 token、页面私有色板、主题专属组件语法

→ 对应 **ADR-0042 + ADR-0043**。

### 第 15 幕 · 中文用语与壳层统一（08-02）【补记】

**问题一：用词太「投融资 / 后台管理」。** 业务页和创建流程里出现「投资组合、下注、赌注、ROI、KPI、工作流」这类词。

**判断**：第一位用户是**没有受过产品培训**的一人公司 CEO。要先让他看懂公司在做什么，再让他理解内部运行逻辑。**赌博隐喻和技术缩写会抬高第一次使用的理解成本。**

→ 界面统一改成日常中文：**业务版图、业务方向、投入产出、工作指标、流程、真实结果、反馈**。并新增「内部英文概念 → 中文界面标签」的映射规则。

> 注意：这条对本文件也有效——所以前面第 2 幕我写的是「第一个业务方向」而不是原文的「业务赌注」。**内部推导可以用 Business Bet，用户界面不能。**

**问题二：壳层每页不一样。** 侧栏宽度、品牌标识、对齐方式、顶部栏高度（52/62 两套）都不统一，Assistant 在工作空间被降级成侧栏卡片。

**判断**：CEO 需要在不同经营场景里保持**同一个空间方向感**。侧栏不能像每页临时拼的后台菜单，首席助理也不能被降级成一张卡片。

→ 统一 `220px` 侧栏 + Curis 品牌标识 + 左对齐导航 + `52px` 顶部栏；分组为「公司 / 经营工具 / 办公室 / 公司资源」；AI 团队作为组织入口；**Assistant 只用全局浮层**。

## 5. 推导记录的缺口与维护规则

### 5.1 当前缺口

| 缺口 | 影响 | 建议 |
| --- | --- | --- |
| 4.3 → 4.4 未回写推导记录 | 「为什么要做 First Arrival」只存在 ADR 里，新人读 Journal 会以为产品停在 4.3 | 把本文件第 13–15 幕合入 Journal（新增 §42–44）与 Reasoning Record（新增 §20–22） |
| 两份文档仍是 `Status: Review` | 蓝图已 4.4，推导记录版本对不上 | 回写后统一标注「对应 Blueprint 4.4」 |
| 视觉/主题/用语类推导无固定归档位 | 只能靠 ADR + CHANGE_LOG 拼 | 在 Reasoning Record 增设「体验与视觉推导」章节 |

### 5.2 建议的维护规则

1. **每次 Blueprint 主版本变化（x.y → x.y+1），必须同步回写推导记录**——Journal 记过程，Reasoning Record 记结论。ADR 记「决定了什么」，但**回答不了「为什么会想到这里」**，两者不能互相替代。
2. **推导记录只记判断，不记实现**。页面改了几个像素不进推导记录；「为什么不能用彩色卡片」要进。
3. **被推翻的假设必须留档**。第 3 节那张表是整份推导里信息密度最高的部分——它防止后人重新踩同一个坑。
4. **写推导记录时用内部术语（Business Bet / Outcome / Evidence）没问题，但写界面文案时必须切换成日常中文**。这两套词汇不能混。

## 6. 最后一句话

这份推导最有价值的地方不是「最终得到了什么结构」，而是**它每次都在同一个地方翻车、又每次都爬回来**：

> 一不留神就退回到「加一个页面 / 加一个模块 / 加一个角色」，
> 然后被同一个问题拦下来——**这解决了 CEO 的哪个真实经营问题？**

从 4.0 到 4.4，产品的定义单位换了六次：页面 → 模块 → 生命周期 → 承诺 → 一天 → 一间办公室。方向始终一致：**越来越像一家真实的公司，越来越不像一套软件。**

而 ADR-0041 给这条路加了一把锁：**页面做出来不算完成，业务跑通才算。** 这也是为什么现在 10 个模块的 Business Runtime 蓝图没定义完，开发就不能开工。
