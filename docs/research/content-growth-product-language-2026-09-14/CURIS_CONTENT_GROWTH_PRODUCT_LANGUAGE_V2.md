## 2. 新的产品边界

| 责任 | Curis必须承担 | 平台/Provider承担 |
|---|---|---|
| 经营 | Business Goal、方向、责任、计划、持续判断 | 不拥有Curis Business或员工 |
| 生产 | 研究、策划、文案、视觉、视频、审核；能力不足诚实暴露 | 可提供规格/制作工具，但不替代Curis责任 |
| 平台规格 | 判断来源/适用地区/账号/时效，生成正确版本 | 平台官方规则；Provider能力metadata只是其中一源 |
| 发布 | 发布员工校验版本/账号/授权、调用、核对和处理等待 | 真实平台操作、限制、审核、外部回执 |
| 分析 | 区分事实与解释，回答业务问题，形成Learning及调整建议 | 返回可获得的数据，不定义经营判断 |
| 用户参与 | 解释原因、准备材料、请求必要动作、追踪恢复 | 原生登录/MFA、身份/钱包、商品绑定、申诉等 |

**产品链**：CEO目标→Leader组织研究与策略→计划/选题→内容意图→平台形态+账号语境→账号版本生产→审核→发布员工→可用Provider/必要用户动作→逐账号回执→可信数据→分析员工→Learning→授权内下一周期。

这不是用户要配置的流程图，不要求每条内容经过十个不同员工。职责可兼任；实际责任由现有Assignment解析。用户当前授权采用AiToEarn候选定位，但R7的C/D结论没有被升级成所有平台可执行。Platform Metadata≠当前账号权限≠Curis已接通能力。

## 3. Content Growth 核心产品模型

### 3.1 用户只需要理解的词

| 用户语言 | 内部对应 | 分界 |
|---|---|---|
| 内容经营业务 | Business | 用户启用的一项业务，不是Curis默认种下的业务 |
| 工作空间 | Workspace | 团队工作的合法载体；账号不是空间 |
| 平台/账号 | Channel / Channel Account | 账号是长期经营对象；连接变化不换历史身份 |
| 经营目标 | Goal / Success Contract | 品牌、线索、收入等，不能缩成赚钱方式 |
| 当前打法 | Strategy及授权内计划方法 | 改定位/受众等仍需相应CEO决定 |
| 本轮计划 | bounded Cycle / Plan | 周期结束不代表责任停止 |
| 内容/选题 | Intent / Topic | 讲什么、为什么、为谁的目标做 |
| 账号版本 | per-Account Variant | 同平台两账号也可完全不同；定稿为版本状态 |
| 发布记录 | Publication | 一账号一次外部发布；可以仅部分成功 |
| 结果/依据 | Result / Evidence | 生产成品、回执、数据和分析结论分型，不混成“全部完成” |
| 需要你处理 | 既有Attention/P7/Handoff的投影 | 不是另建全局Work队列 |
| 学到了什么 | scoped Learning / Review结论 | 带依据/适用范围；建议未接受不算已应用 |

### 3.2 对象关系与经营视角分开

Canonical保持：Company→Department→Business→Workspace；Employee通过Responsibility/Assignment工作。Account是Company资产，经合法绑定服务Workspace。Business→Platform→Account是**经营观察与规划视角**，不是新增canonical父子链或第五种执行scope。[A1–A8]

推荐首个经营空间可服务多个账号；是否多个Workspace由真实独立目标/团队边界决定，不按平台名或账号数量自动创建。Business层统筹其Workspace集合，不能把所有Workspace团队强行并成一个团队。用户可直接打开账号的经营投影；系统仍保留实际承载Workspace和合法责任。

Content Intent可以共享；每个目标账号有自己的Variant；FULL_DIVERGENCE仍可属于同一Intent，不因完全重产就强制新建内容意图。真正目的/核心信息改变时才另建Intent并引用来源。Publication逐账号唯一事实，跨账号“2已发1待确认”只是摘要，不发明一个覆盖全部账号的发布真源。[A7]

**跨业务共享账号不是首版默认捷径。** 已有合法绑定可以有多个经营上下文；打开时明确本次业务/空间，不能合并不同业务的策略、内容或对话。没有匹配绑定则先补合法关联，不能用昵称猜。

## 4. Business Level

### 4.1 第一眼的信息顺序

采用三层信息，不固定三张卡或三列：

1. **经营摘要**：本轮重点、最新有依据的判断、下一步。数据不足就说“尚不能判断效果”，不自动“经营正常”。
2. **需要CEO的事项（有才出现）**：只呈现真实决定/人工动作，按影响与截止排序；不把每条员工进度变通知。
3. **值得注意的账号及工作入口**：账号名称/平台、本轮重点、当前工作或阻塞、目标相关结果一句话。可进入全部账号、当前内容计划和团队工作。

本周计划、团队进度、最近结果融入相关账号与当前工作，避免七块常驻。业务目标为获客时不强制收益条；没有机会输入不摆空机会库；没有可信数据不画零值趋势。

### 4.2 用户操作与后果

| 用户意图 | 点击/输入 | 进入/改变什么 |
|---|---|---|
| 看某账号怎么了 | 账号行/异常摘要 | 当前合法Workspace内账号经营投影，保留返回业务位置 |
| 问整体该怎么做 | 与Leader讨论 | Main的Leader工作对话，携带Business范围 |
| 看团队做到了哪 | 当前工作摘要 | 指向原Workspace/Work，不复制全业务执行列表 |
| 处理手机确认 | 需要你事项 | 同一发布Work的交接详情，回到原事项 |
| 深看效果 | 查看分析 | scoped经营洞察；周期/账号作为分析上下文，不新报表库 |
| 新账号交给团队 | 添加/经营账号 | 识别已有账号和绑定，再形成提案；不自动新建Workspace |

Business聚合不能用一条“健康分”掩盖数据未知。例：“A账号本轮内容已发，效果数据待补；B账号有一条需手机确认；团队继续准备下期内容。”这是**文案示例，不是当前真实业务结果**。

多个Workspace时业务面保留其目录与责任入口；单个Workspace可直接进入上次账号工作现场，但清楚“返回业务”，不抹除Business身份。CEO工作台只汇聚跨业务注意力和决定，业务首屏提供单业务解释；同一事项处理一次、各处同步投影。

## 5. Platform Level

用户要知道“Curis在这个账号当前能替我做哪些事”，默认不是看平台百科。

| 时刻 | 最小表达 | 按需详情 |
|---|---|---|
| 选择账号/发布目标 | 发布、数据、评论三项实际覆盖 | 条件/限制/来源/更新时间 |
| 生产前 | 所选形式与当前有效规格 | 标题/正文/图片/视频/封面/标签/分类/隐私等适用项 |
| 动作受阻 | 原因+下一步 | 打开连接、必要浏览器/手机操作、官方入口 |
| 规则变化 | 哪些未发版本需复核 | 变化证据与适用地区/账号类型，不擅改已审核内容 |

面向用户推荐四种**动作说明**，不是新的Runtime枚举：

- **可由员工执行**：已接通、已验证、当前账号有权且条件满足。
- **需要你确认**：材料已就绪，某一步需用户完成。
- **需连接浏览器后继续**：确需本地会话，说明打开哪个已有连接入口。
- **当前不能代办**：可准备内容、去平台完成；能力未知写“尚未验证”，不等同永久不支持。

“自动化程度”不能覆盖全部动作：同账号可以发布需确认、数据仅能提供文件、评论不可自动。只有用户需要处理连接或查看执行来源时显示AiToEarn/浏览器插件名字。API/MCP/Relay不放首屏；不隐瞒外部服务、费用或数据去向，但按需说明。

规格采用有效平台规则与Provider实际限制的交集；冲突或过期时先核实，不能把Provider最大值冒充平台官方上限。规格更新影响准备中/待发版本，已发布事实保持。前端不预写固定粉丝门槛、最佳发布时间或平台永久能力。[R7、A7]

## 6. Account Operating Experience

### 6.1 账号首屏

**账号是谁、现在为什么经营它、团队接下来做什么**必须在Main独立可见。推荐：账号身份/平台+当前经营目标摘要→本轮重点和最近判断→需要你事项（有才显示）→当前内容计划/工作。当前责任可从相邻员工入口查看，不常驻完整组织树。

| 信息 | 默认可见程度 | 理由 |
|---|---|---|
| Goal/当前打法摘要 | 简短可见 | 用户要知道正在为什么努力 |
| 阶段 | 仅影响本轮方法时出现 | “验证内容方向”比固定粉丝等级有用；阶段为判断，非自动资格证明 |
| 经营/连接/数据状态 | 分开在相应位置表达 | 断连不等于封禁；暂无数据不等于无增长 |
| 计划/近期工作/发布 | 当前相关几项+查看全部 | 连续经营现场，避免任务历史堆屏 |
| 团队与责任 | 当前行动者可见；完整责任按需 | 可直接找员工，不强制单一Account负责人 |
| 数据/收益 | 与目标相关、有来源的结果摘要 | 无来源时留缺口，不强塞全指标 |
| Learning/下一步 | 最近有影响的结论与动作 | 历史经验通过“为什么这样做”进入 |
| 完整策略/历史/连接配置 | 按需进入 | 不做8个常驻Tab |

### 6.2 关键操作

- “调整目标”：形成对同一Goal/Success Contract的明确变更；用户已清楚指定的合法更改不二次审批，歧义自然追问；AI建议触及保护边界才进P7。
- “暂停经营”：暂停该合法责任/计划范围内尚未执行的工作，保留账号/成品/回执；已提交平台操作不能保证撤销。恢复先对账，再续原工作。
- “查看这次发布”：打开账号对应记录、定稿和实际回执；不跳到无关Provider工作区。
- “与发布员工讨论”：在Main定位原Work和该账号版本，Utility可并看回执。
- “账号连接失效”：保留全部历史与目标；只让受影响动作等待，不给整个业务标失败。

账号不默认绑定单一Employee：Leader负责整体取舍；研究/生产/发布/分析由已有责任持有人承担。缺岗显示“这项责任尚无人承担”，不是创建一名“发布Agent”填空。

## 7. Content / Variant Experience

### 7.1 一个选题怎样展开

CEO看“这条内容为哪个目标服务”，再看“准备给哪些账号”。账号版本列表每行只答：账号/形式、准备到哪、谁负责、当前需不需要我、最新结果。标题、素材差异和高级平台选项打开该版本再看，不在列表逐项平铺。

例：同一内容意图“解释产品如何减少重复操作”可产生抖音口播视频、小红书图文、B站演示视频、YouTube适配视频。每个版本同时受平台形式和具体账号定位/受众/语气约束；同平台官方号与创始人账号不能共享整套私有背景。只是同一场景示例，不承诺相应执行能力现已开放。

### 7.2 语言与动作

| 阶段 | 用户理解 | 操作后果 |
|---|---|---|
| Intent/Topic | 这条想讲什么、为什么值得做 | 与策划讨论，引用目标/来源；不展示推理过程 |
| Brief | 做成什么、有哪些要求 | 修改要求进入原Work，不另建平台内容任务系统 |
| Variant生产 | 正在为这个账号制作 | 看负责员工、已产生版本、缺少素材/能力 |
| Review | 这版是否可以按指定条件发布 | 批准绑定版本+目标账号+必要发布条件；不是永久批准此内容所有未来版本 |
| Final | 这是准备发布的定稿 | 新改动形成新版本并复核受影响批准，不覆盖旧回执 |
| Publish | 此账号发布到哪一步 | 看独立发布状态，必要时交接 |
| Result | 已发出去/结果待核对/数据待补 | 打开成品与平台回执，不等同经营成功 |

**后加账号**创建该账号版本并重新校验；**移除未执行目标**留痕且需符合分发策略；不能把已发布事实一起删掉。**完全重做**仍可为同Intent的FULL_DIVERGENCE，修正R2§5“完全不同即不是Variant”的过度约束。**翻新旧内容**保留来源与旧Publication，既有帖子内容不被改写成新版本。[A7]

Common Content+Settings+Overrides是Provider输入组织，Curis用户不需要学这三个词。Curis保持“同一意图—每账号版本”，发布员工把已审核版本转换为具体接口参数；Provider不能在发送时静默替换内容和目标。

素材/模板从现有Result/Artifact/资料库引用；业务入口可按内容用途筛选，但不在每个账号复制素材库。复制策略/模板不复制凭据、发布记录、对话或他号数据。

## 8. Publishing Experience

### 8.1 Curis发布员工负责什么

发布员工对“用正确版本发到正确账号，并取得可信回执或明确等待”负责：校验定稿和政策→核查目标身份/连接/能力→准备上传和平台字段→按允许路径提交→查询原记录→处理人工交接或失败→回传结果。AiToEarn是执行来源，员工身份始终是Curis同一Employee。

用户看到“发布员工正在提交A账号版本”，展开“执行详情”才看到服务来源；若员工并未实际运行、接口未接通，必须显示“尚不能提交/等待连接”，不以品牌文案掩盖事实。

### 8.2 简单但不失真的状态语言

| 用户表达 | 含义/可做什么 |
|---|---|
| 待审核 | 版本未满足批准条件；查看版本/审核 |
| 已准备，计划于…发布 | 尚未执行；时间是意图，不代表平台已排期 |
| 正在提交 | 已运行；可查看真实进展，不能另发一份 |
| 等你在手机确认 | 同一发布的人工动作；去完成/稍后 |
| 已提交，平台处理中 | 不是已公开；员工继续核对 |
| 已发布 | 当前已确认的账号回执；隐私/审核/链接缺口另提示 |
| 发布结果待核对 | 远端可能已接受；先核对，禁止显式“重试发布”诱导重复 |
| 未发布，需处理 | 已知失败；允许动作由原因和原记录决定 |
| 已发布，效果数据待补 | 发送完成，经营判断暂不能做；不重发内容 |

以上是现有状态和外部事实的用户投影，不新冻结Runtime枚举。私密作品和仅获得操作ID不自动出现“查看公开作品”。停止员工、取消排程、撤回手机交接和删除已发帖子不是同一动作；不许用一个“取消”承诺全部可撤销。

### 8.3 部分成功和恢复

一条内容显示“2个账号已发布，1个等待确认”，每账号可进入。已发不回滚；尚未执行项是否继续服从现有Distribution Execution Policy，而不是默认遇错全部继续。对已发布账号不给整组重发；缺数据只补数据；超时先查原operation/record。换Provider不是安全重试的捷径，必须先确认原路径未造成发布。[A7、R7]

## 9. Analytics Experience

### 9.1 五层表达

Platform Data是来源事实；Evidence保存可追溯依据；Analytics Employee解释这些依据；Business Interpretation回答目标是否推进；Learning说明下次改变什么。**来源数据、AI解释和已接受决定不能用同一个状态徽章。**

默认呈现三句话的内容结构：有依据的观察→目前能/不能判断什么→建议下一步。数值后有“截至何时/覆盖哪些内容”简述；点击可看来源、口径、原值和缺口，不摆采集表管理面。

| 数据情况 | CEO看到 | 对分析的约束 |
|---|---|---|
| 真实0 | 0，并可查到有效来源/时点 | 按真实值分析；不因0默认失败 |
| 未采集 | 暂无数据，尚未获取本次表现 | 等待或提供文件；不算0 |
| 不支持 | 当前无法自动获取这项数据 | 可提供平台数据；不反复失败重试 |
| 连接失败 | 数据连接需要恢复，现有数据截至… | 旧数据可读，不填新0 |
| 过期 | 最近数据截至…，本轮判断可能不完整 | 明示时效，不当作当前表现 |
| 无法确认的0 | 返回值为0，但尚无法确认是否实际采集 | 不作为经营结论依据，需核对 |

Provider只给normalized0时，Curis不能推断出真0；已有历史值仍保留，不能自动覆盖。快照发布日期与采样时间不同；累计数只在同源同口径同对象且有效覆盖时比较/差分，重置或删帖导致下降不直接当负增长。[R7]

### 9.2 业务面与经营洞察的分工

业务/账号面显示目标相关的结果摘要和缺口；深度分析、跨账号比较、追问、报告进入既有经营洞察，并携带所选业务/空间/账号/周期。执行分析的Employee归于合法责任；Business Analyst与Company Analyst可合作，不在账号里另建分析系统。[A1–A3、A6]

读简报无需先打开聊天；想问“为什么”才进入分析员工的Main对话，报告留Utility参考。同一报告只有一个Result来源，账号面和洞察只是入口。样本不足说“还不能判断”，不是把不足变成行动建议的装饰脚注。

## 10. Human Handoff

Handoff是正常工作状态。最小内容只回答：**为什么需要你、做什么、去哪里、已准备什么、完成后Curis继续什么**。另给明确的确认依据和有效期（适用时），不复制平台全套操作教程。

示例文案：“A账号的这版视频已准备好。这次发布需要你在抖音手机端确认。打开本次发布入口，核对账号和内容后完成。回来后发布员工会核对作品链接，再进入数据观察。”这是产品文案候选，不声称手机预填已验收。

| 用户动作 | Curis行为 |
|---|---|
| 去平台完成 | 打开已验证目标；保留来源Work/账号/版本，跳转不等于完成 |
| 我已完成 | 登记用户报告→员工核对回执；无可核验来源则仍“待核对” |
| 提供链接/截图 | 作为证据，检查账号/内容/时点；不自动改为经营成功 |
| 稍后处理 | 同一事项延后提醒；不删除工作、不重新建发布 |
| 入口过期 | 检查原发布结果后再恢复该交接；不生成多个仍可执行的新副本 |
| 我不做了 | 明确取消/调整本次意图，保留已有外部事实；责任是否暂停另判 |

正式执行Owner是原Work/Handoff；CEO决定归P7；CEO工作台、通知、业务、账号、内容只是同一Attention的投影。同一连接失效阻塞多条工作，可汇成一项“恢复连接，影响N条发布”，但不合并各自回执。普通“打开主页”不创建待办，提现不默认周期性催办。

## 11. Opportunity / Monetization

### 11.1 机会是输入，不是必经流水线

保留三类真实来源：AI从已获准可访问来源发现；用户提供链接/截图/描述；外部Provider返回已核实对象。每项带来源、适用范围、时效与缺失信息；没有发现能力就显示未接入，不生成假机会Feed。

已有Frozen Content Opportunity是共享内容信号，不能被本轮静默改成账号私有商业订单。商业任务/商品/合作线索先作为既有外部对象/Reference及研究Work的输入；确有需要升级正式商业Opportunity模型时另审，不把统一状态机偷偷引入本稿。[A7]

入口默认“记下这个机会/让团队看看”。员工判断值得做后，可形成内容意图或经营提案；“准备方案”不等于“已经报名/接单”。正式参与、合同、商品/任务绑定仍服从外部权限和CEO决定。收藏不创建整个生产链，所有内容也不要求先有商业机会。

### 11.2 收益与真实价值

账号可以为品牌、线索、收入或多个目标服务；默认突出一个主要目标，次目标只在影响取舍时显示。收入结果要区分预估、平台确认、到账及有无归因证据；只呈现当前业务决策需要的层级。没有数据不能显示“收益0”，奖励上限不等于预期收入，押金占用不默认成本，到账不等于利润。[R6]

“经营有没有产生价值”可以由有效询盘、转化或经确认收益支撑；未接入销售后续时仅记录线索及去向，不新建CRM/订单后台。跨业务移交由既有Work/责任机制承担，成交未知就保留未知。

完全不进入Curis的执行界面：平台钱包、提现表单、实名/MFA、税务/认证材料后台、申诉系统、平台原生商品/商单管理后台。Curis可保留影响经营的事实、来源与必要处理入口；“不复制界面”不等于“忽略这些限制”。

## 12. Employee / Responsibility / Conversation

| 角色关系 | 产品表达 |
|---|---|
| Leader | 对该业务/空间经营责任负责，定本轮重点、分工、整合、异常与下一步；不只是路由器 |
| Publishing Employee | 同一Curis员工在本次账号/工作承担发布责任，Provider只说明执行来源 |
| Analytics Employee | 从可用Evidence形成解释和建议，不把Provider数据当自己的结论 |
| Account | 被经营对象；不会因此生成员工副本、永久聊天副本或新scope |
| Work | 本次实际责任与执行载体；可跨专业Surface，不随看板筛选变化 |
| Conversation | Main持续工作面，可从Leader/Work/版本进入；消息和引用保留当时合法范围 |

“问负责人”默认解析此对象对应责任，而不是总跳Business Leader：问发布找发布责任，问当前打法找该范围Leader；缺责任人就说缺口。点击姓名看身份详情在Utility；点击“讨论这项工作”打开Main Workstation，两个动作不混。

**同Employee换账号**：已有Conversation身份可以继续，新增消息明确本次账号和责任；历史不重写、不全量读取另一账号知识。用户只是浏览B账号时，A对话不会自动变B；要把讨论切到B，Composer明确显示目标改变并保留已输入内容及其原引用，必要时选择继续A/带入合法新话题。Shared允许多个topic，不强制每次换账号新建聊天。[A8§5]

CEO Assistant是全局同一浮动身份，可解释和引导；真正专业工作由合法Employee承担。Assistant引用或跳转到Main既有对话并保留回程，不复制专业聊天内容作为另一份真相，不把任务交给右栏。

授权内战术、内容节奏与计划调整可由Leader推进并留痕；改Goal/Success Contract/Positioning/Audience/商业模式/重大预算或高影响承诺需CEO。已明确的CEO合法指令不是再请求一次批准的理由。分析结论本身不自动改策略；Viewed不等于Accepted。[A6、R8]

## 14. Multi-account / Multi-platform Context

### 14.1 默认最少导航

## 17. Complexity Review

### 17.1 每类信息放在哪里

| 信息类别 | 常驻/按需/外部 | V2处理 |
|---|---|---|
| 目标/本轮重点/实际阻塞/下一步 | Main必要摘要 | 不藏到Context，否则关闭辅助Pane看不懂 |

| 钱包/提现/认证/申诉表单 | 平台外部 | Curis不复制、不常驻催办 |
| Provider协议/Relay/日志 | 默认隐藏，必要诊断按需 | 不成为普通用户工作语言 |

| 所有历史数据/版本 | 原对象/报告详情 | 默认只相关结果，不卡片墙 |
| 机会/收益 | 目标相关且有输入时出现 | 不要求每个账号经营必经商业任务链 |

### 17.2 删除的是过度表达，不是经营责任

删除常驻资格地图、机会专属强制状态机、钱包漏斗、固定45天到账日历、十几字段账号健康卡、全平台自动化评级、二十账号常驻泳道、右侧专业聊天、第二全局交接执行队列。保留其必要能力：资格影响、机会输入、收益证据、准确状态、规模导航、工作对话、人工交接。

复杂度检验的具体标准：默认无新增一级区；单账号无需经过平台详情才能工作；处理发布最多在原Work与外部平台间往返；看结果不要求打开聊天；问员工不会生成平行聊天记录；新账号不复制整套应用；数据未知不需用户理解工程枚举。

**自审结论：语义上已收敛为“看经营→进账号/内容→找员工或处理必要动作→看结果与下一步”。** 尚未做真实用户可用性测试，不能宣称已经最简或可用性通过。未来UI应围绕这条体验证明，而不是重新把127项摊开。

### 18.3 白话回答12个问题

1. **它最终是什么产品？** 由Curis员工持续负责方向、内容、执行协调和反馈的内容经营业务；不是平台后台合集。
2. **第一眼看到什么？** 这轮重点、最近有依据的判断、需要你做的事，以及值得关注的账号和下一步。
3. **账号怎样持续经营？** 保存该账号目标/打法/内容/反馈，在真实Workspace责任下按有限周期推进；换连接、换员工、结束一次周期都不抹历史。
4. **多平台怎样生产发布？** 共用内容意图，每个具体账号各做一版，分别审核、执行、取回执；未必同样自动化。
5. **AiToEarn什么角色？** 提供规格/能力参考和可用平台执行；用户必要时知道服务来源，经营与员工身份始终在Curis。
6. **发布员工做什么？** 核对账号、定稿、权限，调用可用通道，处理交接/失败，并确认真实回执。
7. **分析员工做什么？** 验证数据可用性、解释目标进展、形成有依据且有适用范围的Learning，与Leader调整下一轮。
8. **何时要CEO？** 目标/重大边界决定、明确政策要求的审核、平台真人动作、无法代理的资料/资格或未知结果核对。
9. **什么不该搬进来？** 平台钱包、提现、认证、申诉和商品/商单原生管理后台；只保留影响经营的事实与必要入口。
10. **够简单吗？** 结构和语言已减少重复；实际易用性仍需下一阶段用1/5/20账号和失败状态验证。
