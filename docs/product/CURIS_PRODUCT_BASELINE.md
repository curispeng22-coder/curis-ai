## 一、为什么建立这份文档

过去的产品讨论、V1/V2/V3、Gate、复盘、能力总账和局部实现文档越来越多，部分文档之间已经出现产品层级、用户流程和开发优先级冲突。

从现在开始：

- 本文只回答“Curis 到底是什么、用户怎么使用、系统应如何运行”；
- 《用户能力总账》只回答“目前真实做到什么程度”；
- 《当前交付目标》只回答“团队这一阶段正在交付什么”；
- 其他历史方案、Gate、复盘和旧版本文档全部作为参考资料，不再拥有产品定义权。

遇到冲突时，优先级如下：

```text
本文《产品唯一基线》
>
CEO 最新明确决策
>
《用户能力总账》
>
《当前交付目标》
>
技术契约、Gate、Issue
>
历史讨论与旧版本文档
```

## 二、产品定位

Curis 是面向一人公司的自动任务与工作流系统。

用户是 CEO。  
用户不需要管理每一个执行步骤，也不需要理解模型、Agent、Skill、Tool、API、CLI、数据库和 Gate。

用户只需要：

1. 进入自己的公司、部门和项目；
2. 与项目负责人沟通目标；
3. 确认负责人生成的计划；
4. 启动执行；
5. 查看进度、成果、成本和风险；
6. 只处理必须由 CEO 决定的事项；
7. 对结果批准、返工、暂停或调整目标。

产品最终价值：

> CEO 提出目标后，项目负责人能够自动规划、拆解、调度、执行、验收、返工并交付结果。

## 三、产品组织结构

固定组织层级：

```text
CEO（用户）
↓
公司（Company）
↓
部门（Department）
↓
项目（Project）
↓
项目负责人（Project Owner）
↓
员工与可调用能力
```

### 公司

代表用户经营的 AI 公司。

### 部门

代表一类稳定的业务能力，例如：

- AI 研发部；
- 内容增长部；
- 未来其他业务部门。

### 项目

项目位于部门之下，是长期运行和产生价值的实际载体。

例如：

```text
AI 研发部
├── Curis Workspace 项目
├── 内容增长能力开发项目
└── 连接器平台项目
```

```text
内容增长部
├── 小红书账号项目
├── 抖音账号项目
└── B站账号项目
```

项目持续保存：

- 项目目标；
- 当前计划；
- 当前状态；
- 关键决策；
- 任务与执行记录；
- 成果；
- 成本；
- 风险；
- 项目经验；
- 下一步行动。

### 项目负责人

每个项目只能有一个主要负责人。

CEO 主要与项目负责人沟通，不需要分别推动员工、Agent或席位。

项目负责人必须对最终结果负责，而不是只负责转发任务。

## 四、自动任务流是产品核心

完整主链路：

```text
CEO提出目标
↓
项目负责人澄清需求
↓
形成并冻结验收标准
↓
生成动态执行计划
↓
拆解任务
↓
选择最合适的执行能力
↓
自动执行与跟踪
↓
自动验收
↓
失败：重试 / 换能力 / 重新规划 / 返工
↓
成功：沉淀成果、成本和经验
↓
只在关键问题上请求CEO决策
↓
项目负责人统一汇报最终结果
```

必须支持三种执行方式：

### Agent 模式

适合研究、创意、开放问题、动态规划和不确定任务。

### Workflow 模式

适合稳定、重复、可审计、步骤明确的执行过程。

### 混合模式

项目负责人或强 Agent 负责规划，明确步骤再交给 Workflow、Tool或其他能力执行。

混合模式是默认方向。

## 五、员工与能力的定义

### 员工

员工不是一个固定模型，也不是一个永久聊天线程。

员工表示：

```text
岗位职责
+ 权限边界
+ 项目上下文
+ 记忆
+ 可调用能力池
```

同一个员工可以服务多个项目，但每个项目、每个任务必须使用独立 Session，避免上下文污染。

### 可调用能力

以下都属于项目负责人和员工可以调度的能力：

- 外部 Agent；
- Codex、WorkBuddy及其他专业 Agent；
- 模型；
- Skill；
- Tool；
- MCP；
- API；
- CLI；
- Connector；
- 已有 Workflow。

能力必须可替换，不得将业务流程写死到某个具体 Agent 或模型。

例如：

```text
首选能力不可用
→ 自动选择备用Agent
→ 或使用其他模型 + Skill + Tool完成
```

Agent、模型、Skill、Tool是能力层，不是用户产品主界面中的核心对象。

## 六、前端产品蓝图

前端不是装饰，而是产品入口、产品说明书和验收工具。

第一阶段可以不够漂亮，但必须真实可操作。

统一 Workspace 至少包含以下页面：

### 1. CEO办公室 / 公司首页

显示：

- 公司当前状态；
- 重点项目；
- 需要CEO处理的事项；
- 最近成果；
- 成本与风险摘要。

### 2. 部门中心

显示：

- 部门负责什么；
- 部门下有哪些项目；
- 当前运行状态；
- 部门负责人；
- 项目间资源情况。

### 3. 项目运行工作台（核心页面）

显示并支持：

- 项目目标；
- 项目负责人；
- 与项目负责人对话；
- AI生成的计划；
- 任务拆解；
- 当前执行状态；
- 正在使用的员工、Agent或能力；
- 待CEO决策；
- 成果；
- Token与成本；
- 批准、返工、暂停、调整目标。

### 4. 能力中心

用户可以通过前端管理：

- 模型；
- Agent；
- Skill；
- Tool；
- Connector；
- 凭证。

例如新增模型必须形成完整产品链路：

```text
填写名称、服务商、模型ID、地址和Key
→ 测试连接
→ 保存
→ Key进入凭证库
→ 模型显示可用状态
→ 可被项目负责人和员工选择
```

用户不得依赖终端、curl、环境变量或直接修改数据库完成正常配置。

### 5. 成果中心

统一查看：

- 代码与Git Diff；
- 测试结果；
- 文档；
- Demo；
- 网站；
- 图片；
- 视频；
- 数据报告；
- 发布包；
- 成本与负责人。

### 6. 设置

包括：

- 公司设置；
- 项目目录授权；
- 运行预算；
- 权限；
- 通知；
- 本地与外部能力连接。

## 七、产品功能完成标准

任何功能只有完成以下完整链路，才可以向 CEO 汇报“已完成”：

```text
页面有明确入口
+
用户能够真实操作
+
后端真实保存或执行
+
页面显示状态
+
结果可以查看
+
失败有明确提示和处理方式
```

只有 API、数据库、测试、CLI、Mock或设计文档时，只能标记为：

```text
后台能力已准备
```

不能标记为产品功能完成。

成熟度统一拆成两列：

### 技术成熟度

```text
设计中
→ 代码存在
→ API/CLI可用
→ 真实E2E
```

### 用户成熟度

```text
不可使用
→ 开发者可用
→ 创始人自用
→ 对外用户可用
```

## 八、开发方式

后续采用“前端产品动线牵引开发”。

流程：

```text
先确定页面和用户操作
→ 复用现有后端能力
→ 交互走到哪里发现缺口
→ 只补当前缺口
→ 回到页面继续验证
```

禁止：

- 先重构整个后台再做页面；
- 为未来可能使用的能力持续扩建设施；
- 因实现困难自行改变产品层级和用户流程；
- 一个小功能固定经过所有席位；
- 用测试数量、接口数量、文档数量和Gate数量代替用户结果；
- 新建多套独立前端；
- 在未得到CEO确认前修改本文产品基线。

每个纵向切片应由一个产品交付负责人对结果负责。

产品规划、架构、安全和QA按需参与，不得固定轮转。

## 九、Gate的正确范围

Gate只用于真正高风险事项：

- 凭据与隐私；
- 不可逆数据操作；
- 外部平台OAuth和真实授权；
- 生产部署；
- 商业收费；
- 跨租户权限；
- 大范围数据迁移。

以下普通产品工作不得反复进入Gate：

- 页面布局；
- 产品文案；
- 项目目标；
- 任务拆解；
- 结果展示；
- 模型选择；
- 一般CRUD；
- 普通前后端联调。

## 十、文档整理规则

仓库中只保留三份日常必读文件：

```text
docs/product/CURIS_PRODUCT_BASELINE.md
docs/status/USER_CAPABILITY_LEDGER.md
docs/delivery/CURRENT_DELIVERY_TARGET.md
```

### CURIS_PRODUCT_BASELINE.md

稳定文档。定义产品，不随每个Issue变化。

### USER_CAPABILITY_LEDGER.md

动态文档。记录当前真实能力，必须区分技术成熟度与用户成熟度。

### CURRENT_DELIVERY_TARGET.md

短期文档。只保留当前唯一交付目标、用户动线、验收标准、负责人和阻塞。

其他文件：

```text
docs/archive/
```

归档为历史资料，不作为当前产品或开发指令。

## 十一、产品变更规则

任何产品层级、用户动线或核心交互变更必须经过：

```text
提出变更
→ 说明用户价值和影响
→ CEO确认
→ 更新本文
→ 再进入开发
```

开发团队不能因为：

- 当前接口不方便；
- 前端难实现；
- 历史代码结构不同；
- 某个Agent能力不足；

自行修改产品定义。

## 十二、当前开发方向

现有后台基础设施已经较多，接下来重点是将能力组织成真实可操作的产品。

近期方向：

1. 统一 Workspace 产品壳；
2. 完成项目运行工作台；
3. 完成模型、Agent与凭证配置动线；
4. 接通项目负责人对话、计划确认、任务启动、状态展示、成果查看和返工；
5. 在交互过程中精准补齐后端缺口。

当前不优先：

- 新行业扩展；
- Marketplace；
- 商业计费；
- 大规模Skill/Tool扩充；
- 复杂3D办公室；
- 与核心用户动线无关的后台设施。

---

## 十三、团队汇报规范

团队每次只汇报：

1. 用户今天新增了什么可点击能力；
2. 从哪个页面进入；
3. 如何操作；
4. 后端真实执行了什么；
5. 用户最终看到了什么结果；
6. 当前仍有什么限制；
7. 下一步准备接通哪一段。

产品进度以用户动线为准，不再以Gate、Commit或测试数量为主。
