# Curis 产品架构原则：编排中枢 + 可插拔执行端（Federated Agent OS）

> 产品形态定调文档（design-only，零代码 / 零提交）。由总控于 2026-07-12 拍板立项，待产品规划席正式裁定后纳入产品基线。

## 0. 摘要（三段式）

**结论**：Curis 的本质不是"亲自做完所有事"的工具，而是**个人创业者的 AI 公司 OS / 编排中枢**。当某部门（如内容）的执行必须依赖第三方 agent（如 AiToEarn）时，把它注册为**执行抽象层下的可插拔 Connector**——用户只在 Curis 内操作，第三方仅在"绑定账号 / 执行叶节点"时短暂可见。

**原因**：我们不可能获得所有平台的授权独立做一键发布 / 分析 / 运营；未来其他业务部门同理——**工作流能跑通，但结果必须经第三方 agent 拿到**。这是平台级硬约束，不是 AiToEarn 个例，而是产品的常态。

**建议**：以"**编排中枢 + 可插拔执行端**"作为产品底层架构原则。第三方 agent 是流水线上的执行手，用户只认调度台。执行端的合法落地方式 = **OEM 商业授权** 或 **自托管其开源代码**（白标第三方 Relay 违反其 ToS）。

---

## 1. 产品本质

- **定位**：个人创业者的 AI 业务托管平台——一个人通过 AI 员工运营多个业务渠道，把分散的 AI 能力转化为持续生产力。
- **结构**：内容部门只是多部门之一（内容 / 销售 / 客服 / 运营 / 财务…），每个部门由 AI 员工驱动。
- **价值主张** = 广度（多部门覆盖）+ 编排（跨部门工作流联动）+ 持久化（统一记忆 / 品牌资产）。**价值不在单点能力，而在"一家公司被统一托管"。**

---

## 2. 硬约束：为什么必须引入第三方执行端

- **平台授权不对称**：抖音 / B站 / 国际平台有标准 OAuth API；小红书 / 微信视频号无开放发布 API（靠浏览器插件模拟）。
- **我们不可能为所有平台、所有业务拿到独立授权**。
- 因此：**工作流（编排 / 生成 / 调度）可由 Curis 完成，但叶节点执行（真实发布 / 互动 / 数据）往往要委托第三方 agent**。
- **泛化**：内容部门用 AiToEarn；未来销售 / 客服 / 其他业务可能也要接各自领域的第三方 agent。这不再是"接一个工具"，而是产品的标准执行模式。

---

## 3. 架构模式：执行抽象层（Execution Abstraction Layer）

四层结构：

| 层 | 职责 | 用户是否可见 |
|---|---|---|
| **用户层** | 只面对 Curis OS，发自然语言指令 | 唯一入口 |
| **Curis 中枢层** | 统一编排 + 跨部记忆 + 多部门 AI 员工 + 工作流引擎 | 完全可见 |
| **执行抽象层** | 统一接口（意图 → 选执行端 → 归一化结果），第三方注册为 Connector | 不可见 |
| **执行端层** | AiToEarn / Agent B / Agent C… 可插拔 | 仅绑定账号 / 叶节点时短暂可见 |

**接口契约**：每个执行端实现统一 Connector 接口——
- 输入：结构化意图 + 发布包（目标平台 / 账号 / 内容 payload / 媒体 / 排期）
- 输出：归一化结果回写 Curis 数据模型（发布状态 / 互动 / 数据）

**与既有设计一致**：workflow 的"执行步"绑定可替换 Connector；"发布包 schema"是两端契约。Phase 1 = 手动连接器（产出待发布包），Phase 2 = 接第三方 / 自建执行端，drop-in 替换，工作流不变。

---

## 4. 最小感知原则（Minimal Perception）

- 日常工作流完全在 Curis 内完成，用户不感知任何第三方。
- **仅两步必然短暂暴露第三方品牌（法律要求，不可避免）**：
  1. 绑定平台账号时的 OAuth 授权屏（屏显执行端 / 平台方身份）
  2. 执行叶节点偶尔的归属提示
- **最小感知 ≠ 隐藏**：账号绑定必须明示（ToS / 平台合规要求），不能用他人的 OAuth app 冒充自家品牌。

---

## 5. 付费点（Monetization Thesis）

**用户不为单点能力付费，为"公司 OS"付费：**

1. **AI 公司 OS 订阅**——多部门编排、AI 员工、跨部工作流
2. **统一记忆与品牌资产**——一份账号、一份品牌记忆、跨业务沉淀
3. **编排运行时**——调度、重试、多 agent 协调、跨部联动（真工程价值）
4. **统一账单与体验**——一个平台管全部业务，不用来回切 N 个 agent

> 执行端成本（如第三方 credits）作为 **COGS**，可吸收进订阅或按量附加；若需打包计费，须有 **OEM / 商业授权**（避免白标违规）。

---

## 6. 对比：租户用 Curis vs 直接用第三方 agent（以 AiToEarn 为例）

| 维度 | 直接用 AiToEarn | 用 Curis |
|---|---|---|
| 覆盖范围 | 只有内容营销 | 内容是 1/N 部门，全公司在 1 个 OS |
| 跨业务 | 无，内容是死胡同 | 内容 → 销售 → 客服可联动 |
| 记忆 / 资产 | 仅内容侧 | 一份品牌记忆贯穿所有业务 |
| 工具切换 | 内容用 A，其他另搞 | 一个平台全包 |
| 账单 | 各 agent 分别付 | 一张账单 |
| 用户感知 | "我在用 AiToEarn 发内容" | "我的 AI 公司发了抖音" |

**优势 = 广度 + 编排 + 持久化，不是内容能力本身。** 即便内容发布的叶节点借了 AiToEarn，用户也不会想去直接用它——它给不了其余 90% 的业务，离开成本极高。这正是对前面"双付费 / 导流"死结的终极解药：当我们有 10 个部门时，用户不会因内容这一个叶节点路过 AiToEarn 就跑路。

## 7. 法律与合规边界（执行端接入铁律）

- **白标第三方 Relay / 服务给租户 = 违反其 ToS**（如 AiToEarn §5.1 `non-sublicensable`）→ 非法。
- 干净落地只有两条：
  1. **谈 OEM / 商业授权**（合法白标 + 打包计费）
  2. **自托管其 MIT 开源代码**（执行端变自有，零第三方运行时成本）
  - 无 API 平台（小红书 / 视频号）的合法自建执行端可基于 MIT 项目 `dreammis/social-auto-upload`（patchright 浏览器自动化）改造——同样零第三方 ToS 绑定，且比自托管 AiToEarn 全栈更轻。
- 账号绑定步必然短暂披露第三方（法律要求），是最小感知的边界，不可消除也不该消除。
- 平台冲突：小红书 / 视频号无开放 API → 只能浏览器插件 / RPA（高风险、脆弱）；现可用 MIT 项目 `social-auto-upload`（patchright）自托管作合法执行端，但仍有反爬 / 封号 / UI 脆弱风险，作为"先打通、后替换"的过渡手段，而非终态。

---

## 8. 与内容部门（AiToEarn）的关系

- 内容部门是"执行端模式"的第一个、最完整的样例。
- **阶段 1**：只产出（方向③），不接执行端，验证工作流产出价值。
- **阶段 2**：执行端接入——优先走 **OEM 或自托管 MIT 代码**（非白标 Relay）。
  - **有 API 平台**（抖音 / B站 / 国际）：注册 Curis 自有 OAuth App，走原生 API（分支 A，稳定优先）。
  - **无 API 平台**（小红书 / 视频号）：先以 **social-auto-upload（MIT，patchright 浏览器自动化）自托管** 打通（分支 B），同时并行提交各平台开发者资质申请；资质获批后 drop-in 替换为原生 API（分支 B→A），执行层收敛到更稳的路径。
  - **渐进替换原则**：先 broad+risky（浏览器自动化全覆盖拿结果），后 narrow+stable（逐平台换成官方 API），脆弱面随替换递减。
- 抽象层契约（发布包 schema）Phase 1 就定义，阶段 2 直接 drop-in；切换执行端只改 Connector 层，工作流不变。
