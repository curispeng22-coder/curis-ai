# 内容发布工作台 UI / 运行语义审计

日期：2026-08-09  
范围：`curis-ui-prototype/workspace-runtime-xhs.html`、`workspace-runtime-shortvideo.html`  
目标：验证当前原型是否已经表达当时 Business Runtime v0.4 定义的内容发布责任、状态、CEO 门禁、版本审核审计和外部结果闭环。

> 本审计只评估当前原型的可见交互与运行语义，不把示例数据当成真实业务结果，也不替代 Runtime Simulation。

> 版本说明：本审计保留 2026-08-09 的现场证据，原始核对基于 v0.4；当前运行权威已升级到 Business Runtime v1.0。原审计结论仍然有效，并作为 v1.0 §9.1 的 UI / Simulation 前置证据。

## 1. 审计步骤

1. 打开小红书运营办公室首屏，检查业务目标、可信状态、指标和 Assistant 入口。
2. 查看小红书内容队列，检查内容状态、责任人、CEO 审核和证据呈现。
3. 打开抖音 / TikTok 运营办公室首屏，检查平台专属结果与 AI 团队表达。
4. 查看抖音 / TikTok 内容队列，检查制作、发布、数据和复盘关系。
5. 在小红书“待发布（CEO 确认）”卡片上点击“移动至下一阶段”，验证是否能绕过 CEO 门禁。
6. 检查内容详情是否能绑定审核意见到 `versionId`，并能把 CEO 批准版本与 `publishedVersionId` 发布回执对应起来。

## 3. 优点

- 两个平台已经有域专属指标，而不是完全共用一套指标。
- 运营办公室有责任链、管道、CEO 决策队列和上下文 Assistant，基础信息架构成立。
- 小红书的收藏率、抖音的完播率被明确为北极星指标，并提供口径说明。
- “示例数据”“待授权平台 API”等可信状态已经可见，具备进一步接入真实证据的入口。

## 4. 关键 UX / 运行风险

### P0 · CEO 审核门禁可以被绕过

小红书“品牌合作披露话术”位于“待发布（CEO 确认）”，但其“移动至下一阶段”按钮仍可用。点击后，内容进入“已发布（只读）”，而详情抽屉仍显示原来的“待发布”状态。说明卡片交互、详情状态和 Runtime 状态机没有统一入口。

这直接违反：

```text
APPROVED ≠ PUBLISHED
CEO 审核未完成不得发布
```

### P1 · 当前可见状态仍不是 ContentItem 状态机

小红书界面没有明确显示 `APPROVED`、`SCHEDULED`、`AWAITING_FEEDBACK`、`REVIEWED`；抖音界面把“数据”与“复盘”作为泳道，但没有表现未授权、发布失败、数据冲突、手动补录等分支。

### P1 · 版本审核与发布回执没有审计链

当前原型的详情抽屉没有 `versionId`、版本化审核意见、Reviewer / CEO Approver 或 `publishedVersionId`。因此无法证明 CEO 批准的版本就是平台实际发布的版本，也无法在内容被修改后强制重新审核。该场景尚未进入可执行原型验证，必须作为 Business Runtime v1.0 的 Simulation 门禁。

### P1 · 互动与线索回流没有运行对象

当前原型只显示点赞、收藏、播放、涨粉等聚合指标，没有评论、私信、提及、咨询或订单意向的 `InteractionItem`。因此无法证明互动分流、回复版本、敏感 / 线索升级和外部回复回执，也无法判断哪些互动需要 CEO 介入。

### P1 · 示例数字与业务动作同时出现

页面显示“示例数据”，但同时展示具体粉丝、投入产出、平台结果，并提供“通过”“打回”“放量”等动作。CEO 可能误以为这些数字已经可以用于业务决策。

### P1 · UI 语言和组织语义还未完全中文化

抖音页面仍使用 `Growth AI`、`Content AI`、`Video AI` 等英文角色名。真实用户界面应使用中文岗位名称，英文仅保留为内部对象名或中文后的开发标识。

### P2 · 首屏仍更像运营 Dashboard，而非运营办公室

首屏先展示大量指标卡和责任卡，真正的内容队列在首屏下方。对于 CEO，首屏应先显示“本周期目标、待我确认、下一次外部结果回报”，指标只作为证据上下文出现。

## 5. 可访问性风险

- 状态主要通过颜色点和浅色文字表达，需要补充可读状态文本和 `aria-live` 更新。
- “移动至下一阶段”在不同阶段都显示为可用按钮，缺少禁用原因和门禁说明。
- 当前审计没有覆盖键盘焦点顺序、屏幕阅读器朗读、缩放和移动端重排，需要在 Runtime 实现后单独验证。

## 6. 修正优先级

1. 统一所有卡片操作到 Runtime 状态入口；在 CEO 审核、平台发布和结果验收处显示明确门禁。
2. 为 XHS / TikTok 补齐 ContentItem 状态与失败分支；禁止卡片拖拽直接进入成功态。
3. 示例数据只用于布局预览，不能触发“通过、放量、扩大业务”等真实经营动作。
4. 统一中文岗位名称，并让 Assistant 汇报中显示“为什么现在需要 CEO”。
5. 调整首屏优先级：目标 / 待决策 / 下一回报先于指标卡。
6. 在详情抽屉中增加版本差异、绑定意见、批准人和发布回执校验；批准版本变化必须生成新版本并重新进入审核。

## 7. Runtime Simulation 准备度

| 场景 | 当前原型证据 | 结论 |
|---|---|---|
| XHS / TTK 正常闭环 | 有生产泳道，但没有统一 ContentItem 状态、真实发布回执或结果窗口 | **未通过** |
| 未授权发布 / 手动补录 | 仅有“待授权”展示，没有禁用主动作与手动证据表单 | **未通过** |
| 发布失败 / 重试 | 没有失败状态、错误原因与保留原版本的操作分支 | **未通过** |
| 数据延迟 / 冲突 | 有示例结果，但没有 `STALE / ABNORMAL` 证据路径 | **未通过** |
| CEO 拒绝 / 退回 | 有表面按钮，但没有版本化拒绝原因和重新审核状态 | **未通过** |
| 批准版本 ≠ 发布版本 | 没有 `versionId / publishedVersionId` 审计字段 | **未通过** |
| 互动 / 线索回流 | 没有 `InteractionItem`、意图分流、回复版本或 CEO 升级路径 | **未通过** |
| Workspace Studio 装修 | 有通用画布、节点、配置检查和模拟按钮，但没有平台变体、ReplyPolicy、互动节点或持久化审批 | **未通过** |

因此当前原型的唯一有效结论是：**布局方向可继续使用，运行语义尚未通过**。

## 8. 结论

当前原型已经足以证明“运营办公室”的布局方向，但还不能作为内容发布业务完成证据。下一版 UI 必须先修复 P0 门禁和版本审计缺口，再基于 Business Runtime v1.0 §9.1 逐场景重演；在 Simulation 通过前，不进入业务代码实现验收。
