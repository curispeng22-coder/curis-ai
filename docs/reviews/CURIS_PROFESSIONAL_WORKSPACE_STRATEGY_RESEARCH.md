## A. Executive Summary

Curis 不应承诺“任何业务说一句话，就现场生成专业级软件”。真正可信的策略应是：

> **Verified Professional Workspace First → Derived / Composed Second → Generic Workspace Fallback → Research / Generation Last**

核心原因不是 Generic Package 无价值，而是“可安装、可运行、可恢复”只证明通用底座成立，不证明 Domain 产品深度、专业 UX、行业能力边界、评估语义与价值语义已经成立。

本研究建议把 Curis 的 Workspace 能力分成两种产品形态：

- **Professional Workspace**：经过 Domain Research、专业产品设计、真实能力边界验证和 Domain E2E 验证的 Domain Application。
- **Generic Workspace**：基于通用对象、视图、责任、工作、结果和证据形成的灵活经营环境，服务未知业务、长尾业务、临时经营和早期验证。

Generic Workspace 不是失败品，也不是低配 Demo；它是诚实、可经营、可升级的起点。但它不应被宣传为与经过专业设计的 Vertical SaaS 或 Curis Verified Professional Workspace 等价。

Workspace Engineering 的新定位应从“总是从零生成 Workspace”升级为：

> **Workspace Architect / Resolver / Composer / Installer / Validator / Evolver**

只有在没有 Verified Match、没有合理派生、没有足够专业模块、Generic 也无法安全承载时，才进入新 Domain Research 与 Generated Candidate。

## B. Problem Discovery

### B.1 已确认的底座事实

当前 Product Authority 已接受：Workspace 不是 Page；一个 Workspace 可有多个 Professional Surface；一个长期 Workspace 由一条 canonical Operating Team responsibility boundary 贯穿；Surface 只声明 Responsibility Requirement，不绑定 Employee；Team、Work、Result、Evidence 与 Autonomous Operating 继续复用 Company OS。

2026-08-22 的 Multi-Surface Package Implementation Review 又证明了 bounded `curis.workspace-package/v2` 可以：

- 声明 Domain Navigation 与多个 Surface；
- 在一个 canonical Workspace ID 下切换、深链、恢复 last-active Surface；
- 由 Core 解析 Responsibility 与 Capability Gap；
- 复用 Work / Result / Evidence 与 Team / Employee projection；
- 在 packaged Desktop 中安装、重启和恢复；
- 不新增 Surface Runtime。

这证明了 **Generic Multi-Surface substrate 可行**。

### B.2 仍不能由底座证明的事实

上述实现没有证明：

- XHS、RD 或电商的专业 IA 已经正确；
- 专业 Surface 的对象密度、交互节奏与错误恢复达到产品级质量；
- Domain Action 与真实 Provider 边界已接通；
- Evaluation / Value Semantics 能支持专业判断；
- 一个真实 Domain 已完成端到端经营验证；
- Package 升级能安全迁移完整专业对象与 Specialized UX；
- 第三方 Package 达到安全、兼容和专业质量要求。

因此必须建立三个明确等式：

```text
Installable ≠ Professional
Professional ≠ Verified
Module verified individually ≠ Composed Workspace verified
```

### B.3 当前证据同步边界

`CURRENT_STATE.md` 的 2026-08-21 顶部条目仍把 Generic multi-Surface Package 列为未实现；2026-08-22 的正式 Implementation Review 已给出更新的 bounded accepted evidence。本研究只记录这一 `IMPLEMENTATION STATE SYNC GAP`，不修改 Current State、Pointer 或任何 Authority。

## C. Why Generic Workspace Is Insufficient

Generic Workspace 能表达对象、字段、列表、看板、日历、详情、责任、规则、Work、Result 与 Evidence，但专业经营质量还依赖五类 Domain-specific 资产：

1. **专业语义**：哪些是对象、View、Evidence、Result、External Provider Object；哪些状态允许外部副作用。
2. **专业信息架构**：用户先恢复什么经营语境，哪些工作是一等 Surface，哪些只是 Object View 或 Utility。
3. **专业交互**：代码 Diff、库存调整、订单拆分、内容排期、评论处理等不应退化为同一种 Generic Form。
4. **专业判断**：什么结果算好，证据强度如何，何时继续、调整、等待或升级。
5. **专业能力边界**：哪些操作只是建议，哪些需要真实 Connector、授权、幂等、回滚或人工 Gate。

Generic Builder 可以让对象“可录入”，却不能自动保证业务“被正确经营”。要求 AI 在现场同时发明 Domain Model、IA、UX、能力边界和评估规则，会把所有不确定性集中在第一次使用时，并把验证成本转嫁给用户。

## D. Professional Workspace Definition

Professional Workspace 是针对一个稳定 Domain / Operating Problem 经过专业研究、产品设计与验证的 Domain Application。它仍然是 Curis Workspace，不拥有第二套 Runtime。

它至少应具备：

- 明确的 Domain Model 与对象分类；
- 可解释的 Operating Model / Lifecycle；
- 多个围绕稳定专业问题组织的 Professional Surface；
- Specialized View、Detail、Editor 与 Tool；
- Responsibility Pattern 与 Capability Map；
- Domain Method 与真实 Provider boundary；
- Evaluation Semantics 与 Value Semantics；
- 专业员工协作 UX；
- 失败、未知、权限、外部副作用与恢复表达；
- Package version、migration 与真实 Domain E2E 证据。

“Professional”描述产品深度；它本身不自动等于“Verified”。未经完整验证的专业设计只能叫 Professional Candidate。

## E. Generic Workspace Definition

Generic Workspace 是由 Curis 通用底座组成的真实经营环境：

- Generic Object / Field；
- List / Board / Calendar / Detail；
- Work / Responsibility / Rule；
- Artifact / Result / Evidence；
- Shared Team / Employee Work Area；
- 有限的 Capability Requirement；
- 明确的 Gap、未知和人工 Gate。

它适合：

- Unknown Domain bootstrap；
- 临时项目或短期经营；
- 轻量内部流程；
- 自定义对象与工作；
- Professional Template 尚不存在的长尾业务；
- 验证业务是否值得专业化的早期阶段。

Generic Workspace 的承诺是“可以诚实地开始经营并保留真实历史”，不是“已经达到该行业最佳实践”。

## F. Package / Template Classes

以下名称均为研究候选，不冻结最终产品文案。

| 候选类别 | 本质 | Domain 深度 | UX 深度 | 自动化 | 最低验证 | 用户预期 |
|---|---|---:|---:|---:|---|---|
| Verified Professional Package | 完整专业 Domain Application | 高 | 高 | 可在验证边界内较高 | 全部专业验证 Gate | 可用于正式长期经营 |
| Derived Professional Package | 从 Verified Base 维护的 Domain / Platform delta | 中高至高 | 中高至高 | 继承与 delta 分别验证 | Base provenance + delta + regression | 与来源相近，但适用范围明确 |
| Composed Professional Workspace | 多个可复用专业模块在一个 Workspace 内组合 | 取决于组合 | 取决于组合 | 由组合后的责任与能力决定 | 模块证据 + 组合 E2E | 模块成熟不代表整体自动成熟 |
| Generated Candidate | 研究或 AI 生成的候选专业环境 | 不确定 | 未验证 | 保守 | 结构、风险、Gap 与 CEO Review | 能试用，不能冒充 Verified |
| Generic Workspace Package | 通用对象与工作底座 | 通用 | 通用 | 保守至中等 | Core contract / persistence / recovery | 可工作、可调整、可升级 |

来源与质量必须分开：Official、Partner、Community 是 publisher / provenance；Verified、Candidate、Unverified 是 assurance；Professional、Generic 是产品形态。

## G. Verified Workspace Criteria

“能安装”只是技术 Gate 之一。Curis Verified Professional Workspace 至少需要通过以下五组验证。

### G.1 Domain Truth

- 真实 Domain Research 与明确证据等级；
- Professional Object Model，区分 canonical object、View、Artifact、Evidence、Result 与 External Object；
- Operating Lifecycle、Responsibility Model、Capability Map；
- Evaluation / Value Semantics；
- 已知限制、平台规则与不确定性。

### G.2 Product / UX

- Professional IA 与 Multi-Surface 结构；
- Specialized View / Detail / Editor / Tool；
- Employee Collaboration UX 与 Decision Gate；
- Desktop 1440 / 1280 / 1024 / 390 或适用尺寸验证；
- Loading、Empty、Unavailable、Permission、Failure、Recovery 状态；
- 无 Generic Dashboard wall、Agent monitor 或配置工程化负担。

### G.3 Operating Proof

- 至少一条真实 Domain E2E；
- Work → Result → Evidence → Evaluation → Handoff / Decision → next Work；
- 真实 Provider / Connector 边界；
- 外部副作用、权限与失败恢复；
- 关键价值指标与证据来源可解释。

### G.4 Package / Runtime

- Package validation、digest、version pin、provenance；
- stable Workspace identity；
- Responsibility / Capability fail-closed；
- restart 与 history preservation；
- running Work protection；
- compatible update、migration、rollback 或明确拒绝边界。

### G.5 Product Stewardship

- 明确 owner、support scope、更新节奏和 deprecation policy；
- Domain facts 与 Provider boundaries 可持续维护；
- 版本兼容与迁移说明；
- 第三方依赖、许可证与安全责任清楚。

任何一组缺失，都不能使用 “Curis Verified Professional Workspace”。

## H. Official Workspace Library

Curis 应长期维护一个小而深的 Official Professional Workspace Library，但不应现在制定庞大产品清单。

选择标准应是：

- 用户需求频率与业务价值高；
- Domain 生命周期稳定且可验证；
- 可复用模块价值高；
- Curis 的 Autonomous Operating / Employee model 有真实差异化；
- Provider / Connector 边界可合法接通；
- Curis 有能力持续维护。

Library 条目应展示：适用业务、验证等级、版本、维护者、所需连接、已验证能力、未验证边界、可选模块、迁移政策。它不是营销模板画廊，也不能把“Official”自动等同于“Verified”。

## I. Reusable Professional Modules

Professional Module 应介于 Core 与 Full Workspace Package 之间，作为 Package composition asset，而不是新 Runtime。

候选模块可包括：Research、Content Production、Publishing、Growth Analytics、Commercial Opportunity、Catalog、Inventory、Order、Customer Service。

一个 Module 可以拥有：

- Domain semantic fragment；
- finite Professional Surface / Object View composition；
- Responsibility / Capability requirements；
- Method、Evaluation 与 Value semantics；
- Specialized interaction pattern；
- compatibility、version 与 verification evidence。

Module 不可以拥有：

- canonical Workspace identity；
- Team、Employee、Cycle、Work、Result 或 Session；
- 独立导航壳层；
- Module Runtime、Sub-Workspace 或 Mini App Runtime；
- 任意代码执行权。

模块复用有三层：

1. **Verified Interaction Pattern**：例如 Diff review、Content Calendar、Inventory exception table。
2. **Professional Module**：语义 + UX + Requirement + Evaluation 的组合。
3. **Full Workspace Package**：在一个 Workspace / Team boundary 内组织模块并完成整体验证。

## J. UI / UX as Package Asset

Professional UX 必须成为 Package 的一等资产，否则 Package 只能声明数据，而不能交付专业工作环境。

建议的长期分层是：

```text
Core Shell / tokens / accessibility / routing / truth
→ finite verified interaction and view registry
→ Professional Module composition
→ Workspace Package Surface composition
→ Workspace Instance configuration
```

Package 应能声明：

- Surface composition；
- Specialized View / Detail / Editor / Tool refs；
- interaction pattern refs；
- Domain presentation and terminology；
- responsive and availability behavior；
- object / projection / action mapping。

Core 继续拥有安全边界、路由、权限、数据范围与有限组件注册。近期不允许任意 HTML / React / JS 进入 Package。若有限 registry 日后无法承载某些高价值专业交互，可研究受审查、受签名、受权限限制的 extension，但必须由真实缺口触发，不在本轮设计。

## K. User Customization Boundary

普通用户可以安全配置：

- 业务名称、目标、规则与偏好；
- 已批准的 field / view / filter；
- 可选模块或 Optional Surface 开关；
- Responsibility coverage 与人员变更；
- Capability / Connector 选择与授权；
- layout preference、默认 / last-active Surface；
- 通知、节奏与允许的自动化边界。

普通用户不应被要求：

- 设计专业 IA；
- 发明 Professional Surface；
- 画 Handoff / DAG；
- 理解 Router / Runtime；
- 绑定 Agent ID；
- 编写 SQL、脚本或路由；
- 定义行业 Evaluation / Value Semantics；
- 处理 Package migration。

高级专家或 Workspace Engineering 可以提出结构化变更，但仍需通过 Preview、Gap、Validation 与必要 Gate，而不是把低代码 Builder 暴露给 CEO。

## L. Workspace Engineering New Role

Workspace Engineering 的默认职责应改为：

1. 理解 Business Intent；
2. 读取 Current Company Truth；
3. 识别 Domain 与经营阶段；
4. 查找 Verified Workspace；
5. 判断 Exact Match、Instance Configuration、Derived 或 Composed；
6. 解析 Team / Responsibility / Capability / Connection；
7. 安装、验证并激活；
8. 运营中监测 Gap 与版本；
9. 原地升级与演进；
10. 只有最后才发起新 Domain Research / Generated Candidate。

这不是否定 Workspace Engineering，而是把它从“生成器”提升为长期产品与经营架构能力。

## M. Resolution Order

建议候选顺序：

```text
Business Intent
→ Read Current Company Truth
→ Recognize Domain / scope / risk / duration
→ Search Verified Workspace Library
→ Exact Verified Match?
→ Instance Configuration sufficient?
→ Maintained Derived Package?
→ Verified Modules can compose safely?
→ Generic Workspace can operate honestly?
→ New Domain Research
→ Generated Candidate
→ CEO Review / validation before stronger claims
```

顺序中的每一步都允许返回明确 Gap；不为了“自动完成”而跳过能力、权限或专业验证。

## N. Exact Match / Derived / Composed

### N.1 Exact Match

用户要运营小红书账号，若存在 Verified XHS Professional Workspace，Workspace Engineering 应直接：instantiate → configure account / goal / rules → bind Team → resolve capabilities / connections → validate → operate。不得重新研究“小红书是什么”。

### N.2 Instance Configuration

AI 科技、美妆、宠物等内容垂类，如果仍使用同一 XHS 对象模型、Operating Lifecycle、Surface、能力边界与评估框架，应是同一 Package 的 Instance Configuration，不复制 Package。

### N.3 Derived Package

只有当相邻 Domain / Platform 出现需要长期维护的结构性 delta，才产生 Derived Package，例如：

- 新的 canonical object / state；
- 不同的 Provider / permission boundary；
- 不同的 Specialized UX；
- 不同 Evaluation / Value semantics；
- 不同 migration / compatibility policy。

Derived 必须保留 base provenance、版本兼容与 delta verification。简单换行业文案或账号定位不构成 Derived。

### N.4 Composed Workspace

当一个经营环境需要多个成熟模块时，可以组合，但必须继续满足：

- 一个 canonical Workspace；
- 一条 canonical Operating Team responsibility boundary；
- 一套 Work / Result / Evidence truth；
- 明确的跨模块对象与 Handoff；
- 组合后的 IA 与 E2E 验证。

若研究发现多个独立 Goal、问责团队或经营单元，应建立 sibling Workspaces，而不是 Sub-Workspace。

## O. Generated Candidate

Generated Candidate 只在没有 Verified Match、没有合理 Derived、没有足够模块且 Generic 不能充分承载时出现。

它的产品承诺必须明确：

- `FUNCTIONAL CANDIDATE`；
- `PROFESSIONAL UX UNVERIFIED`；
- `DOMAIN GAPS EXPLICIT`；
- `CAPABILITY / PROVIDER BOUNDARIES PARTIAL`；
- `CEO REVIEW REQUIRED`；
- 外部副作用默认收紧；
- 不显示 Verified badge。

Generated Candidate 必须把假设、证据、未知、缺口和升级路径一起交付，而不是只生成页面。

## P. Upgrade Path

Generic / Generated Workspace 应能尽量原地升级到 Verified Professional Workspace，保持：

- Workspace identity 与 Business relation；
- Operating Team 与 Employee identity；
- Work、Result、Evidence、Decision 与 history；
- Knowledge / Artifact references；
- capability grants 与 provider provenance；
- audit 与 retention policy。

升级流程应包括：

```text
Target Package match
→ compatibility and semantic mapping preview
→ object / field / responsibility / view mapping
→ running Work impact analysis
→ unresolved data and capability gaps
→ user / CEO gate when material
→ staged migration
→ validation
→ activation or rollback
```

不能安全映射的历史数据必须继续可读并带 provenance。若 identity-preserving upgrade 不成立，应提出 sibling Workspace + controlled handoff，而不是静默重建。

## Q. Version Evolution

Official Professional Workspace 的版本演进必须保护：

- running Work 固定使用原 Operating / Package origin；
- Surface 增加不自动改变当前执行；
- Surface 删除必须有显式 migration 或 fail-closed；
- Evaluation semantics 变化需要 versioned comparison；
- Capability requirement 变化需要重新解析授权与供应；
- history 使用当时版本解释；
- rollback 不丢失业务对象与证据。

版本可以增加 Surface、View、Capability 与 Evaluation，但“升级 Package”不能成为绕过产品 Gate 或权限 Gate 的方式。

## R. Autonomous Operating Relation

Professional Workspace 与 Generic Workspace 必须消费同一 Autonomous Operating Core。区别主要存在于：

- Domain semantics；
- Methods；
- Professional UX；
- Capability / Provider coverage；
- Evaluation / Value semantics；
- 可自动执行的安全 envelope。

同一 Core 不意味着相同自治程度。Verified Professional Workspace 因为方法、评估和能力边界经过验证，可以在批准范围内承担更强的持续运行；Generic / Generated 因语义不完整，应更保守地使用 WAIT、ESCALATE、CEO Review 与外部副作用 Gate。这个差异是 Policy / Package evidence，不是第二套 Runtime。

## S. Domain Capability Layer

建议区分两个概念，但不新增 Capability Runtime：

- **Atomic Capability**：web research、writing、image generation、browser、code execution、data fetch。
- **Domain Capability**：XHS content research、XHS publishing、inventory adjustment、order fulfillment、commerce customer service。

Domain Capability 是结构化专业能力合同：意图、前置条件、输入、输出、Evidence、风险、Gate、所需 Atomic Capability / Connector。它最终仍通过 Capability Provider、Assignment 与现有 Tool / Agent / Connector 解析执行。

Domain Capability 不直接授予权限，不绑定 Agent ID，不保存执行 Session，也不形成第二套 Runtime。

## T. Distribution / Ecosystem

近期应采用 Curis Official / Built-in Library，先证明少量高价值 Workspace 的深度、维护和升级能力。

长期可以允许第三方 Professional Package，但至少需要：

- versioned Package contract；
- UX / accessibility contract；
- finite component / action boundary；
- publisher identity、签名与 provenance；
- capability / permission / secret isolation；
- Domain evidence 与 verification level；
- migration、rollback、support 与 revocation；
- Core compatibility 与 regression evidence。

Marketplace 不是当前范围。第三方方向只影响今天的 Package contract 必须保持 publisher-neutral、brand-neutral、versioned 和 fail-closed。

## U. Quality / Trust Levels

建议不要把所有维度压成一个 Badge。至少分三轴：

| 轴 | 候选值 | 回答的问题 |
|---|---|---|
| Product form | Professional / Generic | 这是专业 Domain Application 还是通用经营环境？ |
| Provenance | Curis Official / Verified Partner / Community / User Generated | 谁维护、谁负责？ |
| Assurance | Verified / Candidate / Unverified / Deprecated | 哪些证据已经通过？ |

用户主界面可以压缩为易懂标签，但 Detail 必须能展开：验证范围、版本、连接、已知缺口和升级政策。

## V. XHS Case

XHS 说明 Generic substrate 与 Professional depth 的边界。

### V.1 可复用 Generic / Company OS 底座

- canonical Workspace / Team / Employee identity；
- Responsibility / Assignment / Handoff；
- Work / Result / Evidence / Decision / Cycle；
- Domain Navigation / Surface Registry；
- Generic Object / List / Detail / Calendar substrate；
- Artifact / Knowledge scoped projection；
- Package version、restart、route、availability、gap handling。

### V.2 Professional Domain Layer

- Account、Brand Brief、Topic、Experiment、Note、optional Brand Deal；
- Research → Strategy → Content → Publishing → Growth → Feedback → Review；
- XHS platform facts、account types、compliance and provider boundaries；
- Evaluation：内容有效性、增长来源、证据强度、策略判断；
- Value：账号成长、内容复用、转化与商业机会。

### V.3 Professional UX Layer

- Operating Overview 语境恢复；
- Research & Insight；
- Content Operating 与 Calendar Object View；
- Performance & Growth；
- Feedback Inbox；
- optional Commercialization；
- Note editor / preview / review / publishing interactions；
- 跨 Surface 对象锚点与员工协作。

### V.4 Specialized Capability Layer

- XHS research / signal collection；
- content generation and compliance review；
- publishing / scheduling within real provider limits；
- performance retrieval；
- comment / DM / lead handling within platform and regulatory limits。

Generic Workspace 可以保存 Note、排期与结果，却无法仅靠字段自动推导这些专业语义和 UX。当前 XHS 已有 Domain Research、Authority-reconciled Instance 与 Design Candidate，但 XHS migration、真实 Domain E2E 与完整 Provider boundaries 仍不足以称为 Verified Professional Workspace。

## W. RD Case

RD 证明 Professional Workspace 不是内容业务特例。

Generic substrate 可以表达 Work、责任、文件引用、Result 与 Evidence，但专业研发需要：

- Code / Source、Diff / Changes、Terminal、Build / Test、Preview / Artifact；
- Responsibility Holder 与 Current Executor 的严格区分；
- Artifact Review Request 与责任 Handoff 的区别；
- 多个并行 Employee Workstation；
- provider-native coding session、worktree / source scope 和 test evidence；
- release、rollback、dependency、architecture decision 与 failure recovery；
- Evaluation：correctness、test coverage、performance、security、maintainability；
- Value：可交付、可恢复、可审查的软件结果。

这些 Specialized UX 不应退化为 Generic Form / Table，也不能由 XHS Calendar 模式复制。RD 仍复用同一 Company OS / Package / Autonomous Core。

## X. E-commerce Stress Test

复杂电商同时包含商品、SKU、库存、订单、渠道、营销、客服、内容、结算与财务关系。Generic Workspace 可以做商品列表、订单表和客服 Work，但无法自动保证：

- SKU / 仓库 / 渠道库存一致性；
- order split、fulfillment、return / refund state；
- oversell、stockout、reservation 与 reconciliation；
- 渠道费率、促销、归因与利润；
- 客服 SLA、补偿和高风险退款；
- 真实 Connector side effect、幂等和回滚；
- margin、cash、return rate、inventory turn 等 Value Semantics。

可复用专业模块候选：

- Product / Catalog；
- Inventory；
- Order / Fulfillment / Return；
- Channel Operations；
- Marketing；
- Customer Service；
- Content Commerce；
- Finance / Settlement projection。

如果这些模块服务同一店铺目标并由一支可问责团队经营，可以组成一个 Professional Workspace；如果品牌、店铺、法规边界或团队问责独立，则应形成 sibling Workspaces。不得用 Module Runtime 或 Sub-Workspace 掩盖真实经营边界。

电商压力测试结论：Generic Workspace 能作为 bootstrap 和补充操作面，但对交易一致性与外部副作用不能宣称 Professional 等价；专业模块与整体验证是必要的。

## Y. Product Promise

建议 Curis 对用户承诺：

> Curis 优先为常见、高价值业务提供经过专业研究、产品设计和真实验证的 AI 团队工作环境；相近业务通过配置、派生和专业模块快速适配。没有成熟专业模板时，Curis 仍能提供诚实标注的通用或生成式工作环境，让业务先开始运转、保留团队与经营历史，并在成熟方案出现后尽量原地升级。

不应承诺：

- 任何行业一句话即生成专业级软件；
- 能安装即代表行业验证；
- AI 自动化可以替代所有专业判断；
- 所有 Provider / Connector 默认可用；
- Generated Candidate 与 Verified Workspace 同等质量。

## Z. CEO Decisions

CEO 只需决定以下十项：

1. 我们以后是否优先提供经过验证的专业工作空间，而不是默认从零生成？
2. 通用工作空间是否定位为长尾、未知业务和早期经营的真实起点，而不是专业软件的替代品？
3. 空间工程是否从“从零生成器”升级为“发现、匹配、配置、组合、安装、验证和演进优先”？
4. 专业界面与交互是否成为 Workspace Package 的一等资产？
5. Curis 是否长期维护一个少而深的官方专业工作空间库？
6. 是否允许相近业务通过配置、受维护的派生版本和专业模块组合形成 Workspace？
7. AI 生成的 Workspace 是否必须明确标为 Candidate，并使用低于 Verified 的质量承诺？
8. 通用或生成 Workspace 是否必须尽量支持保留团队、工作、结果、证据和历史的原地升级？
9. 是否保留第三方 Professional Package 的长期方向，但暂不建设 Marketplace？
10. 是否接受本研究提出的用户承诺：专业模板优先、长尾也能开始、质量等级透明、未来可升级，而不是“任何业务一句话生成专业软件”？

STOP FOR CEO REVIEW.
