## 1. Candidate Model

```text
Business Intent
      ↓
Read Current Company Truth
      ↓
Recognize Domain / scope / risk / duration
      ↓
Verified Exact Match?
 ├─ Yes → Instantiate → Configure → Bind Team → Resolve Capability → Validate → Operate
 └─ No
      ↓
Instance Configuration sufficient?
 ├─ Yes → Reuse same Verified Package; no Package copy
 └─ No
      ↓
Maintained Derived Package?
 ├─ Yes → Apply verified base + verified delta
 └─ No
      ↓
Verified Professional Modules can compose safely?
 ├─ Yes → Compose → validate combined IA / responsibility / E2E
 └─ No
      ↓
Generic Workspace can operate honestly and safely?
 ├─ Yes → Bootstrap → operate → collect evidence → preserve upgrade path
 └─ No
      ↓
New Domain Research
      ↓
Generated Candidate
      ↓
CEO Review / bounded validation
      ↓
Candidate, Derived, Composed or future Verified Package
```

Generation is the last resolution path, not the default.

## 2. Layer Comparison

| Resolution layer | Quality promise | UX depth | Automation | Verification | Upgrade path |
|---|---|---|---|---|---|
| Verified Exact Match | 已验证范围内的正式专业产品质量 | 完整 Domain IA、Surfaces、Specialized Views / Tools | 可在已验证规则和 Provider 边界内持续运行 | Domain + UX + Package + Desktop + E2E + evolution | 正常版本升级，保护 running Work 与 history |
| Instance Configuration | 保留来源 Package 的验证等级，限于允许配置范围 | 与 Verified Base 相同 | 与 Base 相同，按实例能力和授权收缩 | 验证配置、Team、Capability、Connection、data scope | 同 Package 原地演进 |
| Derived Package | Base 证据可复用；delta 只在单独验证后成立 | 继承 Base，并加入长期维护的 Domain / Platform delta | 继承部分需重新校验 | Base provenance + delta + regression + migration | 跟随 Base compatibility 与 Derived 版本 |
| Composed Workspace | 模块成熟不自动等于整体成熟 | 模块级专业 UX；整体 IA 必须重新收敛 | 由组合后的 Responsibility / Capability / Evaluation 决定 | Module evidence + composition validation + Domain E2E | 模块独立升级，整体做 impact preview |
| Generic Workspace | 真实可经营、可恢复、Gap 透明；不承诺专业 SaaS 等价 | 通用 Object / List / Board / Calendar / Detail / Work | 保守；未知与外部副作用更多 Gate | Core contract、persistence、scope、failure、restart | 映射到 Verified Package，尽量保留 identity / history |
| Generated Candidate | Functional candidate；专业 UX 与 Domain 能力未验证 | 研究或生成的候选 IA / Surface / View | 最保守；默认 CEO Review / WAIT / ESCALATE | 假设、证据、Gap、风险与候选验证 | 先收敛为 Generic / Derived / Composed，再争取 Verified |

## 3. Resolution Rules

### Rule 1 — Exact before invention

已有适用 Verified Workspace 时，不重新研究同一 Domain，不复制 Package，不生成新菜单。

### Rule 2 — Configuration before derivation

行业垂类、账号定位、品牌语气、目标、团队与规则差异，优先使用 Instance Configuration。只有对象、生命周期、专业 UX、Provider boundary 或 Evaluation semantics 出现长期结构性变化时，才建立 Derived Package。

### Rule 3 — Composition before generation

已有 Verified Modules 能覆盖主要经营问题时，优先组合。组合必须保持一个 canonical Workspace 与一条 accountable Operating Team boundary；多个独立 Goal / Team boundary 应形成 sibling Workspaces。

### Rule 4 — Generic before pretending

Generic Workspace 能让业务安全开始时，应诚实使用 Generic，而不是生成一个看起来专业但未经验证的产品。

### Rule 5 — Generation requires evidence

Generated Candidate 必须同时交付 Domain assumptions、evidence、unknowns、capability gaps、risk gates、verification plan 与 upgrade path。

### Rule 6 — Same Core at every layer

所有层继续使用同一 Company OS / Autonomous Operating Core。质量差异来自 Domain semantics、UX、Method、Capability、Evaluation、Value 与验证证据，不来自新的 Runtime。

## 4. Decision Inputs

Workspace Engineering 在每一层至少判断：

- 业务目标是否长期；
- Domain / platform / regulatory boundary；
- 是否存在一个或多个 accountable Team boundary；
- Verified Match 的适用范围和版本；
- 需要哪些 Professional Modules；
- Capability / Connector / permission 是否可用；
- 是否存在高风险外部副作用；
- Generic 是否足够安全；
- 需要保留哪些 identity、data、Work、Result、Evidence 与 history；
- 何时必须 CEO Gate。

## 5. User-facing Outcome

用户看到的不是内部解析树，而是一句明确说明：

- “已找到经过验证的小红书专业工作空间，将按你的账号和团队配置。”
- “这个业务可由已验证模块组合，但组合后的整体仍需一次验证。”
- “目前没有成熟专业模板，先建立通用工作空间；已明确哪些能力可用、哪些需要补齐。”
- “这是 AI 生成的候选环境，专业界面和行业能力尚未验证，需要先审查再用于关键经营。”

## 6. Non-goals

本 Candidate 不定义最终 Package Schema、Template Library、Marketplace、Module Runtime、Sub-Workspace、UI Store、自动安装流程或开发 Issue。
