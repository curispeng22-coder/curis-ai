# Curis 产品重新推导审计

Status: Review

日期：2026-08-10  
目的：重新推导 Curis 的完整产品形态，纠正“单机自用可以删减能力”和“Blueprint 先划定范围再实现”的偏差。

## 1. 审计结论

当前 Curis 的经营逻辑已经形成，但产品定义出现了层次混淆：

```text
产品身份
CEO 经营逻辑
用户使用体验
技术实现约束
未来商业化边界
```

它们被写进同一套“当前规则”后，出现了三个直接后果：

1. Blueprint 越来越像研发审查制度，而不是完整产品说明。
2. “Local Desktop / 单一 CEO”被误解为可以省略模型、Skill、Tool、能力配置和真实运行能力。
3. 页面被要求先证明 Runtime 状态，导致用户使用链路、产品入口和完整 App 形态没有优先形成。

这不是 Curis 经营模型错误，而是产品规划层次错误。

## 2. 重新确定产品身份

Curis 首先是一款 Desktop App，其核心用途是帮助一位 CEO 创建、经营和扩展一人 AI 公司。

```text
App
└── CEO 经营个人 AI 公司
    ├── 创建公司
    ├── 创建业务
    ├── 配置 AI 组织
    ├── 配置模型、Skill、Tool 和知识
    ├── 搭建业务 Workspace
    ├── 运行工作
    ├── 获取真实结果
    ├── 做出经营决策
    └── 优化和扩展公司
```

Local 只描述交付方式，不描述产品能力等级。

> 本地部署可以减少租户、计费和云端运营复杂度，但不能减少 CEO 为了经营公司必须使用的功能。

## 3. 产品完整性的判断标准

产品是否完整，不由页面数量、后端模块数量、部署方式或用户数量决定，而由 CEO 能否独立完成以下闭环决定：

```text
进入 App
→ 建立公司
→ 表达经营意图
→ 形成业务
→ 配置模型与能力
→ 组建 AI 员工
→ 搭建 Workspace
→ 委派与执行
→ 查看结果和证据
→ CEO 验收或修正
→ 外部反馈回流
→ 调整能力、组织和业务
→ 开始下一轮经营
```

任何一个关键环节缺失，Curis 都只能算部分产品，而不是完整产品。

## 4. 完整产品地图

### 4.1 App Shell

- 应用身份、公司切换（当前只有一个 Company，但不能把结构写死）
- 全局 Assistant
- 全局搜索与上下文返回
- 通知、运行状态、主题和设置
- 当前 CEO 所在经营位置和最近工作

### 4.2 首次进入与公司创建

- 空白但不空旷的首次空间
- Assistant 自我介绍和经营访谈
- 公司基本设定
- CEO 经营目标和边界
- 第一个业务方向
- 第一个结果和验收方式
- 初始公司结构建议
- 首批 AI 员工和能力建议
- CEO 确认、修改或重新开始

### 4.3 CEO 经营入口

- CEO Operating Day：今天发生了什么、需要知道什么、需要决定什么
- 公司脉搏：业务、能力、容量、现金/成本、风险和外部结果
- Assistant 主动汇报、准备、提醒、分流、跟进和召集
- 待决策、待验收、待补证据和异常事项
- 从任何事项回到原经营上下文

### 4.4 公司和组织

- 公司定位、经营目标和阶段
- 业务版图，而不是项目列表
- AI Workforce Map：CEO → Assistant → 专业 AI → Workspace AI
- AI 员工档案、责任、汇报关系、当前状态、运行记录和结果
- 岗位创建、调整、暂停、交接和替换
- 部门 / 办公室创建与拆分
- 组织容量、负载、成本和能力缺口

### 4.5 能力中心

能力中心不是可选后台，而是公司能够工作的基础设施。

- 添加模型和模型提供商
- 验证模型连接
- 模型参数、默认模型、备用模型和成本记录
- 接入 Skill
- 接入 Tool / Connector / 外部服务
- 配置凭证引用、权限、数据范围和副作用等级
- 能力版本、测试、启用、停用和替换
- 能力分配给 AI 员工、岗位和 Workspace
- 能力缺口、调用失败、成本和容量观察

能力完整链：

```text
添加
→ 验证
→ 形成能力
→ 配置权限
→ 分配给岗位 / 员工
→ 在 Workspace 中调用
→ 查看结果 / 成本 / 失败
→ 调整、替换或停用
```

### 4.6 业务与业务版图

- 发现业务机会
- 创建业务方向
- 业务目标、服务对象、外部承诺和验证结果
- 业务阶段：构想、验证、运行、扩大、暂停、退出
- 业务投入、产出、风险和下一检查点
- 从业务进入 Workspace
- 从结果反向调整业务或创建新业务

### 4.7 Workspace Studio

Workspace Studio 是搭建业务空间的地方，不是 Agent 配置器。

```text
理解业务
→ 设计工作方式
→ 安排岗位
→ 配置模型 / Skill / Tool / 知识
→ 设计工作阶段
→ 配置数据窗口和外部反馈
→ 配置验收与失败路径
→ 试运行
→ CEO 确认
→ 进入业务办公室
```

### 4.8 业务 Workspace

每个业务有自己的业务办公室，但共享公司身份、Assistant、组织和能力基础。

统一保留：

- 当前目标和外部结果
- AI 团队与工作状态
- 当前周期和承诺
- 执行过程和交接
- 证据、验收和反馈
- 失败、阻塞、重试和下一步

业务可以有不同的布局：研发工作台、内容运营工作台、研究工作台等，但不应被压扁成同一种看板。

### 4.9 会议与决策

- Assistant 会前准备
- 对话式会议空间
- 事实、观点、建议、异议和未知
- 决议、承诺、责任人、时间和证据
- CEO 批准、修改、拒绝或延后
- 决议回到 Workspace 和公司经营循环

### 4.10 结果、知识和资产

- 外部平台数据或 CEO 手动录入
- 客户验收和交付反馈
- 运行证据和来源
- 版本、成果、知识和公司经验
- 决策引用的事实与历史
- 结果反向形成 Insight、能力改进和业务调整

### 4.11 经营工具

- 日历：经营节奏、检查点和承诺，不是预置事件列表
- 成本与资源：模型调用、能力成本、业务投入和产出解释
- 通知：按影响分级，不制造信息噪音
- 设置：公司、CEO、连接、数据、主题和本地运行

## 5. 产品形态与实现阶段分离

完整产品地图中所有上述能力都存在。实现时使用阶段标签，而不是把能力写成“不做”：

| 标签 | 含义 |
| --- | --- |
| 可用 | CEO 当前可以真实使用 |
| 建设中 | 产品形态已确定，正在形成完整链路 |
| 待接入 | UI / 运行逻辑存在，等待模型或外部连接 |
| 人工回退 | 暂无 API 时由 CEO 手动提供真实结果 |
| 商业化后 | 仅涉及租户、计费、市场或云端平台能力 |

“暂时未实现”不能被写成“Curis 不需要”。

## 6. Blueprint 5.0 收敛结果

唯一 Blueprint 5.0 已按以下顺序组织：

```text
产品身份
→ CEO 生命周期
→ 完整 App 地图
→ CEO 用户动线
→ 公司经营逻辑
→ AI 组织与能力系统
→ Workspace Studio 与业务 Workspace
→ 结果、反馈和决策
→ 页面和交互原则
→ 当前实现状态
→ 未来商业化拆分
```

技术 Runtime、Simulation、Issue、Review 和文件边界保留在实现附录，不再作为产品入口或产品想象的前置限制。

## 7. 明确纠正

以下判断废止：

- 单机自用可以省略模型、Skill、Tool 和能力管理。
- 三业务只是验证样例，不需要形成完整业务体验。
- 未来能力可以直接从产品地图删除。
- Blueprint 可以用“暂不建设”替代完整产品定义。
- 页面只有在满足全部 Runtime 门禁后才允许形成产品体验。

新的判断是：

> 先设计完整产品，再按优先级逐步实现；实现阶段可以简化技术方式，但不能删掉 CEO 经营所需的能力。

## 8. 规划完成后的下一步

1. CEO 确认 Blueprint 5.0、页面级布局契约和 EvoFlow 借鉴边界。
2. 以 `docs/plan/curis-product-completion-roadmap-evoflow-2026-08-10.md` 为开发顺序和 Issue 拆分依据。
3. 按 Phase 0–8 建立正式 Issue；每个 Issue 必须包含真实入口、空态、配置、运行、结果、失败和返回 CEO 的动线。
4. 开发过程中继续以 Blueprint 5.0 为产品真相，以 `CURRENT_STATE.md` 区分已交付事实，不从旧 UI 或历史 Blueprint 反推产品。

## 9. CEO 的完整使用动线

### 9.1 第一次打开

```text
打开 App
→ 看到空的 CEO 办公室
→ Assistant 介绍自己
→ CEO 说出想经营什么
→ Assistant 整理为公司与业务方案
→ CEO 修改 / 确认
→ Company、首个业务、Assistant 和最小 AI 团队生成
```

这里的关键不是“完成注册”，而是让 CEO 感觉公司正在被建立。

### 9.2 已有公司进入 App

```text
打开 App
→ CEO Desk / 今日经营
→ Assistant 汇报昨天、今天、风险和待决策
→ CEO 处理少量高影响事项
→ 点击事项进入业务、团队、能力或 Workspace 上下文
→ 完成后回到原来的经营位置
```

CEO 不需要先猜哪个模块拥有信息；Assistant 和 CEO Desk 负责把信息整理成入口。

### 9.3 配置 AI 员工能力

```text
CEO 发现业务需要能力
→ 打开能力中心或直接告诉 Assistant
→ 添加 / 选择模型
→ 接入 Skill / Tool / 外部连接
→ 验证可用性和权限
→ 选择岗位 / 员工 / Workspace
→ 设置成本、容量和副作用边界
→ 试运行
→ 启用
```

能力中心必须同时支持“资产管理视角”和“经营配置视角”：前者管理可用资源，后者回答“谁需要它、为什么需要、现在是否够用”。

### 9.4 创建新业务

```text
CEO 说出机会或新想法
→ Assistant 判断是否已有业务可承接
→ 若没有，形成新业务草案
→ 明确服务对象、结果、投入和验证周期
→ 提出 AI 团队和能力方案
→ CEO 确认
→ 进入 Workspace Studio
→ 交付第一版业务办公室
→ 开始第一个周期
```

新业务不应该从一个空表单开始，也不应该强迫 CEO 先理解 Workspace、Agent 或 Runtime 等内部术语。

### 9.5 一天结束

```text
业务结果、成本、失败、外部反馈和 CEO 反馈回流
→ Assistant 归纳变化和未知
→ 形成学习与下一步建议
→ CEO 继续、调整、暂停、扩大或关闭
→ 公司和 Workspace 进入下一轮
```

## 10. 由经营动线反推导航

导航不按后端表或旧页面排列，而按 CEO 在经营中反复问的问题排列：

| 导航区域 | CEO 要解决的问题 | 主要入口 |
| --- | --- | --- |
| 今日经营 | 现在发生了什么，我要处理什么？ | CEO Desk、Assistant、待决策、待验收 |
| 经营 | 公司是否健康，方向是否需要调整？ | 公司脉搏、风险、投入产出、决策 |
| 业务 | 我正在经营哪些业务，它们创造了什么价值？ | 业务版图、业务详情、新业务 |
| 公司 | 我的 AI 团队和能力是否足够？ | AI 团队、岗位、部门、能力中心、资源 |
| 工作空间 | 每个业务具体如何工作？ | Workspace Portal、Studio、业务办公室 |
| 公司资产 | 结果和知识是否可以复用？ | 成果、知识、记忆、财务、日历 |
| 经营工具 | 一次需要集中讨论或确认什么？ | 会议、决策、审查 |

“能力中心”不能隐藏在组织页中；“会议”不能只是一个空壳入口；“日历”不能只保留未来占位。只要它们是 CEO 完成经营闭环所必需的，就必须拥有完整产品形态。

## 11. 对当前前端现场的初步判断

当前前端已经有许多目标入口，但完整性不一致：

| 区域 | 当前现场 | 产品判断 |
| --- | --- | --- |
| CEO Desk | 已接入 Runtime 投影和 Assistant | 方向正确，但需要成为所有经营动作的返回中心 |
| 能力中心 | 有模型 / 能力目录、详情和注册入口 | 必须继续补齐 Skill、Tool、权限、验证、分配和成本动线 |
| 业务版图 | 已有 Runtime Workspace 卡片 | 需要补齐创建业务、阶段决策和业务结果反馈 |
| Workspace Portal | 已有门户、Studio 和三业务入口 | 需要让 Studio 真正完成“业务空间装修”，而不是只提交 Blueprint 草案 |
| AI 团队 | 有 Workforce Map 和员工页面 | 需要统一 Runtime 员工、岗位、能力分配与组织关系 |
| 会议工作台 | 当前仍是规划中占位 | 需要形成会前、讨论、决议和回写闭环 |
| 日历 | 当前仍是规划中占位 | 需要由经营承诺和检查点生成，而不是预置日历 |
| 成果 / 报告 | 部分页面仍有示例内容或旧 Project 语义 | 必须清理示例数据和旧链路，全部回到真实 Company / Business / Workspace |
| 研发 / 小红书 / 抖音 | 已有 Runtime 页面和业务差异 | 需要继续补齐真实能力接入、执行、外部反馈和 CEO 调整 |

这说明当前最需要的不是继续增加治理规则，而是逐页补齐完整 App 动线。

## 12. 新的产品规划原则

1. **完整形态先于实现顺序。** 所有 CEO 必需能力先进入产品地图，再决定先后。
2. **本地实现不等于低配产品。** 可以用本地数据库、人工输入和本地模型替代云服务，但不能删除经营动作。
3. **能力接入是核心产品。** 模型、Skill、Tool、知识、权限、成本和容量必须成为可使用的公司基础设施。
4. **Assistant 是第一位 AI 员工。** 它是产品主入口和经营协调者，不是一个按钮或聊天浮层。
5. **Workspace 是业务办公室。** 它不是配置表，也不是 Task 列表；它必须让 CEO 看到业务目标、团队、状态、执行和结果。
6. **页面完成要看用户闭环。** 空态、配置、运行、失败、结果、反馈和返回路径都属于产品。
7. **阶段标签不等于产品排除。** 暂未实现、人工回退、待外部接入和商业化后分别记录，不互相替代。
8. **治理服务产品。** Runtime、Simulation、Issue 和 Review 用来保护真实经营，不得成为 CEO 体验的前置障碍。

## 13. 按完整形态安排实现顺序

下面是实现顺序，不是产品范围。每一阶段都要保持完整 App 地图和后续入口可见。

### 第一优先：让 CEO 能真正建立并启动公司

- 首次进入空间、Assistant 对话、公司创建和第一业务创建
- 能力中心：至少完整支持模型添加、连接验证、默认 / 备用模型和分配
- AI 员工：岗位、责任、汇报、能力绑定和启停
- Workspace Studio：从业务描述到业务办公室，而不是只提交一份草案
- CEO Desk：创建后能看到公司、业务、AI 团队和下一步

### 第二优先：让三条业务真正工作

- 研发工作台：周期、代码 / 构建 / 测试证据、CEO 验收和下一周期
- 小红书运营工作台：内容版本、授权发布、互动和手动结果反馈
- 抖音 / TikTok 运营工作台：内容生产、发布回执、指标窗口和增长调整
- 三条业务统一使用能力中心和 Assistant，但保留业务自己的工作方式

### 第三优先：让公司可以持续经营

- CEO Operating Day 的主动汇报、异常和决策收束
- 会议工作台：准备、讨论、决议、承诺和回写
- 日历：从承诺、检查点和节奏生成
- 成果、知识、记忆、成本和能力负载回流
- 从结果创建新业务、扩展 Workspace 或调整组织

### 第四优先：打磨完整 Desktop 产品

- 统一侧栏、页面层级、主题和中文文案
- 所有页面统一空态、失败、等待、权限和返回路径
- 本地模型 / 外部连接配置、数据备份、升级和恢复
- 打包、启动、更新、单实例和本机使用体验

### 第五优先：商业化延伸

- Platform / Admin
- 多租户和多用户
- 计费、模板版本和市场
- 云端部署与跨设备同步

这些阶段都不是“做了前面的就不需要后面的”。它们共同构成 Curis 的完整产品，只是交付顺序不同。
