# ADR-0017: 多租户 CEO 模型与「部门目录」通用化设计

## Status
Proposed

## Context

用户澄清了产品的设计初衷，修正了此前「单人公司 + 未来才多部门」的假设：

1. **产品从设计之初就是商业化的多人系统**：每次登录的人都是一个独立的 CEO，拥有自己的商业范围、可选运营平台、可配置的公司部门。
2. **部门是一等的可配置实体，且不限于业务型**：既包含对外承接业务的「业务部」（抖音、小红书、微信、头条、番茄、起点等平台通道），也包含对内治理的「职能型部门」，例如：
   - **人事部**：增删部门员工、给员工分配角色定位、配备不同技能（即 L2/L5 员工层 + 角色/技能配置，当前 gate 禁止，未来需开放）；
   - **行政部**：统计部门与员工的 ROI、任务量、token 消耗产出比等（即 L6 经济层的核心度量）；
   - **BI 部**：产出各维度数据的可视化与分析（即 L6 分析展现层）。
3. 系统把「公司自身」也当成可被部门运维的数据对象——职能型部门消费公司运营数据，反哺 CEO 驾驶舱与演进治理。这要求系统**自可观测**。

这与此前架构文档的差异：之前把 L5（组织/部门）、L6（经济/ROI）当作「内部架构层」与「未来多部门业务」割裂讨论；本 ADR 将其统一为**用户可配置的、业务型与职能型并存的部门目录**，并明确产品是商业化多租户。

### 关键约束（来自 AGENTS.md 当前 gate）
- 当前上线范围仍是 **AI Task Executor MVP v0.1**，严格禁止：L5 公司组织、L6 经济/ROI、Employee CRUD、多 Agent、外部服务、复杂 UI。
- 因此本 ADR 是**未来阶段方向（Proposed）**，不是当前可实现任务；落地需 总控决策席 批准对应未来 gate，且接外部平台/密钥/合规必触发 安全边界席。

## Decision

提出四项子决策，作为「先打地基（ADR-0016）→ 开多部门」的下一步方向：

### D1 — 多租户 CEO 模型（设计预留，实现暂缓）
- 每个登录者是一个 CEO 租户；其「公司」= 一份 `company_topology` manifest（启用哪些部门、各接哪些平台、质量线、护栏引用）。
- **现在就做**：聚合根（Task / Department / Employee / Asset / EvolutionLog）预留 `tenant_id` 作用域，使未来开启多租户时只是「加列 + 中间件注入」，而非重写。
- **暂不实现**：真正的多租户隔离、凭证按租户作用域隔离、worker 透传 `tenant_id`。当前仍是单用户单进程。
- 隔离档位留作未来决策：A. 共享库 + tenant_id 列（推荐起步，隔离靠中间件纪律）；B. 每租户独立库/schema（企业版阶段）；C. 每 CEO 独立部署（否决，违背「同一套系统」）。

### D2 — 部门目录通用化（业务型 + 职能型）
- 每个部门 = 一份 **Manifest** 配置单元，字段：`能力集 · 可用工具类 · 质量线 · 输出通道 · ROI schema · 护栏引用 · 员工角色 spec`。
- 部门分两类，共用同一套 Manifest 缝：
  - **业务型（对外）**：业务部及其平台通道，对应集成网格 + 异步长时编排。
  - **职能型（对内）**：人事部 / 行政部 / BI 部 /（可扩展财务、法务、客服…），在系统内部运维公司自身。
- 系统级维护「部门类型目录」（建一次、全员可用）；每个 CEO 从目录中挑选子集组成自己的公司拓扑。

### D3 — 职能型部门「元循环」与自可观测
- 职能型部门消费公司运营数据（Tasks / Employees / Tokens / Platforms / Assets / EvolutionLog），产出 ROI 统计、角色/技能配置、可视化分析，反哺 CEO 驾驶舱与 Evolution Governor 的经济驱动编排。
- 这把 ADR-0016 的 D3（追加写演进/度量事件日志 + correlation id）从「审计 nice-to-have」**升级为硬依赖**：行政部/BI 部要算 token 产出比、做可视化，系统就必须把自身运行数据作为一等可查询数据暴露。
- 人事部管理 Employees 的增删/角色/技能 = 未来 L2/L5 员工层的事实接口；其与 ADR-0016 D1（runtime role 接入）是同一能力的「配置面」与「执行面」。

### D4 — 两级治理与开放边界
- **类型级扩展**（新增一个*部门类型*，如冒出「电商」）：仍走 **gate + ADR**，防止系统自行长出陌生部门（watchmen 入口）。
- **实例级扩展**（在已有类型下，某 CEO 启用/停用部门、增删平台账号、调整质量线）：仅配置 + 入审计日志，无需走完整 gate；human-in-loop 中的「人」即该 CEO 本人。
- Evolution Governor 的演进范围被限制在*单个部门内部*，不得越界改其他部门的 manifest（护栏即数据）。

## Consequences

**变得更容易：**
- 「新增一个业务/职能方向」从一次跨 L0–L6 大爆炸，降级为一次 manifest 注册 + 实例级配置。
- 产品形态从「一个 AI 公司」升级为「可拼装的商业能力目录，每个 CEO 组装自己的公司」——部门模块化即商业模式本身。
- 内部架构层（L5/L6）与外部业务（视频/文案/小说）用同一套部门模型表达，心智统一、复用执行内核与工具系统 v1.8。

**变得更难 / 需正视的代价：**
- **多租户终结「纯本地零依赖」简洁性**：数据/凭证/计算的租户隔离是硬需求，与 MVP 核心卖点冲突——必须分阶段、先预留再实现。
- **自可观测成为地基而非补丁**：系统必须先把自身运行数据建为可查询/可归因的数据源，行政部/BI 才成立；这把 ADR-0016 D3 的优先级显著提前。
- **职能型部门引入元递归复杂度**：部门在运维部门（人事管业务部员工、行政算业务部 ROI），需明确数据权限边界（租户内跨部门可见、租户间不可见）。
- **治理开销复利风险仍在**：部门类型一多，每新增类型走 gate+ADR 仍可能反噬交付；D4 的两级治理是缓解而非消除。

**明确的非目标（Forbidden / 当前 gate 外）：**
- 不解除自动改码禁令；生产变更仍需人工批准。
- 现在不实现多租户隔离、Employee CRUD、外部平台集成、L6 经济回流——均留待对应未来 gate，并经 总控决策席 / 安全边界席 批准。
- 不预支过多部门类型槽位；新槽位在真实第 2、3 个部门出现、模式被验证后再补。

## Relations
- 依赖 **ADR-0016**（执行实质化：runtime role 接入 / Governor 沙箱 / 追加写事件日志）——本 ADR 的 D1 复用 0016 D1，D3 升级 0016 D3。
- 取代此前对话中散列的「L5/L6 多部门方向 / 部门插件缝 / 多租户部门拓扑」三份设想，合并为统一方向。
- 触发 **总控决策席**：是否开放「多租户 + 部门目录」未来阶段 gate。
- 触发 **安全边界席**：D1 多租户隔离、业务部外部平台凭证与合规、发布安全状态机。
