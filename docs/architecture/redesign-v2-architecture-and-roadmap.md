## 0. 总目标总结（几轮讨论收敛）

产品的真实定位不是「一个单人 AI 助手」，而是**商业化的多租户「AI 公司系统」**：

- **每个登录者 = 一个独立的 CEO**，拥有自己的商业范围、可选运营平台、可配置的公司部门。
- **部门是一等可配置实体，分两类**：
  - 业务型（对外）：业务部及其平台通道（抖音 / 小红书 / 微信 / 头条 / 番茄 / 起点）。
  - 职能型（对内）：人事部（增删员工、配角色技能）、行政部（ROI / token 产出比统计）、BI 部（可视化分析），可继续扩展财务 / 法务 / 客服。
- **地基**是已交付的受控自演进内核：Tool System v1.8 + Evolution Governor。
- **本次重设计补三件事**（此前设计缺的）：
  1. 独立的**数据统计 / 分析层**（此前 L6 经济层只是声明，无采集、无聚合、无展现）；
  2. **数据冗余治理与沉淀分层**（此前所有数据进单库 SQLite，公司成长后会膨胀、难归档、易冗余）；
  3. **面向公司成长的弹性模型**（部门 / 员工增删有聚合、有事件、有审计，不是硬改代码）。

---

## 1. 现有设计的核心缺口（重设计动机）

| # | 缺口 | 后果 |
|---|------|------|
| 1 | 无独立统计层，L6 经济层仅为文档声明 | 行政部 / BI 部没有数据可算，ROI / token 产出比无法产出 |
| 2 | 所有数据进单库 SQLite，无分层 / 归档 | 公司成长后库膨胀、查询变慢、历史无法廉价留存 |
| 3 | 部门 / 员工是硬编码概念，无弹性模型 | 增删部门 / 员工需改代码，违背「配置化公司」初衷 |
| 4 | 单脑 Orchestrator，无异步长时、无 correlation id | 视频长任务阻塞；一次「触发演进→失败」链路无法跨层追溯 |
| 5 | 派生数据与主数据混存，缺真相源 | 统计结果不可重算、易不一致 |

## 2. 分层架构表达（对齐唯一事实源）

> **编号约定（强制，不重排 L0–L6）**：本文档所有分层严格沿用 `knowledge/002_Product_Vision.md` 与 `knowledge/003_Architecture.md` 的 canonical 模型，不引入新 L 编号：
>
> ```
> L6 经济层: ROI / 成本 / 优化
> L5 公司层: 组织 / 部门 / 职责
> L4 工作流层: 任务拆解 / 编排 / 状态流转
> L3 工具层: 工具注册 / 路由 / 执行 / fallback
> L2 员工层: AI执行角色 / 员工能力 / 角色偏好
> L1 执行层: Task / Run / Status / History / Result
> L0 产品层: 用户界面 / 操作台 / 可视化
> ```
>
> 本重设计的三项新增内容以下列方式表达，均不重排编号：
> - **D 数据底座（横切层，不占 L 编号）**：追加写事件日志、correlation id、冷热分层沉淀，贯穿全层。
> - **统计与分析能力**：归为 **L6 经济层的度量/统计子集**（未来 gate），不另立 L1。
> - **公司/部门/员工弹性模型**：归为 **L5 公司层 + L2 员工层**（未来 gate），不另立 L2/L5。

```
L6 经济层(未来gate)        ROI / 成本 / 优化 · 统计与分析度量子集(指标/聚合/BI供给)
L5 公司层(未来gate)        组织 / 部门 / 职责 · 多租户 CEO · 部门目录(业务型+职能型)
L4 工作流层                任务拆解 / 编排 / 状态流转 · 异步长时编排
L3 工具层                  工具注册 / 路由 / 执行 / fallback · 平台集成网格(Connector) · 凭证库
L2 员工层(未来gate扩展)    AI执行角色 / 员工能力 / 角色偏好 · 技能装配
L1 执行层                  Task / Run / Status / Result · Evolution Governor · Tool System v1.8
L0 产品层                  操作台 · CEO 驾驶舱 · 部门视图 · 可视化看板
─────────────────────────────────────────────────────────
D  数据底座(横切·不占L编号) 追加写事件日志 · correlation id · 冗余去重 · 冷热分层沉淀 · 跨层可追溯
```

**关键变化（均不重排 L 编号）**
- **统计与分析能力归 L6 经济层度量子集（未来 gate）**：向上喂 CEO 驾驶舱 / 行政部 / BI 部，向下从 D 数据底座取事件，产出 ROI 反哺 L4 编排（经济闭环）。
- **D 数据底座横切全层**：任何写操作发领域事件 → 追加写事件日志（不可变，带 correlation id）→ 各层从日志派生所需数据。这是「统计能力」和「冗余治理」的共同前提。
- **部门目录归 L5 公司层（未来 gate）**，由 Manifest 驱动（能力集 / 工具类 / 质量线 / 输出通道 / ROI schema / 护栏 / 员工角色 spec），业务型与职能型共用同一缝。

## 3. 统计与分析能力设计（L6 经济层度量子集）

### 3.1 指标模型
| 维度 | 指标 |
|------|------|
| 产出 | 任务量、完成量、发布量（按平台）、内容产出计数 |
| 成本 | token 消耗、API / 算力成本、人工审批时长 |
| 效率 | token 产出比 = 产出计数 / token 消耗；任务平均耗时 |
| 经济 | ROI = 收益 / 成本（收益来自平台回流，见阶段 5） |

### 3.2 采集与聚合
- **采集**：L1 执行层的每次状态变更发领域事件（TaskCreated / StepExecuted / TokenConsumed / Published …），写入事件日志。
- **聚合**：定时 / 事件触发，按 **部门 / 员工 / 时间 / 平台** 维度 rollup，写入温层聚合表（物化视图）。
- **展现**：
  - 行政部 → ROI 看板（部门 / 员工 ROI、token 产出比、任务量）。
  - BI 部 → 多维可视化（趋势、对比、漏斗）。
  - CEO 驾驶舱 → 全局经济与健康概览。
- **反哺**：ROI 进入 L4 编排，驱动「哪个部门值得加资源」的经济闭环。

### 3.3 为什么这样设计
统计与分析能力**不碰主数据**，只读事件日志派生。派生数据可随时从真相源重算，所以「统计结果不一致 / 不可信」这类问题从架构上被消除。

## 4. 数据冗余与沉淀策略

### 4.1 冗余治理（避免无谓复制）
- **真相源唯一**：追加写事件日志不可变；聚合表、看板都是派生，**可重算 = 安全冗余**。
- **媒体资产内容寻址**：视频 / 图片按 hash 去重，同一素材只存一份（业务部多次引用不复制）。
- **跨部引用用 ID 不拷贝**：部门间共享业务对象（如一条文案）只存一份，其他部门引用其 ID。
- **反模式（明确禁止）**：不要为「每个部门各存一份相同业务数据」而做数据竖井。

### 4.2 沉淀分层（随公司成长不膨胀）
| 层 | 存储 | 内容 | 读写特征 |
|----|------|------|----------|
| 热 | 操作库（SQLite / 未来 Postgres） | 活跃 Task / Employee / 部门 / 配置 | 高频读写 |
| 温 | 分析库（聚合表 / 物化视图） | 周·月 ROI rollup、统计指标 | 读多写少，供行政 / BI |
| 冷 | 对象存储 / 列式归档（parquet） | 历史原始事件 + 媒体资产 | 廉价、可查、可重新聚合 |

- **沉淀规则**：热数据超过阈值（时间 / 量）自动沉降到温层；温层历史 + 原始事件定期归档到冷层。
- **可逆性**：冷层数据可重新聚合回温层（行政 / BI 需要历史对比时触发），不丢不锁。
- **演进记录同样沉淀**：EvolutionLog / 决策 / 回滚记录进入冷层，审计链长期可查。

## 5. 面向公司成长的弹性模型

- **部门增删**：Manifest 注册 / 注销 + `company_topology` 编辑。实例级（某 CEO 启用 / 停用已有部门）= 仅配置 + 入审计；类型级（冒出新部门类型，如「电商」）= 走 gate + ADR。
- **员工增删**：Employee 聚合根 + 事件驱动；人事部操作（增删 / 分配角色 / 配技能）全部入审计日志。
- **多租户预留**：聚合根带 `tenant_id` 作用域；现在单用户仅预留，未来隔离落地时加列 + 中间件注入，不重写。
- **公司 = topology 子集**：每个 CEO 的公司是其从部门目录挑选的子集，互不可见。

## 7. 风险与权衡（明确说出来）

- **多租户 vs 本地零依赖**：你想要的「每人拼自己的公司」与 MVP「单文件 SQLite、零外部服务」互斥。正确做法 = 分阶段、先预留后实现，不在当前 gate 硬上。
- **统计与分析能力前置 vs 范围蔓延**：阶段 1 提前做统计是对的（它是行政 / BI / 经济的前提），但要守住「只派生、不改主数据」，避免做成另一个 god-module。
- **沉淀分层增加运维面**：热/温/冷三套存储 + 归档任务，是一笔持续运维成本；对个人 MVP 阶段可先只做「事件日志 + 温层聚合」，冷层留到阶段 5。
- **治理开销复利**：部门类型一多，每新增类型走 gate+ADR 仍可能反噬交付——用「类型级走 gate / 实例级仅配置」分流缓解。
- **watchmen 问题仍在**：系统自己改自己（Evolution Governor）的信任面，在所有阶段都保持「生产变更需人工批准」，不解除自动改码禁令。
