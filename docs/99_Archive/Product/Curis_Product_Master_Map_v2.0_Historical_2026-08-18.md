## 1. Curis 的顶层产品定义

### 1.1 一句话

> Curis 是一间可被普通用户直接使用的 AI 公司：用户从 CEO 工作台说出目标，Curis 帮他形成业务、员工和数字办公室，成熟的 AI 产品在办公室内工作，公司再根据真实结果不断调整和成长。

### 1.2 用户真正感受到的价值

```text
我说出想做的事
→ Curis 帮我组成一家公司来做
→ 我知道谁负责什么
→ 每项业务有自己的工作空间
→ AI 在我离开后继续工作
→ 有问题时我能找到具体员工并介入
→ 我看到真实结果和依据
→ 公司从结果中变得更强
```

### 1.3 固定框架与开放空间

| 固定的 Company OS | 开放的 Workspace |
| --- | --- |
| CEO / 用户 | 业务自己的主工作面 |
| Company | 业务对象和工作对象 |
| CEO Assistant | 专业 Agent、工具和自动化组合 |
| 组织、部门、岗位、员工 | 业务自己的布局和导航 |
| Business / Commitment / 业务目标 | 业务自己的节奏、阶段和视图 |
| Capability / 公司资源 | 业务自己的输入、输出和数据窗口 |
| 资料库、知识、会议、决策 | 业务自己的外部结果和反馈方式 |
| 公司级目标、结果、复盘和变化 | 业务自己的用户介入点 |

固定的是关系、责任和公司事实；开放的是每个业务如何工作。

产品层对 Workspace 的最简单理解是：

> Workspace = 专家团队 + 专业工作环境 + 自动协作方式。

这句话是普通用户的入口表达，不把“专家团队”物化为新的组织对象；成员、责任、交接和结果仍回到现有 Employee、RoleSlot、Handoff 和 Outcome 关系。

## 2. 一级产品框架

Curis 保留六个主工作区域，加一处左下角用户头像菜单。全局 Assistant、搜索、最近工作、通知和运行提醒是跨层能力，不另占一级导航。

```text
Curis Desktop
├── 首页 / CEO 工作台 公司今天发生了什么，我需要做什么
├── 业务空间         每个业务如何独立工作并产生结果
├── 组织中心         公司已经有哪些人，谁负责什么
├── 人才市场         发现和扩展公司外部能力
├── 资料库           Curis 能读取什么，过去产生了什么
└── 会议             公司如何讨论、决定和跟进

左下角用户头像
└── 公司与个人设置、资源维护、帮助与退出
```

### 2.1 一级结构总表

| 一级区域 | 用户心智 | 核心问题 | 不应该变成 |
| --- | --- | --- | --- |
| 首页 / CEO 工作台 | 我的公司首页 | 今天发生了什么？现在最重要的事是什么？ | 数据大屏、任务列表或固定秘书侧栏 |
| 业务空间 | 我的业务办公室 | 这项业务正在怎样工作、交付和获得结果？ | 统一 Runtime 页面、通用看板 |
| 组织中心 | 我的 AI 公司 | 公司已经有哪些人？谁负责什么？怎样组建和调整团队？ | 平级 Agent 目录、空部门管理器 |
| 人才市场 | 公司外部的能力生态 | 我可以发现、招聘或引入什么？ | 公司员工列表、技术设置后台 |
| 资料库 | 公司与外部资料 | Curis 能读取什么？员工知道什么？过去产生了什么？ | 孤立知识库或文件仓库 |
| 会议 | 公司讨论和决定 | 哪些事情需要讨论、决定和回看？ | 会议记录存档或决策按钮集合 |
| 左下角用户头像菜单 | 公司与个人维护 | 账户、公司资源、通知、主题和数据如何管理？ | 日常工作入口、人才市场的替代入口 |

### 2.2 CEO 工作台

CEO 工作台是默认首页，也是公司级对话入口。它回答“现在应该关注什么”，而不是罗列所有模块。

对于已经建立且正在运行的公司，首屏默认由四类内容组成：

1. **公司简报**：最近一段时间公司最重要的结果、变化和趋势。
2. **今日变化**：业务、员工、Workspace、外部结果和资源的新增、完成、异常或偏移。
3. **问题处理**：需要用户补充、确认、接管、拒绝或决定的事项。
4. **CEO Assistant 对话**：用户可以直接询问、委派、创建业务、调整方向或请求解释。

首屏的主动作只有一个；首次建立公司、尚无业务或存在阻塞时，由第 17 节的首次打开状态接管首屏，不强行展示空的运营简报：

> 继续今天最重要的事，或直接告诉 Assistant 你想做什么。

辅助入口：

- 进入某个业务空间。
- 查看某名员工正在做什么。
- 打开一项结果或问题。
- 查看一场会议或待决定事项。
- 搜索公司中的业务、员工、资料和历史。

CEO 工作台不默认显示：

- Runtime 状态机。
- 全量 Task / Workflow / Run 列表。
- 所有 Provider、Model、Skill、MCP 清单。
- 空的部门、岗位或能力卡片。
- 未经真实数据支持的指标和趋势。

### 2.3 组织中心

组织中心展示公司关系，不要求用户从零设计组织。

核心内容：

- 公司组织关系：CEO、CEO Assistant、部门、岗位、员工和汇报关系。
- 部门：稳定的责任聚合和共享能力，不是第一天必须创建的容器。
- 业务：公司正在经营的价值方向、目标、投入和结果。
- 员工 / 专家：一个具有公司身份的专家 / Agent，持续承担一项或多项责任。
- 招聘：把 Coze Agent、Workbuddy 专家、Codex、Claude Code、本地 Agent 或职业模板变成公司的员工。
- 组队：从公司已有员工中选择成员，组成某个 Workspace 的专家团队；组队不等于再次招聘。
- 组织建议：当责任重复、工作量增加或能力共享达到条件时，Assistant 建议成立或调整部门。

组织中心的默认阅读顺序是：

```text
公司 → 业务 → 责任 → 员工 → 当前工作 → 结果
```

而不是：

```text
Agent → Model → Tool → Prompt → Workflow
```

部门 / Shared Service 的出现必须由真实工作触发，而不是由创建流程强制生成。Assistant 只有在发现以下至少一项持续事实后，才提出组织建议：

- 两个或以上岗位反复承担同类责任，需要共享知识、能力或检查标准。
- 多个业务或 Workspace 反复依赖同一组员工和能力，分散管理已经造成等待、冲突或重复成本。
- 某项长期责任已经需要独立负责人、容量和复盘节奏。

建议卡必须说明“为什么现在出现、会聚合哪些责任和成员、会影响哪些业务、需要 CEO 确认什么”。形成部门不会自动改变已有岗位、员工或 Handoff；责任变化必须另有明确的变更与交接记录。部门合并、拆分或解散时保留员工身份、工作历史、Outcome 和未关闭责任，不得用删除组织节点伪造完成。

### 2.4 业务空间

业务空间是所有业务 Workspace 的入口。这里先看业务和办公室的关系，再进入具体办公室。

业务空间首页需要表达：

- 业务要创造什么价值。
- 当前有哪些 Workspace。
- 谁负责这些 Workspace。
- 最近的结果和反馈。
- 当前健康、风险和下一检查点。
- 进入办公室或继续与负责人对话。

业务空间不把所有业务压成同一个卡片字段。卡片只提供跨业务导航所需的最低共同信息，具体业务内容进入各自 Workspace。

### 2.5 人才市场

人才市场是公司外部的能力生态，负责“发现和扩展”，不是组织中心的员工列表，也不是设置里的技术维护面。它可以聚合成熟产品和开放生态中的：

- 专家 / Agent：产品、研发、设计、内容、增长、研究、运营等职业人才。
- 技能：专业 Skill、工作方法、Prompt / Instruction 和可复用实践。
- 连接器：GitHub、Figma、Google Drive、Notion、平台 API、MCP 等。
- 职业模板：已经组合过的岗位责任、能力、知识和工作方式起点。
- 外部能力：Tool、Knowledge、Agent、MCP 及其他可验证的工作能力。

人才市场的默认结构可以是：

```text
[专家] [技能] [连接器]
搜索 / 分类 / 推荐 / 已安装
```

产品边界必须清楚：

| 用户动作 | 人才市场负责 | 后续落点 |
| --- | --- | --- |
| 发现专家 / Agent | 展示适合的职业方向、能力、示例工作和来源 | 招聘后进入组织中心，成为公司员工 |
| 发现技能 | 展示适合的岗位、依赖和示例效果 | 安装 / 引入后成为公司可用技能，再分配或自动装配给员工 |
| 发现连接器 | 展示连接范围、可做什么和风险 | 安装后到设置授权，成为公司资源，再授权给员工 / Workspace |
| 发现职业模板 | 展示岗位能力组合和适用场景 | 招聘或应用后形成公司员工 / Workspace 起点 |

三个职责必须分开：人才市场负责发现和扩展；设置负责连接、授权、维护和撤销；组织中心负责公司已经拥有谁、谁负责什么；业务空间负责这些员工真正在哪里工作。市场项目在未招聘、未安装或未授权前，不得直接出现在公司员工、公司能力或 Workspace 可运行资源中。

人才市场不要求 Curis 自建封闭 Skill Store。它优先聚合外部 Skill、MCP、Tool、Agent、Prompt / Instruction、工作方法、Knowledge 和 Curis 自有 Skill，再由 Curis 组合成职业能力和可招聘的人才模板。

### 2.6 资料库

资料库是公司与外部信息世界的统一入口，不是简单文件管理器。它回答：

> Curis 能读取什么、员工知道什么、过去产生了什么、哪些东西可以再次使用？

资料库至少包含三类资料来源：

| 来源 | 典型内容 | 产品必须支持 |
| --- | --- | --- |
| 本地资料 | 文件、文件夹、用户导入资料、本地知识库 | 读取、文件夹索引、搜索、权限和来源 |
| 外部资料 | 云盘、Notion、Obsidian、GitHub、网页、外部知识库和其他数据源 | 连接、授权、同步 / 索引、引用和权限 |
| 公司产生 | 研究报告、产品文档、内容、代码成果、会议资料、数据分析、经验和知识沉淀 | 自动沉淀、版本、来源追踪、复用和过期管理 |

资料必须能够回答：

- 它来自哪里、何时读取或产生？
- 谁可以查看、引用和修改？
- 哪个员工、Workspace 或业务正在使用？
- 是否被结果、会议或决定引用？
- 是否过期、冲突、未经确认或需要重新同步？

资料库把外部资料带进公司，也把公司工作结果沉淀回可复用的资料；它不是把所有文件丢在一起，也不替代 Workspace 自己的工作对象。

### 2.7 会议

会议是把事实、分歧和选择变成责任与行动的工作面，不是会议记录存档。Curis 保留两个上下文：

| 会议上下文 | 处理什么 | 主要参与者 | 结果回到哪里 |
| --- | --- | --- | --- |
| Company Meeting | 跨业务 Commitment、公司方向、资源取舍和 CEO 决策 | CEO、CEO Assistant、相关业务负责人和员工 | Company、Business、Commitment、Organization 或 Capability |
| Workspace Meeting | Cycle 内的方案、质量、交接、局部阻塞和工作方式调整 | 当前 Workspace 员工、相关能力和用户 | Cycle、Work object、Workspace；影响公司时再升级 |

两级会议都遵循：

- 准备：Assistant 收集当前 Commitment、Cycle、Evidence、历史和分歧。
- 讨论：参与者提出事实、方案、风险和不同意见。
- 决定：继续、调整、暂停、扩大、替换、拒绝或升级。
- 跟进：产生责任、后续 Cycle / Work object、结果和回看时间。

Workspace Meeting 只有在影响 Commitment、跨 Workspace 资源、公司方向或外部承诺时才升级为 Company Meeting。会议不能凭空生成结果，必须引用来源工作和 Evidence；结束后必须回到业务、Workspace、资料库或 Decision 的后续工作。

### 2.8 左下角用户头像菜单：公司与个人设置

设置不再作为主工作区一级导航。它属于用户头像菜单，因为它回答的是“我和这家公司如何维护”，而不是“公司今天要做什么”。

头像菜单至少包含：

- 当前用户与个人偏好：姓名、头像、语言、主题、通知和快捷键。
- 当前公司：公司资料、公司目标、公司级规则和未来的公司切换。
- 公司资源：已连接的模型、Agent Provider、Tool、Skill、MCP、外部连接和 Knowledge 来源。
- 权限与数据：数据范围、外部动作确认、隐私、导出和本地数据管理。
- 运行与成本：连接健康、能力容量、成本预算、后台运行状态和诊断。
- 帮助与反馈：帮助、问题反馈、版本信息和退出。

这些内容仍然完整存在，但默认不要求用户先打开设置。用户可以从具体工作上下文直接进入相关资源：

- 工作缺少搜索能力 → 直接打开“接入搜索”并回到原工作。
- 员工需要更换执行 Agent → 从员工详情进入“更换执行能力”。
- Workspace 缺少发布连接 → 从启动检查进入“连接发布平台”。
- 公司需要调整通知 → 从头像菜单维护通知规则。

人才市场负责发现和扩展；设置里的资源负责连接、授权、维护和撤销。它们在日常对话和 Workspace 中按需出现。用户不应为了完成普通工作先浏览技术设置。

设置仍然负责维护：

- 模型与模型提供商。
- Agent Provider 与外部 Agent。
- Tool / 外部服务 / 浏览器 / 文件能力。
- MCP。
- 已引入的 Skill 及其版本、依赖和影响。
- 权限、数据范围、副作用和用户确认规则。
- 通知、主题、账户、本地运行和数据管理。

### 2.9 跨层能力

以下能力不占一级导航，但必须随时可用：

- 全局 CEO Assistant 对话（Global Assistant Runtime 只负责跨页面承载，不形成第二个 Assistant 身份）。
- 全局搜索和最近访问。
- 通知与待处理队列。
- 正在运行的工作、等待用户和需要审批的事项。
- 资源健康、连接失效、成本异常和容量不足提醒。
- 当前上下文指示：公司 / 业务 / Workspace / 员工 / 工作对象。
- 运行中的长任务和需要用户介入的事项。
- 返回原位置的上下文导航。

原则：

> 主导航负责稳定地表达“我在哪里”；对话和搜索负责快速表达“我想做什么”；头像菜单负责维护“我和公司怎样运行”。

### 2.9.1 覆盖审计：简洁没有删掉什么

对普通用户最常见的任务逐项检查后，能力归属如下：

| 用户任务 | 主要入口 | 必须覆盖的能力 | 是否需要一级导航 |
| --- | --- | --- | --- |
| 开始公司 / 新业务 | CEO 工作台对话 | 意图理解、方案预览、确认、第一 Workspace | 否，首页已覆盖 |
| 看公司今天怎样 | CEO 工作台 | 简报、变化、问题、结果、待决定事项 | 是，首页 |
| 找到谁在负责 | 组织中心或当前 Workspace | 岗位、员工、汇报、当前工作、历史 | 是，组织中心 |
| 开始一项业务工作 | 业务空间 / Workspace | 独立 UI、工作对象、员工、能力、结果 | 是，业务空间 |
| 处理具体问题 | 当前问题、员工或工作对象 | 对话、局部修改、恢复、继续 | 否，跨层能力 |
| 发现和扩展公司能力 | 人才市场 | 专家、技能、连接器、职业模板、来源和安装 / 招聘 | 是，人才市场 |
| 查看公司资料和积累 | 资料库 | 本地资料、外部资料、公司成果、索引、引用和复用 | 是，资料库 |
| 讨论和做决定 | 会议或 CEO 工作台问题卡 | 事实、方案、决策、执行反馈 | 是，会议 |
| 接入模型/Agent/工具 | 人才市场 → 设置，或上下文缺口入口 | 发现、导入、验证、授权、替换、回退 | 人才市场发现；设置后置维护 |
| 查看后台运行和审批 | CEO 工作台通知/问题处理 | 进度、等待、审批、异常、恢复 | 否，跨层能力 |
| 查看成本和连接健康 | CEO 工作台提醒或头像菜单 | 成本、容量、健康、诊断 | 否，跨层能力 |
| 修改个人偏好或退出 | 左下角用户头像 | 主题、通知、账户、帮助、退出 | 否，头像菜单 |

结论（原 v2.0 复审）：没有删除这些用户需要的能力，只是把“日常工作”和“维护系统”分开；设置从一级导航下沉后，反而更符合普通桌面 App 的使用习惯。

### 2.10 从一级产品反推能力

后续产品规划采用固定顺序：

```text
一级产品
→ 用户要完成什么
→ 页面必须提供什么
→ AI 自动做什么
→ 最后反推需要哪些底层能力
```

不再先列 Model、Provider、Tool、Skill、MCP 或数据能力，再寻找它们应该放在哪个页面。任何新增底层能力都必须回答：

> 它服务哪个一级产品、哪个用户动作？

| 一级产品 | 用户动作 | 页面必须提供 | AI 自动做什么 | 最后反推的能力 |
| --- | --- | --- | --- | --- |
| 首页 / CEO 工作台 | 看公司、处理问题、决定下一步 | 跨业务状态、简报、问题、待处理、真实结果 | 聚合、解释、排序、提出建议并跟进 | Assistant、Truth、结果分析、通知和决策回流 |
| 业务空间 | 让团队持续完成一项业务工作 | Workspace、专家团队、上下文、自动协作、局部介入、结果回流 | 委派、流转、恢复、汇报和复盘 | 员工接入、上下文、工作对象、Handoff、结果契约 |
| 组织中心 | 招聘员工、看关系、调整责任 | 员工详情、岗位、部门、业务归属、汇报关系和当前团队 | 推荐员工、岗位能力和组织调整 | 员工身份、组织关系、招聘确认和历史 |
| 人才市场 | 发现专家、技能、连接器并扩展公司能力 | 搜索、分类、来源、示例、安装 / 招聘 / 引入入口 | 推荐适合岗位和业务的能力组合 | 市场目录、导入适配、职业模板和能力组合 |
| 资料库 | 找资料、引用资料、沉淀结果 | 本地 / 外部 / 公司产生、索引、搜索、权限、引用和来源 | 读取、归类、引用、沉淀和提醒冲突 | 文件读取、连接、索引、权限、来源追踪和知识沉淀 |
| 会议 | 围绕事实讨论、决定并回到执行 | 多人讨论、资料引用、结论、决定、责任和执行反馈 | 准备材料、召集参与者、提炼分歧和跟进 | 对话协作、引用、Decision、责任回流和通知 |

无法归属到一级产品和明确用户动作的底层能力，默认不进入产品开发规划；技术配置只有在设置或上下文缺口中有明确维护动作时才进入实现范围。

### 2.11 四个 CEO 意图入口与六个 Desktop 工作区域

“四个 CEO 入口”表达用户想解决哪类经营问题；“六个主工作区域”表达 Desktop 把这些问题放在哪里。两者不是两套导航，也不要求一一对应：

| CEO 意图入口 | 主要回答 | Desktop 工作区域 | 说明 |
| --- | --- | --- | --- |
| 经营 | 公司现在发生了什么，下一步要决定什么 | CEO 工作台 | 聚合 Truth、Assistant、问题、Decision 和 Operating Day |
| 业务 | 我正在经营什么价值方向 | 业务空间 | 查看 Business、Commitment、投入、结果和下一步 |
| 公司 | 谁负责什么，公司能力是否够用 | 组织中心 + 人才市场 + 头像菜单 | 组织中心看责任，人才市场扩展能力，头像菜单维护资源和权限 |
| 工作空间 | 这项业务具体怎样工作 | 业务空间 → 独立 Workspace | 业务空间是入口，Workspace 是开放的独立应用 |

人才市场、资料库和会议是必要的支持工作区域：人才市场承接外部能力发现和扩展，资料库承接资料、Outcome 和学习，会议承接需要讨论的分歧与 Decision；它们不需要被硬塞进“四个 CEO 入口”，也不因此降级为可删除的附属页面。

因此最终导航原则是：

> 四个入口保持 CEO 心智简单，六个工作区域保证完整产品可用；全局 Assistant、Truth、Decision、Change 和返回路径贯穿二者。

## 3. 普通用户主路径

### 3.1 第一次打开：从一句话开始

```text
打开 Curis
→ CEO Assistant 介绍自己
→ 用户说出想做的事
→ Assistant 追问最少必要信息
→ 生成第一项业务与最小 Workspace 工作预览，必要时给出最小团队建议
→ 用户确认目标、第一步边界和是否立即开始
→ 进入第一间 Workspace
→ Workspace 以真实工作方式开始运行
```

用户第一次不需要：

- 先命名部门。
- 先选择 Provider。
- 先编排 Workflow。
- 先配置全部员工。
- 先理解 Simulation 或 Runtime。

如果缺少能力，系统给出自然语言的启动检查：

> “内容研究可以开始；发布到平台还缺少连接。你可以现在接入，或先用人工反馈继续。”

### 3.2 每天打开：看公司，不看系统

```text
打开 Curis
→ CEO 工作台简报
→ 查看今日变化
→ 处理少量高影响问题
→ 进入一个业务 / 员工 / 结果
→ 对话、确认、委派或局部修改
→ 回到 CEO 工作台
```

CEO 不需要逐个检查每个办公室。Assistant 汇总变化，只在需要用户判断时升级。

### 3.3 开始一项新业务

```text
用户：“我要做小红书。”
→ Assistant 识别业务目标、受众、节奏和期望结果
→ 推荐内容增长 Workspace 起点
→ 生成业务、组织建议、员工和能力缺口
→ 展示“会做什么 / 需要什么 / 什么时候问我”
→ 用户确认或修改
→ 形成可运行的内容办公室
```

### 3.4 委派复杂工作

```text
用户表达目标
→ Assistant 判断由哪个业务 / Workspace / 员工负责
→ 给出简短的工作预览
→ 用户确认高影响动作
→ 员工开始工作
→ 页面外继续运行
→ 通知进度、问题或成果
```

### 3.5 局部介入

```text
发现某个环节不满意
→ 打开该环节负责的员工或工作对象
→ 直接对话并说明修改
→ 只重做当前环节
→ 下游按新结果继续
→ 保留旧版本、修改原因和结果差异
```

示例：

> “这篇文案重写，保留选题和品牌语气，改得更适合新用户。”

系统不应因此重跑选题、素材、发布和整条业务工作。

### 3.6 公司成长

```text
工作结果持续积累
→ Assistant 发现趋势、风险和重复责任
→ 建议成立部门、复用员工、替换能力或改造 Workspace
→ 用户查看影响、成本、风险和预期结果
→ 用户确认高影响变化
→ 新版本开始工作
→ 继续观察和复盘
```

### 3.7 渐进式成立公司

用户不需要先完成一套“公司注册 + 组织设计 + 能力配置”流程，才能获得第一次工作结果。Curis 应把公司成立拆成两件事：

```text
对用户：先确认想做什么、第一项业务和第一步高影响边界
对系统：只物化让第一项工作合法开始所需的最小 Company / Business / Employee / Capability / Workspace 事实
```

后续部门、岗位、员工数量、能力组合和 Workspace 细节，随着真实工作需要逐步显现。用户可以先看到：

- 这个办公室会帮我完成什么。
- 第一项工作会产生什么结果。
- 哪些事情会自动做，哪些事情会问我。
- 现在缺什么，以及人工回退是什么。

只有当某项变化会影响方向、成本、权限、外部副作用或责任归属时，才要求用户确认。这样“公司”不是一次表单提交出来的空壳，而是在第一项真实工作中逐步变得完整。

## 4. Company 模型

### 4.1 Company 是用户正在经营的整体

Company 包含：

```text
Company
├── 方向与目标
├── CEO 与 CEO Assistant
├── 组织与员工
├── 业务与 Workspace
├── 公司能力与连接
├── 知识、成果、模板和经验
├── 会议、决策和承诺
├── 外部结果、数据和反馈
└── 下一轮调整与成长
```

Company 不是单纯的 Tenant、数据库根对象或空的组织目录。

### 4.2 Company 的三个时间面

| 时间面 | 用户要知道什么 |
| --- | --- |
| 现在 | 公司今天发生了什么、谁在工作、哪里需要我 |
| 过去 | 哪些决定、成果、知识和经验已经积累 |
| 下一步 | 接下来做什么、需要哪些资源、有什么变化建议 |

CEO 工作台、资料库、会议和组织中心分别提供不同的阅读角度，但共享同一公司上下文。

### 4.3 公司默认组织

第一天的最小组织：

```text
CEO
└── CEO Assistant（Company-level 第一位 AI 员工 / Chief of Staff）
    └── Professional AI 员工
        └── Workspace RoleSlot / Workspace AI 责任
```

CEO Assistant 直接向 CEO 汇报，负责公司级简报、请求分流、专业员工协调、交接回收、异常升级和一天的收束；它不是一个普通 Workspace 员工，也不是一个 Provider 配置卡。每个 Company 只能有一个当前 CEO Assistant 身份，替换其执行能力不会替换身份；替换身份本身是公司级高影响变化，必须由 CEO 确认。

部门只有在责任重复、协作稳定或共享能力形成后才建议建立。组织是经营结果，不是注册表单。

### 4.4 Business 与 Workspace

| 对象 | 业务含义 | 用户理解 |
| --- | --- | --- |
| Business | 一项价值方向、投入选择和外部结果 | 我在经营什么 |
| Commitment | 公司在这项业务上明确要交付或验证的结果、范围和责任 | 这轮答应要做到什么 |
| Workspace | 为这项业务装配的数字办公室 | 这项业务怎样工作 |
| RoleSlot | Workspace / Blueprint / Stage 中的具体责任位置 | 这一环节由谁以什么责任工作 |
| Cycle | Workspace 中一段有边界的工作轮次 | 这一轮具体怎么推进 |
| Department / Shared Service | 因重复责任或共享能力形成的组织聚合 | 哪些人和能力应该长期一起工作 |
| Employee | 在办公室中承担责任的人 | 谁在负责 |
| Outcome | 工作和外部世界产生的结果 | 做成了什么 |
| DecisionPacket | Assistant 为 CEO 准备的事实、选项和影响包 | 现在需要我判断什么 |
| Acceptance | CEO 对结果是否满足承诺的判断 | 这次结果是否算数 |

一个 Business 可以拥有多个 Workspace；一个 Workspace 服务一个明确的业务责任范围，但不能代替业务目标和经营判断。产品层默认把 Workspace 读成“专家团队 + 专业工作环境 + 自动协作方式”，而不是要求用户理解 RoleSlot 或 Cycle。

### 4.5 唯一关系图

后续页面、API、Workspace 和 Provider 设计都以这条关系为基准：

```text
Company
├── CEO
│   └── CEO Assistant（Company-level 第一位 AI 员工）
│       └── Professional AI Employees
├── Organization
│   ├── Department / Shared Service (按需形成)
│   │   └── Position → Employee
│   └── Position → Employee (第一天可直接承担)
├── Business
│   ├── Commitment
│   └── Workspace
│       └── Cycle → Handoff → Work object → Outcome / Evidence
├── Knowledge / Memory / Asset
└── Meeting
    ├── Company Meeting → Company Decision
    └── Workspace Meeting → Local Adjustment / Escalation

Commitment ←────────── Cycle
RoleSlot / Stage ─────→ Handoff ─────→ Employee / CEO
RoleSlot ──────────────→ Capability Supply Check ──→ Capability / Binding
Employee ──────────────→ Executor / Capability
Commitment + Outcome / Evidence ──→ Acceptance ──→ Meeting / Decision
Truth / Exception / Acceptance ────→ DecisionPacket ──→ CEO Decision
Decision ────────────→ Business / Organization / Capability / Workspace / Commitment 的变化
变化 ────────────────→ Company 的下一轮 Operating Loop
```

关系规则：

- Position 定义组织中的长期责任；RoleSlot 定义某个 Workspace / Blueprint / Stage 的具体责任位置；AIEmployee 是可被找到、对话和复用的稳定工作身份；Executor 只是当前执行方式。一个 AIEmployee 可以承担多个 RoleSlot，但每个 RoleSlot 的输入、输出、容量和 Handoff 必须分别记录，不能互相替代。
- Business 定义价值方向；Commitment 定义本轮要交付或验证的结果；Workspace 是持续的办公室；Cycle 是办公室内有边界的一轮工作，并指向它服务的 Commitment；Handoff 记录责任如何被接住；Work object 是具体执行事实。不能把其中任一层压成同一个对象，也不能因为新 Commitment 就复制一间 Workspace。
- Outcome / Evidence 先属于产生它的 Workspace；只有经过确认、复用或沉淀，才进入资料库或决策上下文。
- Acceptance 是对结果是否满足 Commitment 的判断，不等于工作完成，也不等于下一步 Decision。
- DecisionPacket 是 Assistant 基于事实、Evidence、未知、选项、影响和回退条件准备的判断材料；它可以建议但不能替 CEO 作出 Decision。Decision 是 CEO 的有效选择，必须回写受影响对象。
- Handoff 不是通知、聊天或页面跳转；只有接收方明确接住输入和责任，才算交接完成。
- Department / Shared Service 只有在责任重复、协作稳定或能力共享形成后才物化；它不能成为第一天的空容器，也不能替代 Business 或 Workspace。
- Capability 被员工或 Workspace 使用，但不拥有业务目标；Provider 也不能直接成为 Company 的事实来源。
- RoleSlot 先提出能力需求，Capability Supply Check 只判断当前供给、权限、风险和成本是否满足；检查通过不改变 CapabilityBinding、Employee、RoleSlot 或 Workspace 的生命周期，授权和激活仍需分别发生。
- Meeting / Decision 解释和改变公司关系，但不取代来源工作，也不凭空生成结果。
- CEO Assistant 可以创建或连接这些关系，但不能在关系图之外发明一套隐形对象层级；Global Assistant Runtime 只是跨页面承载基础设施，不是第二个 Assistant 或第二套员工真相。

## 5. Workspace 模型

### 5.1 定义

> Workspace 是 Curis 公司中的数字办公室，可以内嵌成熟 AI 产品或自定义业务工作方式；它共享公司上下文和组织资源，但拥有自己的 UI、工作对象、节奏、自动化和结果窗口。

普通用户可以把它理解为：

> 专家团队 + 专业工作环境 + 自动协作方式。

专家团队只是 Workspace 中现有员工的组合与工作视图，不是新的一级导航、系统对象或独立生命周期。

### 5.2 Workspace 的四个边界

| 边界 | Workspace 自己决定 | Company 统一提供 |
| --- | --- | --- |
| 工作方式 | 阶段、队列、视图、协作和自动化 | 目标、责任、权限、员工身份和公司规则 |
| 工作对象 | 内容、代码、研究条目、行情、客户会话等 | 结果、状态、异常和反馈返回契约 |
| 能力组合 | 哪些 Agent、Tool、Knowledge 参与 | 公司授权、数据范围、成本和副作用边界 |
| 用户介入 | 哪个环节需要审查、修改、接管或批准 | 高影响动作的确认和公司级决策 |

### 5.3 Workspace 不是统一 Runtime 页面

所有 Workspace 只共享以下最小公司契约：

```text
能知道自己属于哪家公司和哪项业务
能知道哪些员工承担哪些责任
能使用被授权的公司能力和知识
能接收用户目标、约束和指令
能返回状态、成果、数据、异常和用户介入点
能把重要结果交回 Company Operating Loop
```

它们不必共享：

- 页面布局。
- 顶部指标。
- 阶段数量。
- 工作对象。
- 结果展示方式。
- 具体 Agent 协作形式。
- 日历、看板、编辑器或研究面板的比例。

### 5.4 Workspace 的用户可见生命周期

用普通用户语言表达为：

```text
想法
→ 方案
→ 准备开始
→ 正在工作
→ 结果回收
→ 复盘改造
```

内部可以拥有更细的配置、权限、验证和运行状态，但不把内部状态直接升级为一级用户任务。

#### 5.4.1 责任交接契约

Workspace 的阶段不是靠页面顺序自动推进，而是靠显式 Handoff 让下一责任主体真正接住工作。每次交接至少说明：

| 交接内容 | 用户要知道什么 |
| --- | --- |
| From / To | 谁交给谁，接收方是员工、Workspace、CEO 还是外部结果窗口 |
| Input | 交接了哪些目标、约束、资料、版本和未解决问题 |
| Expected Output | 接收方要产生什么结果或明确反馈 |
| Acceptance / Checkpoint | 何时由谁检查是否接住，检查条件是什么 |
| Next Step | 接住后继续什么；拒绝、超时或失败回到哪里 |

用户可见的交接语言是：

```text
准备交给某人 → 对方已接收 → 正在处理 → 结果交回 / 需要补充 / 被退回
```

“已发送”“通知已读”或“页面打开”都不代表责任已经转移。CEO Handoff 是把需要用户判断的事项交回 CEO，不等于 CEO 已接受结果；Acceptance 仍必须单独发生。

### 5.5 三类示例 Workspace

#### 研发 Workspace

参考 Codex、Claude Code、ChatGPT 和 Workbuddy 的成熟协作模式。

产品层先显示“我的研发团队”：

```text
团队：ChatGPT（产品负责人）+ Codex（开发工程师）
      + Claude Code（架构审查）+ Workbuddy（产品设计 / 协调）
工作环境：对话 + 文件 + Git + 代码 + 终端 + 测试 + Review
自动协作：需求 → 方案 → 开发 → 审查 → 修改 → 交付
```

用户看到的是谁正在做什么、下一步交给谁、哪里需要自己；Provider、Executor 和内部责任位置只在高级详情中出现。

可能包含：

- ChatGPT：需求理解、产品分析、方案讨论。
- Codex：文件修改、代码实现、测试和并行开发。
- Claude Code：架构分析、代码审查、问题排查。
- Workbuddy：跨任务协调、进度汇总、通知和审批。
- 文件、Git、终端、测试、Review、成果和变更记录。

用户看到的是一个研发办公室，不是四个 Provider 配置页。用户可以说：

```text
“@ChatGPT 分析这个需求。”
“@Codex 按方案实现。”
“@Claude Code 审查这一版。”
“@全体讨论风险。”
```

这些调用都回到研发 Workspace 的项目上下文、岗位责任和结果流。

#### 内容 Workspace

可能包含：

- 选题、研究、素材、草稿、版本和审核。
- 文案、视觉、发布、互动和复盘员工。
- 平台适配、发布回执、评论/私信/提及、线索和数据反馈。
- 内容日历、结果比较、品牌知识和可复用模板。

内容 Workspace 不应被做成研发 Workspace 的换色版本。

#### 投资 Workspace

可能包含：

- 行情、自选、研究问题和来源。
- 研究 Agent、数据分析 Agent、风险审查和报告生成。
- 组合、假设、交易记录、风险边界和决策复盘。
- 数据新鲜度、来源和用户确认。

投资 Workspace 的核心不是“自动下单”，而是研究、判断、风险和决策连续性；任何外部动作都必须有明确确认边界。

## 6. 空间搭建模型

### 6.1 定义

> 空间搭建不是创建页面，而是把一个业务想法转换成一个可以工作的数字办公室。

空间搭建要同时回答：

- 这项业务要创造什么结果？
- 谁负责哪些工作？
- 需要哪些能力和知识？
- 工作怎样从输入走到输出？
- 哪些结果来自外部世界？
- 哪些地方需要用户介入？
- 缺少能力时怎么开始或人工回退？
- 以后怎样复用和改造？

### 6.2 普通用户创建空间

普通用户只需描述意图，Assistant 负责形成第一版空间方案：

```text
用户：“我要做小红书，大部分工作希望 AI 完成。”
↓
Assistant 询问少量必要信息：目标人群、内容方向、发布频率、品牌资料和用户介入边界
↓
生成空间预览：业务目标、岗位、能力、知识、工作方式、结果和需确认事项
↓
用户修改或确认
↓
启动检查：哪些可以立即运行、哪些需要接入、哪些可人工回退
↓
进入小红书办公室
```

用户看到的预览不是技术蓝图，而是：

```text
这个办公室会帮你做什么
谁会负责
需要哪些资料和能力
什么时候会来问你
第一周会产生什么结果
```

### 6.3 “我要做小红书”的空间结果

第一版可以形成：

```text
业务：内容增长
└── 小红书办公室
    ├── 员工
    │   ├── 内容研究
    │   ├── 选题策划
    │   ├── 文案创作
    │   ├── 视觉制作
    │   ├── 发布运营
    │   └── 数据复盘
    ├── 能力
    │   ├── 文本模型
    │   ├── 图片生成
    │   ├── 搜索与研究
    │   └── 数据分析
    ├── 知识
    │   ├── 品牌资料
    │   ├── 历史内容
    │   ├── 目标用户
    │   └── 平台规则
    ├── 工作方式
    │   └── 研究 → 选题 → 创作 → 审核 → 发布 → 反馈 → 复盘
    └── CEO 介入点
        ├── 方向确认
        ├── 发布前审查
        ├── 高风险互动
        └── 周期复盘
```

这不是固定模板的最终答案，而是用户可以确认和改造的首版办公室。

### 6.4 空间装配能力如何搭建空间

空间装配能力是 Curis 的一种责任和 Workspace 模式，不要求第一天以一个空部门出现在用户组织里。它可以由 Assistant 调度，也可以在高级工作面中被专业用户使用；只有当这项责任长期重复、需要共享能力和独立协作时，才考虑形成正式部门。

它的输入：

- 用户意图和业务目标。
- 业务类型和外部结果。
- 公司已有员工、能力、知识和模板。
- 用户偏好、成本和介入边界。

它的输出：

- Workspace 工作方式。
- 角色和员工建议。
- 能力和知识组合。
- 外部 Agent 接入建议。
- 数据输入和结果返回方式。
- 用户介入点和失败备用路径。
- 第一版工作计划和启动检查。

空间装配能力不应该只生成页面。它交付的是：

> 一间有目标、有员工、有能力、有工作方式、有结果窗口、可以开始工作的办公室。

### 6.5 模板如何复用

模板不是静态页面副本，而是可调整的业务起点，至少包含：

- 适用业务和目标。
- 推荐 Workspace UI 类型。
- 推荐岗位和责任。
- 推荐 Agent/Tool/Knowledge 组合。
- 默认工作方式和节奏。
- 默认结果与反馈方式。
- 默认用户介入点。
- 已知限制和需要确认的假设。

模板复用路径：

```text
选择模板
→ 读取公司已有资源
→ 替换不适合当前公司的岗位/能力/知识
→ 生成公司专属版本
→ 用户确认
→ 运行并记录结果
→ 复盘后形成下一版模板或公司私有模式
```

模板不能静默覆盖正在运行的 Workspace。升级必须可预览、可确认、可回退。

### 6.6 招聘、组队与外部 Agent 接入

外部 Agent 进入 Curis 有两条普通用户路径，另保留一条高级能力路径：

```text
招聘：外部 Agent / 专家 / 职业模板
→ 形成一个具有公司身份的员工
→ 配置岗位能力包、公司关系和汇报对象

组队：公司已有员工
→ 选择成员进入某个 Workspace
→ 明确谁负责什么、谁正在做什么、接下来交给谁

直接接入能力（高级）：外部 Agent 只承担一个环节
→ 作为当前员工的 Executor / Capability 使用
→ 不单独形成公司员工身份
```

招聘与组队必须区分：招聘改变公司成员，组队改变 Workspace 的协作组合；组队不复制员工身份，也不改变员工的工作历史。

招聘一个外部 Agent / 专家的路径是：

```text
发现一个外部 Agent / 专家 / 职业模板
→ 查看它适合什么岗位和责任
→ 形成员工身份并补齐公司关系
→ 自动推荐或确认岗位能力包
→ 连接并验证输入、权限、数据范围和输出
→ 设定用户确认和成本边界
→ 在 Workspace 中试用
→ 观察结果
→ 保留、替换、暂停或回退
```

外部 Agent 被“招聘”为员工后：

- 员工身份、岗位、公司关系和工作历史独立于底层模型或 Agent，可替换执行方式而不抹掉身份。
- 不自动获得全部公司知识、工具和权限；仍须经过岗位能力包和公司授权。
- 不跳过用户确认、成本和副作用边界。
- 必须能够返回状态、成果、错误和需要用户介入的位置。
- 如果只被直接接入一个环节，则仍是 Executor / Capability，不在产品层冒充员工。

### 6.7 Workspace 如何成长和改造

空间改造由真实结果触发：

```text
发现结果下降 / 工作卡住 / 成本过高 / 责任重复
→ Assistant 解释原因和证据
→ 提议调整岗位、能力、知识、工作方式或 UI
→ 用户查看影响和差异
→ 生成新版本
→ 小范围试用或正式切换
→ 观察结果并复盘
```

改造可以只影响一个环节。文案质量下降，不需要重做整个内容办公室；只需调整文案员工的承担能力、知识或方法，再观察下游结果。

## 7. AI 员工模型

### 7.1 产品层先看到员工 / 专家，内部保留四层分离

产品层定义：

> 员工 = 一个具有公司身份的专家 / Agent。

人才市场中的专家 / Agent 不等于公司员工；只有完成招聘并赋予公司身份、岗位、职责和关系后，才进入组织中心成为员工。用户先看到员工的身份、岗位、当前工作、能力、结果和关系；不需要先理解 Position、RoleSlot 或 Executor。员工可以直接对话、被委派、进入多个 Workspace，并在团队中接住和交回工作。

内部仍保留四层分离：

```text
岗位 Position
  组织中的长期责任：例如“内容策略”

工作位置 RoleSlot
  某个 Workspace / Blueprint / Stage 的具体责任：例如“本轮选题研究”

AI 员工 AIEmployee
  稳定的工作主体：可以被找到、对话、委派和评价，可承担一个或多个 RoleSlot

执行能力 Executor
  当前实际执行方式：GPT、Claude、Codex、Coze Agent、OpenOPC、EvoFlow、本地 Agent 或工具组合
```

Position、RoleSlot、AIEmployee 和 Executor 不能合并，但这些是高级详情和内部实现语言。更换模型或 Agent 只能改变 Executor；调整 Workspace 的责任位置不能抹掉 AIEmployee 的身份和历史；替换 AIEmployee 也必须保留原 RoleSlot 的责任、旧 Handoff 和未关闭结果。

CEO Assistant 是唯一的 Company-level 特殊 AIEmployee：它直接向 CEO 汇报，协调 Professional AI Employees，接收并汇总跨 Workspace 结果；Workspace AI 是具体 RoleSlot 的执行责任投影，不是另一个平级员工系统。

### 7.2 员工的产品属性

每个员工至少要有：

- 身份与岗位：名称、头像、责任范围和汇报对象。
- Agent / 模型：当前基础执行方式，以及可替换的执行者。
- 技能组合：员工知道怎样完成这类工作的方法和规则。
- 知识 / 文件：员工可以依据的公司资料、岗位资料和工作文件。
- 工具与连接：员工可以使用的工具、渠道和外部连接。
- 权限：数据范围、外部动作、成本和副作用边界。
- 记忆 / 经验：可查看、可纠正、可过期的工作经验。
- 公司关系：所属部门、业务、Workspace、团队和汇报关系。
- 当前工作、工作历史、成果、反馈、失败和用户介入入口。

### 7.2.1 职业能力组合 / 岗位能力包

模型只是员工的基础执行能力。岗位能力包把以下内容组合成一个可直接使用的职业起点：

```text
角色责任 + 模型 + 技能组合 + 知识 / 文件
+ 工具 / 渠道 + 权限 + 当前上下文 + 工作经验
```

例如“小红书运营专家”应自动获得合理的选题、内容创作、数据观察、平台连接和复盘建议；用户可以直接开始工作，再按实际结果微调，不需要先研究应该安装哪些 Skill。

岗位能力包只是员工配置的产品表达，不是新的系统对象或生命周期。员工结果不好时，复盘默认按以下顺序寻找能力缺口：技能、知识、工具、上下文、权限、模型和工作方式；找到缺口后只调整下一轮需要的部分，并保留旧结果和经验。

### 7.2.2 招聘后的员工与 Workspace 专家团队

招聘把外部 Agent、专家、编码 Agent、本地 Agent 或职业模板变成公司员工；组队则从现有员工中选择多人进入某个 Workspace。普通用户只需看懂：

| 团队信息 | 用户要看到什么 |
| --- | --- |
| 成员 | 谁在团队里 |
| 责任 | 谁负责什么 |
| 当前工作 | 谁正在做什么 |
| 下一步 | 工作接下来交给谁 |

团队可以按责任自行流转工作；用户仍可随时打开具体员工，对某一个环节局部介入、补充上下文、要求重做或改变下一步。RoleSlot、Handoff、Cycle 继续作为底层支撑，不成为普通用户的必学概念。

### 7.2.3 员工详情的直接工作模式

员工详情沿用成熟 Agent 产品已经验证的三栏模式：

```text
左侧：员工 / 专家列表
中央：与当前员工直接对话和工作
右侧：员工设置
      模型 · 技能 · 知识 / 文件 · 渠道 / 连接 · 权限
```

Curis 在右侧设置和员工详情中补充公司需要的关系信息：部门、岗位、业务、Workspace、汇报关系、工作历史、成果和经验。高级的 Provider、RoleSlot、Capability Supply Check 和 Executor 只在需要排错、审计或配置时展开，不重新发明一套复杂员工配置 UI。

### 7.3 员工的四种使用方式

1. **直接对话**：问进展、给指令、补上下文、要求解释。
2. **委派工作**：给一个目标，让员工独立完成并汇报。
3. **查看历史**：查看过去做过什么、哪些结果被接受、哪里反复失败。
4. **调整承担能力**：更换模型、Agent、Tool、Skill 或 Knowledge，岗位和身份保留。

### 7.4 局部介入契约

任何多阶段 Workspace 都要能回答：

- 当前哪个员工负责？
- 它接收了什么输入？
- 产出了什么中间结果？
- 下游依赖什么？
- 用户修改后从哪里继续？

用户说“重新写这篇文案”时：

```text
保留：业务目标、选题、品牌边界、已确认素材
重做：文案员工负责的当前版本
继续：审核、发布、互动和反馈环节
保留：旧版本、修改意见、差异和最终选择
```

### 7.5 员工如何成长

员工成长不是任意改变人设，也不默认先换模型，而是先从真实结果分析能力缺口：

```text
技能缺失 / 组合不合理？
→ 知识不足？
→ 工具、连接或权限不足？
→ 上下文或工作方法有问题？
→ 最后才判断模型能力是否不足
```

形成可验证的成长闭环：

```text
工作 → 真实结果 → 原因分析
→ 调整技能 / 知识 / 工具 / 权限 / 上下文 / 工作方法 / 模型
→ 下一轮工作 → 结果比较
→ 有效经验沉淀 → 更新员工职业能力组合
```

员工有效经验经过多次验证后，可以进入岗位能力包；在多个业务中验证后，才建议沉淀为公司可复用的人才模板：

```text
员工有效经验
→ 多次验证
→ 岗位能力包
→ 多业务验证
→ 公司可复用人才模板
```

重要经验必须可查看、可纠正、可过期；不能把一次错误输出自动写成公司规则。

## 8. 能力生态与职业能力体系

### 8.1 人才市场、设置与公司能力的边界

人才市场是一级产品，负责公司外部的能力发现和扩展；设置不是能力市场，而是已引入资源的连接、授权、维护和撤销；组织中心只展示公司已经拥有的员工和责任；业务空间只展示这些员工在哪里工作。

```text
人才市场：发现专家 / Skill / 连接器 / 模板 / 外部能力
→ 安装 / 引入 / 招聘
设置：连接、授权、版本、权限、成本、撤销
→ 公司可用资源
组织中心：公司已经拥有谁、谁负责什么
→ 员工职业能力
业务空间：这些员工在哪里工作、结果如何
```

市场项目在未安装、未授权或未招聘前，只是外部候选，不得冒充公司 Capability、员工或可运行的 Workspace 资源。

设置维护已进入公司的技术资源：

```text
模型
Agent Provider
Tool
Skill
MCP
外部服务 / 连接
Knowledge 来源
权限、成本、数据范围和副作用策略
```

用户日常不进入技术资源维护面寻找“下一步要点什么”。日常使用从对话、人才市场或 Workspace 开始，系统按需要推荐能力组合或提示缺口。

### 8.2 能力的产品语义

用户不需要先问“我有哪些 Provider”，而是先看到：

> “这个岗位需要搜索和数据分析，目前搜索可用，数据分析需要接入一个来源。”

设置和能力生态把技术资源转成公司资源；但 Skill 不再只是与 Tool / MCP 并列的普通资源。它是职业能力体系中的工作方法单元，必须结合责任、知识、工具、权限、上下文和经验才能判断是否有效：

| 技术资源 | 公司语义 |
| --- | --- |
| Model | 这个员工可以怎样思考和生成 |
| Agent Provider | 这个员工可以把哪类工作交给谁执行 |
| Tool | 员工可以做什么动作 |
| Skill | 员工知道怎样做这类工作 |
| MCP | 员工可以连接哪些外部能力 |
| Knowledge | 员工可以依据哪些公司资料 |
| Connection | 员工可以读取或写入哪个外部世界 |

职业能力的产品层次是：

```text
外部 Skill / MCP / Tool / Agent / Prompt / Instruction / 工作方法 / Knowledge
                              + Curis 自有 Skill
                                      ↓
                              统一能力资源
                                      ↓
                              职业能力组合
                                      ↓
                              岗位能力包 / 人才模板
                                      ↓
                              招聘 → 员工 → Workspace 团队
```

Curis 的核心不是拥有最多 Skill，而是把各种来源组合成真正能干活的员工，并根据真实业务结果持续优化组合。岗位能力包仍是员工配置的产品表达，不新增 Skill Store、能力对象或独立生命周期。

### 8.3 能力使用路径

```text
在对话 / Workspace 中提出目标
→ Curis 判断已有能力是否足够
→ 直接调用已授权能力
→ 缺少能力时给出自然语言缺口
→ 用户选择接入、替代或人工回退
→ 能力进入岗位 / Workspace 的可用范围
```

### 8.3.1 能力供给检查

能力缺口不是一个“找不到 Provider”的提示，而是当前 RoleSlot 能否合法开始工作的产品事实。每个 RoleSlot / Blueprint 产生明确的能力需求，Curis 只从当前有效的 Company Capability 供给中检查候选，不把凭证或未经验证的目录项投影给用户。

用户看到的路径是：

```text
发现 RoleSlot 需要能力
→ 选择可用的 Company Capability 候选
→ 检查可用性、权限、数据范围、风险和成本
→ 供给阻塞 / 供给齐备 · 未授权
→ CEO 授权并激活
→ RoleSlot 可运行
```

必须明确区分：

```text
目录可见 ≠ 已连接
已连接 ≠ 供给检查通过
供给齐备 ≠ 已授权
已授权 ≠ 已激活
已激活 ≠ 已产生真实结果
```

检查失败、能力撤销、版本不一致或目录元数据漂移时，系统必须 fail-closed，并提供四个真实选择：

- 接入或修复当前能力。
- 选择满足同一输入 / 输出契约的替代能力。
- 使用该 RoleSlot 已定义的人工回退。
- 暂停这项责任并保留原因、Owner 和下一检查点。

人工回退可以让工作继续，但必须记录人工责任、来源、时间和输入输出；外部结果或 CEO 手动补录默认标为 `UNVERIFIED`，不能生成“已验证”结果、自动扩大业务或伪造激活。能力恢复后重新检查同一个 RoleSlot / Workspace 版本，不用新建对象或覆盖旧失败记录。

### 8.4 能力维护路径

```text
人才市场发现 → 安装 / 引入
→ 设置 → 公司资源 → 添加/导入
→ 验证身份、权限、输入和输出
→ 选择可使用的岗位 / Workspace
→ 设置成本与副作用
→ 试用和观察
→ 更新、暂停、替换或撤销
```

公司资源设置不应让用户直接修改正在运行的所有工作。变更要说明影响：

- 哪些员工会受影响。
- 哪些 Workspace 会受影响。
- 预计成本和风险如何变化。
- 是否保留旧能力作为回退。

## 9. 对话模型

### 9.1 对话是统一意图入口

用户可以用对话：

- 创建公司、业务、员工或 Workspace。
- 询问公司、业务和结果。
- 委派复杂工作。
- 修改一个工作对象。
- 召集多个员工讨论。
- 处理异常和请求恢复。
- 创建自动化或检查点。
- 请求分析、复盘和公司调整。

### 9.2 当前上下文自动继承

```text
公司级：公司、全部业务、今日经营
业务级：业务目标、投入、结果和相关 Workspace
Workspace 级：办公室布局、成员、工作对象、知识和能力
员工级：岗位责任、记忆、历史和当前工作
对象级：当前文档、代码、内容、研究条目或数据
```

用户可以显式切换上下文，但不需要每次重新输入背景。

### 9.3 @员工与多 Agent 协作

@提及是帮助用户表达责任分工的轻量方式，不是要求用户管理一堆 Agent ID。

```text
@ChatGPT 分析需求
@Codex 实现方案
@Claude Code 审查改动
@全体讨论风险
```

Curis 负责将这些调用映射到：

- 当前 Workspace。
- 对应岗位和员工。
- 可用的执行能力。
- 上下游交接。
- 结果和用户介入点。

### 9.4 对话结果必须可进入工作

对话不能只产生一段文字。它可以产生：

- 业务草案。
- Workspace 方案。
- 员工委派。
- 工作对象修改。
- 会议议题。
- 决策草案。
- 资料或知识候选。
- 自动化草案。

涉及公司状态变化时，Assistant 先展示影响和请求确认；普通问答不制造多余审批。

### 9.5 CEO Assistant 是经营代理，不只是聊天入口

CEO Assistant 帮普通用户承担 CEO 原本需要完成的理解、判断准备、委派和跟进，但不替用户伪造事实或默默做高影响决定。它的完整行为链是：

```text
观察公司、业务和 Workspace 的真实变化
→ 用普通语言解释发生了什么和为什么重要
→ 给出少量可比较的建议
→ 代用户发起低风险工作，或请求高影响确认
→ 跟进执行、结果和异常
→ 在下一次简报中说明结果是否改变了原判断
```

Assistant 每次提出行动前至少说明：

- 依据是什么，哪些是事实、推断或未知。
- 影响哪项业务、员工、Workspace、成本、权限或外部结果。
- 它准备做什么，预计会产生什么结果。
- 用户需要确认什么，或者为什么可以自动继续。
- 如果失败、缺数据或用户拒绝，下一步和人工回退是什么。

### 9.6 按影响分级的行动权限

| 行动类型 | 示例 | Assistant 默认行为 |
| --- | --- | --- |
| 只读理解 | 汇总进展、解释结果、搜索公司资料 | 直接回答，标明来源和新鲜度 |
| 可撤销内部工作 | 生成草稿、安排研究、整理资料候选 | 可直接开始，完成后汇报 |
| 影响成本或权限 | 更换执行能力、扩大数据范围、启用新连接 | 展示影响并请求确认 |
| 外部或不可逆动作 | 发布、发送、交易、对外承诺、改变公司方向 | 必须明确确认，保留决定和结果 |

对话本身不是事实存储，也不是完成证明。涉及工作、结果、决定或资源变化时，Assistant 必须把行动落到对应的 Workspace、员工、资料库、会议或公司记录；用户稍后从 UI 返回时，仍能看到同一状态和上下文。

当真实数据不足时，Assistant 应明确说“现在不知道”，说明缺口，并提供接入、人工补录、替代来源或暂不判断的选择；不能用看似完整的分析填补未知。

## 10. Workspace 接入模型

### 10.1 外部 Agent 接入方式

Curis 允许三种接入方式：

1. **直接使用**：成熟产品已经解决了完整工作方式，Workspace 只提供公司上下文和入口。
2. **组合使用**：多个 Agent、工具和数据源组合成一间业务办公室。
3. **适配使用**：外部能力无法直接满足公司契约时，增加最小 Adapter；不把整个产品重写进 Curis。

### 10.2 Workspace 对外部能力提供什么

```text
Company Context
Business Context
Employee Identity
Role Responsibility
Authorized Capability
Knowledge / Memory
Goal / User Instruction
介入与确认边界
```

### 10.3 外部能力返回什么

```text
Current State
Progress / Waiting / Blocked
Intermediate Output
Final Result
External Data / Receipt
Error / Recovery Point
Cost / Usage
User Intervention Request
```

这是产品契约，不等于本轮确定 API 字段。任何外部 Agent 若不能表达这些信息，只能作为受限工具或人工辅助，而不能被当作完整 Workspace 员工能力。

### 10.4 Workspace 自有 UI

Workspace UI 可以是：

- 对话 + 文件 + 编辑器。
- 看板 + 队列 + 详情面板。
- 研究画布 + 来源 + 报告。
- 行情 + 图表 + 研究笔记。
- 内容日历 + 素材 + 版本 + 互动。
- 浏览器或其他成熟应用的嵌入式工作面。

Curis 只要求它在公司壳中共享：

- 当前公司 / 业务身份。
- 相关员工和负责人。
- 公司级对话和通知。
- 结果返回和资料沉淀。
- 权限、确认和退出路径。

## 11. 经营闭环

### 11.1 公司的主循环

```text
目标 / Commitment
→ 组织员工与能力
→ Cycle 在 Workspace 中自动工作
→ 真实数据和外部结果
→ Evidence / Acceptance
→ Assistant 分析
→ DecisionPacket 准备判断材料
→ CEO 讨论与决策
→ 复盘、知识和资料库沉淀
→ 调整业务、组织、能力和空间
→ 下一轮目标
```

### 11.2 每一环的产品表现

| 环节 | 普通用户看到什么 | AI 负责什么 | 用户保留什么 |
| --- | --- | --- | --- |
| 目标 | 想达成的结果和优先级 | 澄清、拆解、推荐业务/空间 | 方向和重要取舍 |
| 组织 | 谁在负责、是否缺人/缺能力 | 生成和调整最小团队 | 高影响组织变化 |
| 工作 | 进展、当前环节、问题和预计结果 | 委派、执行、交接、提醒和恢复 | 关键指导和接管 |
| 数据 | 外部反馈、回执、来源和变化 | 采集、归类、对比和解释 | 不确定事实的判断 |
| 分析 | 原因、趋势、风险、机会和建议 | 形成简报和候选 DecisionPacket | 是否采纳建议 |
| 复盘 | 哪些有效、哪些失败、如何改进 | 提取经验和新方案 | 确认重要公司学习 |
| 调整 | 员工、能力、业务或 Workspace 的变化预览 | 生成改造方案和影响 | 批准高影响变化 |

### 11.3 经营对象的用户语言

底层可以保留 Commitment、RoleSlot、Cycle、Handoff、Acceptance、DecisionPacket、Capability Supply Check、Truth、Change、Evidence、Run 和 Executor 等机制，但默认 UI 不要求用户理解这些词。产品层优先显示：

| 内部 / 高级详情 | 默认产品语言 | 用户真正需要知道什么 |
| --- | --- | --- |
| Commitment | 目标 / 这轮承诺 | 这次要做到什么 |
| Position | 岗位 / 长期职责 | 这个员工长期负责什么 |
| RoleSlot | 责任位置 | 这一环节由谁负责 |
| AIEmployee | 员工 / 专家 | 谁在负责、能否直接找到 |
| Executor | 当前执行方式 | 现在由哪个 Agent / 模型在做 |
| Cycle | 本轮工作 | 这一轮推进到哪里 |
| Handoff | 交接 | 接下来交给谁，是否已接住 |
| Outcome / Evidence | 结果 / 结果依据 | 做成了什么，凭什么这样判断 |
| Asset | 资料 / 公司沉淀 | Curis 能读取什么、过去产生了什么、还能怎样复用 |
| Capability / Connection | 能力 / 连接 | 公司现在能用什么，授权和风险是什么 |
| Acceptance | 结果确认 | 这次结果是否算数 |
| DecisionPacket | 给 CEO 的判断材料 | 现在需要我判断什么 |
| Capability Supply Check | 能力启动检查 | 这个责任现在能不能开始 |
| Truth | 事实 / 依据 | 哪些是真实已知，哪些未知 |
| Change | 变化 / 执行结果 | 决定之后实际发生了什么 |

高级详情、排错、审计和配置页面可以同时显示内部名称，但必须先显示上面的用户语言；内部严谨性保留在关系、证据、权限和状态中，不靠术语数量制造产品复杂度。

### 11.4 自进化边界

允许自动优化：

- 低影响的提示和表达偏好。
- 已被确认的知识引用方式。
- 已验证的工作排序和提醒节奏。
- 不改变外部副作用的内部协作方式。

必须请求 CEO 确认：

- 外部发布、发送、交易或承诺。
- 新增成本、权限或数据范围。
- 替换公司级岗位承担者。
- 改变业务方向、预算或关键结果。
- 让新 Agent 获取公司敏感知识或执行高影响动作。

### 11.5 Company OS 的四个跨切运行面

`Truth / Assistant / Decision / Change` 不是四个新的一级入口，也不是替代 Company、Business 或 Workspace 的对象；它们贯穿所有工作面，把局部工作接回公司经营。

| 跨切运行面 | 普通用户问题 | 必须提供 | 不应变成 |
| --- | --- | --- | --- |
| Truth | 现在真实发生了什么？依据是什么？ | 来源、时间、新鲜度、版本、外部回执、人工输入和未知状态 | 一张孤立数据大屏 |
| Assistant | 谁帮我理解、委派和跟进？ | 当前上下文、解释、建议、命令、通知和回到原工作的能力 | 固定秘书侧栏或第二套对象层 |
| Decision | 我需要选择什么？影响是什么？ | 选项、影响、责任、确认、拒绝、修改和后续动作 | 讨论结束后的一个按钮 |
| Change | 决定之后公司发生了什么变化？ | 受影响对象、版本、责任、实施状态、回退方式和复盘时间 | 没有责任人的变更日志 |

四个运行面的共同路径是：

```text
Truth 提供事实
→ Assistant 帮用户理解和准备选择
→ Decision 记录用户判断
→ Change 执行并说明影响
→ 新的 Truth 回到下一轮 Company Operating Loop
```

CEO 工作台聚合公司级视图；Workspace 提供局部真实状态和介入点；资料库保存可引用、可复用的资料、结果和学习；会议承载需要讨论的分歧。任何 Workspace 都不能因为拥有自己的 UI，就跳过 Truth、Decision 或 Change 的返回契约。

### 11.6 判断材料与 CEO 选择

当事实、异常或结果需要改变公司行动时，Curis 先生成 DecisionPacket，再等待 CEO 的 Decision。两者在用户体验上连续，但责任上不能合并：

```text
真实事实 / Evidence / 未知
→ Assistant 解释为什么现在需要判断
→ DecisionPacket：选项、影响、责任、推荐、回退条件
→ CEO 选择继续 / 调整 / 暂停 / 替换 / 拒绝
→ Decision 生效并回写 Business / Workspace / Employee / Capability
→ Change 跟进执行、结果和复盘时间
```

DecisionPacket 至少让用户看懂：

- 现在发生了什么，哪些是事实、推断或未知。
- 如果不处理会影响什么，处理会改变什么。
- 可以选择哪些路径，每条路径的成本、风险和责任是谁。
- Assistant 推荐什么，以及推荐依据。
- 用户拒绝、延后、证据不足或执行失败时回到哪里。

“建议已生成”“我已替你选好”或“卡片已关闭”都不代表 CEO 已作出 Decision。只有用户明确选择并被记录，受影响对象才可以进入对应的 Change。

## 12. 竞品产品级参考矩阵

本节只提炼用户为什么这样使用、页面为什么这样组织，以及 Curis 直接借什么。产品事实以官方材料为准，Curis 映射是产品推断。本轮 Coze、Workbuddy 和豆包的条目还吸收了 2026-08-14 在已登录桌面环境中的只读体验；这些观察只用于交互参考，不作为 Curis 功能已交付或接入完成的证据。

| 产品 | 用户为什么这样用 | 页面/交互为什么有效 | Curis 借鉴 | 等级 |
| --- | --- | --- | --- | --- |
| ChatGPT | 用户先有问题或目标，不想先选应用结构 | 对话是入口，Project 自动带文件、指令和历史 | CEO Assistant 作为公司级意图入口；Workspace 自动继承上下文 | L1 |
| ChatGPT / Codex | 长工作需要继续、并行、审查和自动运行 | 线程按项目组织，进度、差异、审查和自动化集中 | Workspace 拥有连续工作现场；离开后继续，回来时从结果接续 | L1/L2 |
| Coze | 用户希望直接找到一个 Agent 并开始工作 | 左侧 Agent/会话列表，中央直接对话，右侧集中设置模型、技能、文件/文件夹、渠道/连接和其他选项 | 员工详情沿用三栏模式；Curis 再加公司关系、岗位、Workspace、历史、成果和经验 | L1/L2 |
| Claude Code | 用户希望直接在项目里提问、修改、测试和继续 | 项目上下文和会话连续，权限按需询问 | 研发 Workspace 直接嵌入成熟开发工作方式 | L1/L2 |
| OpenOPC | 用户希望像管理一家公司一样委派复杂目标 | 公司、岗位、员工和执行承担者有不同层次 | Company、Position、RoleSlot、AIEmployee、Executor 分离；组织由目标产生 | L2/L3 |
| EvoFlow | 长任务不能只靠聊天记录推进 | Plan、Supervisor、子任务、状态、恢复和局部重编排集中 | Workspace 的长任务底层支撑；前台显示计划、进度、问题和下一步 | L2/L3 |
| Relevance AI | 用户想直接使用已配置的 Agent/Workforce | 构建平台与 Chat 分开，@提及、多 Agent 和 Workforce 进入熟悉聊天 | 日常使用不进入 Builder；对话中点名员工或团队 | L1/L2 |
| Workbuddy | 用户想直接召唤职业专家或一组专家处理复杂目标 | 精选场景直接提供“专家”和“专家团”，详情页展示擅长什么、示例任务和团队成员 | “专家”对应 Curis 员工；“专家团”对应 Workspace 的员工组合；Curis 增加公司、部门、业务、长期目标、结果回收和自进化 | L1/L2 |
| 豆包 | 用户希望从对话直接进入长任务、技能和本地电脑工作 | 左侧放新工作任务、AI 浏览器、技能和历史；中央是任务对话；输入区附近显示工作任务、本地电脑、按需确认和技能 | 把工作模式、技能、权限/确认入口放在当前对话附近；仍由 Curis 员工和 Workspace 承接公司上下文 | L1/L2 |
| Linear | 大型 App 需要快速找到对象和继续工作 | Workspace/Team 层级稳定，搜索、最近访问和快捷创建降低成本 | 六个主工作区域保持稳定；搜索和最近工作跨层可达 | L1 |

### 12.1 已确认的直接借鉴

- ChatGPT：对话作为主入口，Project/空间作为自动上下文。
- Codex：按项目组织线程、并行 Agent、持续工作、审查和自动化。
- Claude Code：项目内直接工作、会话继续、权限按需介入。
- Coze：左侧 Agent 列表、中央直接工作、右侧简洁设置，以及 Agent、Knowledge、Tool、渠道和模型的集中配置。
- OpenOPC：公司、岗位、员工和执行能力分离；Curis 进一步把 Workspace 内 RoleSlot 与稳定 AIEmployee 分开。
- EvoFlow：长任务的计划、Supervisor、进度、恢复和局部重编排。
- Relevance AI：构建与使用分离、@员工、多 Agent/Workforce 和自然语言创建。
- Workbuddy：职业专家与专家团的直接召唤、示例任务和团队成员可见性。
- 豆包：工作任务、技能、本地电脑和按需确认靠近对话入口，降低长任务的理解成本。
- Linear：稳定的桌面信息架构、搜索、最近工作和快捷创建。

### 12.2 明确不复制

- 不把任何竞品的 Agent 目录直接当 Curis 首页。
- 不把 Coze 的 Builder 或 EvoFlow 的 DAG 画布当普通用户主路径。
- 不把 OpenOPC 的默认公司结构当所有 Curis 公司的组织答案。
- 不把 Linear 的 issue/project 语义恢复为 Curis 的根对象。
- 不把外部 Agent 的“完成”直接当作业务结果。
- 不用模板、静态 UI、测试通过或模型调用成功替代真实结果、反馈和 CEO 验收。

### 12.3 Curis 自己必须建设的最小差异层

Curis 不需要重新实现成熟 Agent 的工作界面和执行引擎，但必须建设以下让“多个成熟能力成为一家公司”的差异层：

| Curis 自建能力 | 解决的问题 | 不应扩张成 |
| --- | --- | --- |
| 公司上下文与责任关系 | 同一个目标属于哪家公司、业务、Workspace、岗位和员工 | 另一套通用项目管理器 |
| CEO Assistant 经营代理 | 谁汇总变化、解释原因、提出建议并跟进下一步 | 只会聊天的总入口 |
| Provider / Adapter 接入契约 | 不同外部能力如何获得上下文、被授权、被替换并返回结果 | Curis 重写所有 Agent |
| 跨 Workspace 的注意力与返回 | 用户怎样知道哪里需要自己，并回到原工作 | 全量 Runtime 控制台 |
| 结果、来源、反馈和决策连续性 | 工作怎样变成可信结果，再影响下一轮公司行动 | 只记录状态的日志系统 |
| 渐进式组织、资源和空间调整 | 公司怎样从一项工作逐步长出来并安全变化 | 第一天要求用户配置完整组织 |

判断标准很简单：如果一个能力不帮助普通用户开始真实工作、不让成熟能力在公司关系中协同、也不让结果进入反馈和决策循环，Curis 就不应为了“平台完整”而自行建设它。

## 13. UI 设计总规则

这不是页面规格，而是后续 UI 设计的母规则。

### 13.1 一级导航稳定而完整

只显示：

```text
首页 / CEO 工作台 / 业务空间 / 组织中心 / 人才市场 / 资料库 / 会议
```

左下角用户头像打开公司与个人设置菜单。全局 Assistant、搜索、最近工作、通知、当前工作和返回路径保持全局可达，不再增加“Agent、Workflow、Runtime、数据、分析、能力、设置”一堆一级入口。人才市场是发现和扩展能力的一级产品，不等于技术配置入口。

### 13.2 每个页面只回答一个用户问题

- 首页 / CEO 工作台：我现在该关注什么？
- 业务空间：这项业务怎样工作？
- 组织中心：公司已经有哪些人，谁负责什么？
- 人才市场：外部有哪些专家、技能和连接器可以引入？
- 资料库：Curis 能读取什么，过去产生了什么？
- 会议：我们要讨论和决定什么？

设置不作为主工作区问题；它在头像菜单中回答“我和公司怎样维护、连接和运行”。

### 13.3 默认显示业务语言

优先显示：

- 负责的人。
- 当前工作。
- 结果。
- 原因。
- 下一步。
- 需要用户做的选择。

内部对象名只在高级信息、排错、审计和配置场景出现。员工默认称为“员工”或“专家”，专家团队默认显示为“团队成员、责任、当前工作、下一步”；只有进入高级详情才显示 RoleSlot、Handoff、Cycle、Executor 等内部名称。

### 13.4 一个主行动，多个次级入口

首屏只突出一个主行动；设置、历史、技术详情、版本和高级配置进入次级层。避免一个页面同时要求用户搭业务、管组织、接能力和启动运行。

### 13.5 对话与 UI 互相转移

```text
对话提出意图
→ UI 展示方案
→ 用户在 UI 中比较和确认
→ 对话继续执行或解释
→ UI 展示状态和成果
```

对话不能替代可浏览的结果；UI 也不能把自然语言意图强行拆成复杂表单。

### 13.6 空态必须是下一步，不是死胡同

每个空态要说明：

- 这里是什么。
- 目前为什么为空。
- 用户可以直接说什么或做什么。
- Assistant 可以帮忙做什么。
- 如果缺能力，人工回退是什么。

### 13.7 复杂度按需展开

```text
首页：事实、结果、问题、下一步
详情：责任、上下文、历史、版本
高级：Provider、Model、Tool、Skill、MCP、权限、Trace、成本
```

### 13.8 左下角头像菜单规则

头像菜单不是一个隐藏所有功能的杂物抽屉，而是稳定的维护入口。建议顺序：

```text
头像 / 公司名称
├── 当前用户与个人偏好
├── 当前公司与公司资料
├── 公司资源与连接
├── 权限、数据与外部动作
├── 运行、成本与诊断
├── 帮助与反馈
└── 退出
```

交互规则：

- 菜单打开后先显示当前用户和公司，不先显示技术资源。
- 有问题时从 CEO 工作台、员工详情或 Workspace 启动检查直接跳到对应设置，并能返回原位置。
- 头像菜单中的“公司资源”可以进入完整维护面，但日常工作不依赖它。
- 连接失效、成本异常和需要授权的事项仍必须在 CEO 工作台或当前 Workspace 主动提醒，不能因为设置被隐藏就降低可见性。
- 头像、公司名称和菜单按钮必须有清晰的可见标签或辅助文本，不能只依赖一个难以识别的图标。

### 13.9 Desktop 空间原则与右侧检查器

固定壳层采用“固定一级侧栏 + 可折叠上下文侧栏 + 自由主工作区 + 按需右侧检查器”：

```text
左侧第一栏：我在哪里
  首页 / 业务空间 / 组织中心 / 人才市场 / 资料库 / 会议
  最近工作 / 头像与设置

左侧第二栏：当前上下文是什么
  随一级模块展开，可折叠

中间主工作区：我正在做什么
  由当前模块或 Workspace 决定具体 UI

右侧检查器：我正在看 / 修改什么
  按需展开，关闭后回到原工作
```

上下文侧栏示例：

| 一级模块 | 上下文侧栏 |
| --- | --- |
| 资料库 | 搜索、最近、本地、我的资料、外部资料库、公司产生 |
| 人才市场 | 搜索、专家、技能、连接器、分类、已安装 |
| 业务空间 | 部门、业务、Workspace、最近工作 |
| 组织中心 | 公司、部门、员工、当前团队 |

进入具体 Workspace 后，第二栏可以切换为 Workspace 自己的导航，并且必须可折叠，为研发、画布、数据等专业工作腾出空间。

点击员工、专家、Skill、文件、工作对象、结果或设置项时，优先从右侧展开详情 / 编辑面板，不为了普通查看离开当前工作，也不大量使用 Modal。员工检查器至少可按需显示：身份、岗位、模型、技能、知识 / 文件、工具、渠道、权限、当前工作和历史成果。

空间原则固定为：

> 左边负责“我在哪里”；中间负责“我正在做什么”；右边负责“我正在看 / 修改什么”。

Modal 主要保留给删除、不可逆操作、高风险授权和高影响确认；普通查看、编辑、配置、员工详情、Skill 详情、文件信息和工作状态优先使用侧栏展开。

## 14. 产品母契约

后续每个 Workspace、员工和能力设计都必须满足以下契约。

### 14.1 Workspace 契约

- 有明确业务归属和结果目标。
- 有独立的业务 UI 和工作对象。
- 有可识别的责任员工。
- 每个 Workspace / Blueprint / Stage 的 RoleSlot 都有明确输入、输出、负责人、能力需求、容量和失败出口。
- 能在阶段边界生成并追踪显式 Handoff，确认责任被接收、执行和交回。
- 能获取公司上下文和授权资源。
- 能返回状态、成果、数据和异常。
- 能暴露用户介入点。
- 能把结果回收到资料库、会议、决策和经营循环。

### 14.2 员工契约

- 岗位责任清楚。
- 产品层先能看懂“这个员工是谁、负责什么、正在做什么、接下来交给谁”。
- 高级详情能区分 Position、RoleSlot、AIEmployee 和 Executor，保证身份、责任位置和执行方式不会混淆。
- 可以直接对话和委派。
- 有工作历史和经验。
- 具备身份与岗位、模型、技能组合、知识/文件、工具、渠道/连接、权限、记忆/经验和公司关系。
- 当前执行能力可见但可替换。
- 能看见自己接收、交出和等待的 Handoff。
- 能报告状态、成果、问题和需要的输入。
- 支持局部重做，不强迫整个 Workspace 重跑。

### 14.2.1 CEO Assistant 契约

- 每个 Company 只有一个当前 CEO Assistant 身份，并直接向 CEO 汇报。
- 负责公司简报、请求分流、专业员工协调、Handoff 回收、异常升级和经营日收束。
- 可以在既有授权内发起低风险、可撤销的内部工作；不能替 CEO 产生高影响 Decision 或 Acceptance。
- 必须把 Brief、Handoff、DecisionPacket、检查点和 Closeout 回到同一 Company / Business / Workspace 上下文。
- 发生未知、失败、退回或能力缺口时，必须说明责任、原因、下一检查点和人工回退。
- Global Assistant Runtime 只提供跨页面承载、通知和命令入口，不生成第二个 Assistant 身份。

### 14.3 能力契约

- 说明能做什么和不能做什么。
- 说明需要哪些输入、知识、权限和连接。
- 说明成本、副作用和数据范围。
- 可分配给岗位 / 员工 / Workspace。
- 必须能被具体 RoleSlot 的 Capability Supply Check 重新核对，并区分供给、授权、激活和可运行。
- 可验证、暂停、替换和撤销。
- 失败时提供替代能力或人工回退。

### 14.4 结果契约

- 结果有来源和时间。
- 能区分内部完成、外部反馈、人工补录和未知。
- 用户可以查看、修改、接受、拒绝或继续。
- 结果可以进入资料库、知识、会议和下一轮决策。
- 结果不因页面刷新、应用重启或用户离开而丢失。

### 14.5 用户可见生命周期

以下是产品语言，不是 Runtime 状态机。内部可以有更细的状态，但不能跳过用户能理解的事实和下一步：

| 对象 | 用户可见变化 | 进入下一阶段的最低事实 | 不能误读为 |
| --- | --- | --- | --- |
| Company | 想开始 → 有工作起点 → 经营中 → 调整中 → 暂停/关闭 | 有方向、第一项业务和可工作的起点 | 创建一条根记录 |
| CEO Assistant | 介绍 → 在岗 → 汇报/协调 → 等待 CEO / 升级 → 复盘/替换 | Company-level 身份、汇报关系、责任契约和可用能力明确 | 一次欢迎对话或全局通知 |
| Business | 想法 → 已确认 → 运行中 → 学习/调整 → 暂停/结束 | 目标、责任和至少一个可工作的办公室 | 一个名称或文件夹 |
| Commitment | 候选 → 已确认 → 进行中 → 达成/偏离/取消 | 结果范围、负责人、检查点和判断标准清楚 | 一句目标或 KPI |
| Workspace | 预览 → 可开始 → 运行中 → 等待/阻塞 → 复盘/改造 → 暂停/退役 | 责任员工、能力检查、结果方式和人工回退 | 保存 Draft |
| RoleSlot | 规划 → 待接手 → 可运行 → 工作中/等待/退回 → 关闭/失效 | Workspace 阶段责任、输入输出、能力需求、容量和失败出口明确 | 一个员工名称 |
| Cycle | 计划 → 进行中 → 等待/阻塞 → 待验收 → 已关闭/需调整 | 本轮输入、责任、截止或检查点和退出条件清楚 | 一次 Run 或一张任务卡 |
| Handoff | 准备 → 已提交 → 已接收 → 处理中 → 交回/退回/失效 | 交接双方、输入输出、检查点和失败回路清楚 | 一条通知或聊天消息 |
| Department / Shared Service | 建议 → 形成中 → 运行中 → 调整/解散 | 共享责任、成员范围和能力收益明确 | 一个空部门容器 |
| Employee | 候选 → 在岗 → 工作中/等待 → 暂停/替换 | 岗位责任、承担关系和可用执行能力 | 目录里的 Agent |
| Capability | 发现 → 已连接 → 已授权 → 可用 → 降级/暂停/撤销 | 身份、权限、输入、输出和副作用边界已验证 | 目录可见 |
| Capability Supply Check | 未检查 → 检查中 → 阻塞/供给齐备 → 供给漂移/需重查 | 当前 RoleSlot 的供给、权限、数据范围、风险和成本被重新核对 | 不等于已授权或已激活 |
| Outcome | 生成中 → 待检查 → 外部反馈/待验收 → 已接受/已拒绝/未知 → 复用/归档 | 来源、时间、版本和可信程度清楚 | 内部调用成功 |
| Acceptance | 待判断 → 接受/拒绝/部分接受 → 已回到下一步 | Commitment、Evidence、影响和用户选择已对齐 | 点一下“完成” |
| Company Meeting / Workspace Meeting | 提议 → 准备 → 讨论中 → 待决定 → 跟进 → 关闭 | 上下文、议题、事实、参与者、决定和责任清楚 | 一段聊天或纪要 |
| DecisionPacket | 草稿 → 待 CEO 判断 → 已处理/已失效 → 已应用/已回滚 | 事实、未知、选项、影响、回退条件和来源明确 | 一条建议文本 |
| Decision | 待决定 → 继续/调整/暂停/替换/拒绝 → 已执行 → 已复盘 | 影响、责任、用户选择和后续动作已记录 | 一条建议文本 |
| Asset | 候选 → 已确认 → 可复用 → 过期/归档 | 来源、所有者、适用范围和复用方式明确 | 任意文件 |

生命周期的共同规则：

- 每次升级都要说明新增了什么事实、谁负责和下一步是什么。
- 阻塞、降级、拒绝和暂停都必须保留原因、责任人、恢复或替代路径。
- 页面刷新、应用重启、离开 Workspace 或更换 Executor 后，生命周期和历史不能被重置或伪造。
- 用户看到的是“准备开始、正在工作、等我处理、结果待确认、是否满足这轮承诺、已进入下一步”等业务语言；高级面才展开内部状态名。

### 14.6 产品装配门

以后新增一个 Workspace、员工能力或跨层功能，至少要通过以下七个产品问题；答不清楚就停在方案阶段，不进入实现：

1. 普通用户能否从自然语言目标开始，而不是先理解内部对象？
2. 能否说明它复用哪个成熟能力，以及 Curis 只补哪一层公司契约？
3. 用户能否看见真实状态、结果、来源和未知，并区分能力供给、授权、激活和真实结果，而不是只看到成功标记？
4. 用户能否定位责任员工，并只介入有问题的局部环节？
5. 结果能否回到业务、资料库、会议、决定或下一轮工作？
6. 离开、重开、失败或替换执行能力后，状态、责任、版本和下一步是否仍然成立？
7. Commitment、Handoff、Acceptance、DecisionPacket 和 Decision 是否分别表达了承诺、责任转移、结果判断、判断准备和后续选择，而没有被压成同一个完成状态？

产品装配门不是开发测试清单，也不能被一次页面演示替代；它是判断“这是否属于 Curis 产品层”的最小门槛。

## 15. 当前 → 目标的产品纠偏方向

以下不是实现任务清单，而是原 v2.0 对现有产品方向的判断（v3.0 继续承接）：

| 当前容易出现的表达 | v2.0 的产品表达 |
| --- | --- |
| Company 创建完成 | 公司已经有方向、第一项业务和可工作的起点 |
| Workspace Draft | 这间办公室准备怎样帮助业务工作 |
| Simulation 未通过 | 还有什么不能开始、谁处理、怎样人工回退 |

| Runtime Error | 工作哪里出了问题、谁负责、怎样恢复 |

目标不是删除底层事实，而是把它们翻译成普通用户可以行动的语言。

## 16. 自审结论：简洁是否覆盖完整

### 16.1 已覆盖的用户任务

当前六个主工作区域加跨层能力，已经覆盖普通用户的完整基本循环：

```text
开始公司 / 新业务       → CEO 工作台对话
理解公司和责任          → 组织中心
进入具体业务并工作      → 业务空间 / Workspace
发现和扩展公司能力      → 人才市场
查看资料和公司积累      → 资料库
讨论、决定和跟进        → 会议 + CEO 工作台问题处理
处理异常、委派和局部改动 → 全局 Assistant + 当前员工/工作对象
维护模型和外部连接      → 左下角头像菜单 + 上下文缺口入口
查看运行、成本和健康    → CEO 工作台提醒 + 头像菜单诊断
```

### 16.2 仍然必须存在、但不必成为一级导航的能力

以下能力不能因为界面简洁而删除，只是分别下沉到正确位置：

| 能力 | 归属 | 可见方式 |
| --- | --- | --- |
| 自动化和定时工作 | CEO Assistant / Workspace | 对话创建，Workspace 管理，完成后进入通知和审查队列 |
| 长任务 | Workspace / 员工 | 当前工作、进度、等待、暂停、恢复和局部重编排 |
| 通知和审批 | CEO 工作台跨层队列 | 主动提醒，点击回到原上下文 |
| 成本和容量 | 公司资源与 CEO 简报 | 异常主动提醒，完整数据在头像菜单 |
| 连接与权限 | 头像菜单 + 上下文启动检查 | 缺口时就地处理，完成后回到原工作 |
| 帮助与反馈 | 头像菜单 | 全局可达，不干扰工作主路径 |
| 搜索与最近工作 | 全局壳层 | 快捷键、搜索按钮和最近访问 |
| 会议准备与执行反馈 | 会议 + CEO Assistant | 从问题卡、业务和结果直接进入 |

### 16.3 仍需警惕的遗漏

简洁方案只有在以下三点成立时才完整：

1. CEO 工作台真的能聚合运行中的工作、异常、审批和结果，而不是只显示静态简报。
2. 头像菜单虽然不在主导航，但公司资源、数据、连接、帮助和账户设置仍然容易找到。
3. 每个 Workspace 都能独立返回结果、状态和用户介入点，不因统一壳层而重新变成 Runtime 页面。

如果这三点没有实现，问题不是一级导航少，而是跨层能力没有真实落地。

### 16.4 哪些还可以更精简

- “设置”从一级导航移到左下角头像菜单：应当收敛，已纳入本修订。
- “会议”保留为一级工作区域，但默认从 CEO 工作台的问题卡和决策事项进入；没有活跃会议时不强调空的会议首页。
- “资料库”保留为一级工作区域，因为本地资料、外部资料、成果和模板既是公司长期积累，也是员工工作的输入，不应埋在各 Workspace 或头像菜单里；日常仍从结果和对话直接进入资料库。
- “组织中心”保留为一级工作区域，因为用户必须能理解谁负责什么；但部门、岗位、招聘和能力配置不应全部平铺在首屏。
- “业务空间”保留为一级工作区域，因为 Workspace 是 Curis 的核心扩展能力；业务列表只是入口，真正内容由独立 Workspace 决定。

因此当前最简且不丢能力的形态是：

```text
六个主工作区域
+ 一个全局 Assistant
+ 一个全局搜索 / 最近工作
+ 一个全局问题与通知队列
+ 左下角头像维护菜单
```

---

## 17. Desktop 壳层与首次打开状态

Curis 是 Desktop App，但“Desktop”不等于把网页包进一个固定后台壳。壳层的职责是保持公司上下文、让用户随时回到正在发生的事，并承载跨 Workspace 的 Assistant、搜索和介入；真正的工作内容仍由各业务 Workspace 决定。

### 17.1 稳定壳层

所有公司状态共享同一套最小壳层：

```text
左侧第一栏：六个主工作区域
  首页 / CEO 工作台 / 业务空间 / 组织中心 / 人才市场 / 资料库 / 会议
  最近工作 / 头像与设置
左侧第二栏：当前模块或 Workspace 上下文，可折叠
顶部：当前公司 / 业务 / Workspace / 员工上下文
中间：当前真正的工作现场，由当前模块或独立 Workspace 提供
右侧：按需检查器，查看或修改当前员工、资料、结果、工作对象或设置
全局：Assistant、搜索、最近工作、问题与通知
```

左侧第一栏稳定表达“我在哪里”；第二栏表达“当前上下文是什么”，并可在专业 Workspace 中折叠；中间不被统一页面结构限制；右侧只在用户需要查看或修改对象时展开。

壳层不固定加入：

- 永远展开的 Assistant 第三栏。
- 所有对象共用的 Runtime 侧栏。
- 各种常驻指标、连接状态和技术日志。
- 进入每个页面前都必须经过的设置向导。
- 为查看普通详情而弹出的 Modal 或离开当前工作的新页面。

原则：

> 壳层负责“我在哪家公司、现在发生什么、我怎样介入”；Workspace 负责“这项业务具体怎样工作”。

### 17.2 四种首次打开状态

同一个默认入口，依据公司当前事实显示不同的第一步。不能把所有用户都送进同一张空 Dashboard。

| 公司状态 | 用户此刻最需要知道 | 默认首屏 | 主行动 |
| --- | --- | --- | --- |
| 尚未建立公司 | Curis 能为我做什么，怎样开始 | CEO Assistant 的创办引导 | 说出目标，形成第一项业务 |
| 已建立、尚无运行业务 | 公司已经存在，下一步怎样产生真实工作 | CEO 工作台的第一项业务引导 | 确认第一项业务和最小 Workspace |
| 已有业务运行中 | 公司最近发生了什么，哪里需要我 | CEO 工作台简报、变化和问题 | 处理最高影响事项或继续工作 |
| 有等待、阻塞或审批 | 什么事情正在等我，影响是什么 | 问题与待处理队列，保留原上下文 | 补充、批准、修改、接管或恢复 |

四种状态都保留相同的 Assistant、搜索和返回能力。状态变化只改变首要行动，不改变产品对象和导航语义。

### 17.3 空态不是空白页

每个空态必须回答三件事：

1. 现在是什么事实，不能假装已有数据。
2. 为什么用户会看到这个空态。
3. 下一步能产生什么可观察结果。

例如，“尚无外部连接”应说明哪项工作因此不能运行，并提供“接入后回到原工作”或“先用人工反馈”的选择；不能只显示一个“暂无数据”卡片。

### 17.4 桌面恢复

重新打开、崩溃恢复或从通知返回时，默认优先恢复上次的公司上下文和未完成工作，而不是只恢复上次 URL。若原工作已结束或失效，必须给出结果、原因和新的下一步。

“恢复到原位置”不等于“恢复到原状态”：工作状态、结果、失败和用户决定必须以真实持久化事实为准。

## 18. CEO 注意力与返回模型

Curis 的核心不是让 CEO 看更多通知，而是把需要判断的变化按影响排序，并让每一项都能回到产生它的业务、员工或 Workspace。

### 18.1 注意力优先级

默认优先级从高到低：

```text
需要 CEO 决定
→ 阻塞或等待输入
→ 外部结果、反馈或高影响变化
→ 重要偏移、风险和资源异常
→ 正在运行的进度
→ 已完成但尚未查看的结果
→ 普通历史记录
```

“有变化”不自动等于“需要打扰 CEO”。低影响进度可以汇总，只有改变结果、成本、风险、时间或责任的事项才升级到问题处理。

### 18.2 每个关注项的最小信息

CEO 看到的每个关注项至少说明：

- 发生了什么，以及何时发生。
- 影响哪项业务、Workspace、员工或工作对象。
- 当前由谁负责，处于什么状态。
- 为什么现在需要用户，或者为什么只需知会。
- 需要用户做什么，完成后会进入哪一步。
- 依据、结果版本和数据新鲜度是否足够。

主动作使用普通用户语言：

```text
查看结果｜批准继续｜修改要求｜接管处理｜补充信息｜暂停｜恢复｜稍后处理
```

“已读”不是“已处理”。只有用户完成决定、责任转移或明确关闭，关注项才离开待处理队列；低影响信息才可以单独标记已读。

### 18.3 返回原点契约

从 CEO 工作台、通知、搜索或 Assistant 进入深层对象后，页面必须保留：

```text
公司 → 业务 → 本轮 Commitment + 关联 Workspace → Cycle → Handoff → 员工 / 工作对象 → 当前问题或结果
```

处理完成后提供“返回原工作”，并把结果、决定和下一步带回 CEO 工作台。不能把用户送进一个没有上下文的详情页，再要求用户自己寻找发生了什么。

## 19. 对象边界与入口归属

每个业务对象只有一个 canonical home，但可以从多个上下文被打开。这样既保留快速入口，也不让导航因为快捷动作不断膨胀。

| 对象 | 普通用户语言 | canonical home | 主要回答 | 不应承担 |
| --- | --- | --- | --- | --- |
| Company | 我经营的整家公司 | CEO 工作台 | 公司现在、过去和下一步 | 变成 Tenant 或设置表单 |
| CEO Assistant | 谁替我看公司、协调员工并跟进结果 | CEO 工作台 | 公司简报、请求分流、交接回收、升级和收束 | 变成固定秘书侧栏或普通 Workspace 员工 |
| Business | 我在经营什么价值方向 | 业务空间 | 目标、投入、结果和反馈 | 代替具体办公室工作 |
| Commitment | 这轮答应要做到什么 | 业务空间 / CEO 工作台 | 范围、负责人、检查点和是否达成 | 变成抽象 KPI 列表 |
| Workspace | 这项业务怎样工作 | 业务空间下的独立办公室 | 工作对象、节奏、员工、能力和结果 | 变成统一 Runtime 页面 |
| RoleSlot | 这个环节由谁负责（高级详情：责任位置） | 对应 Workspace / Stage | 输入、输出、负责人、能力、容量和失败出口 | 变成员工身份本身 |
| Cycle | 这一轮工作怎么推进 | Workspace | 输入、责任、进展、等待、验收和关闭 | 退化为单个 Task |
| Handoff | 接下来交给谁、是否已接住 | Workspace / CEO 工作台 | 交接双方、输入、输出、检查点和失败回路 | 退化为通知或聊天消息 |
| Department / Shared Service | 哪些责任和能力应该长期聚合 | 组织中心 | 共享责任、成员、能力收益和调整 | 退化为空部门目录 |
| Organization / Employee | 员工 / 专家：谁对什么负责 | 组织中心 / 员工详情 | 责任、当前工作、能力和替换 | 平铺成 Agent、Model、Tool 目录 |
| Work object | 现在正在做的具体工作 | 对应 Workspace | 输入、进度、版本、问题和局部介入 | 升级成新的一级产品区域 |
| Outcome / Evidence | 做成了什么，凭什么 | 来源 Workspace + 资料库 | 结果、来源、验收、反馈和影响 | 只显示“成功”状态 |
| Acceptance | 结果确认：这次结果是否算数 | 来源 Workspace / CEO 工作台 | 是否满足目标、保留什么、下一步是什么 | 变成简单完成按钮 |
| Asset | 公司留下了什么 | 资料库 | 知识、成果、模板、经验和复用 | 变成无来源文件仓库 |
| Company Meeting / Workspace Meeting | 在什么上下文讨论什么 | 会议 + 来源业务 / Workspace | 事实、分歧、决定和后续责任 | 孤立的纪要存档 |
| Decision | 讨论后要改变什么 | CEO 工作台 / 会议 | 选择、影响、执行和复盘 | 只保存一句结论 |
| DecisionPacket | 给 CEO 的判断材料：现在需要我判断什么 | CEO 工作台 / 当前会议 | 事实、未知、选项、影响和回退条件 | 变成 AI 自动批准 |
| Capability / Connection | 发现什么、公司能用什么 | 人才与能力 Market / Discover 发现 + 头像菜单设置 | 来源、可用性、授权、成本、风险和替换 | 普通用户的默认起点 |
| Capability Supply Check | 能力启动检查：这个责任现在能不能开始 | Workspace Studio / 当前缺口入口 | 供给候选、检查结果、阻塞原因、Owner 和下一检查点 | 变成 Capability 本身或自动激活 |
| Settings | 我怎样维护公司和自己 | 左下角头像菜单 | 账户、偏好、数据、资源、帮助 | 承载日常业务工作 |

三个容易混淆的边界必须固定：

- 组织中心展示“谁负责什么”；业务空间展示“这项业务正在怎样产生结果”。
- 业务是经营对象；Commitment 是本轮承诺；Workspace 是持续运行对象；Cycle 是有边界的工作轮次；工作对象是 Workspace 内的当前执行事实。
- Assistant 可以跨对象发起行动，但不能制造第二套对象层级；完成后必须落到一个已有业务、Workspace、员工或结果。

### 19.1 用户问题到入口的翻译

| 用户说法 | 首选入口 | 进入后的落点 |
| --- | --- | --- |
| “我想开始做一件新事。” | CEO 工作台 / Assistant | Business 预览与第一 Workspace |
| “这家公司现在怎样？” | CEO 工作台 | 公司简报、变化、问题和结果 |
| “谁在负责这件事？” | 组织中心或当前 Workspace | 员工责任和当前工作 |
| “这项业务具体怎么做？” | 业务空间 | 独立 Workspace |
| “这个结果从哪里来？” | 结果卡或资料库 | 来源工作、Evidence、版本和反馈 |
| “我想发现或引入专家、技能、连接器。” | 人才与能力 Market / Discover | 发现、招聘 / 安装 / 引入后进入公司流程 |
| “我想改变模型、连接或权限。” | 头像菜单，或当前缺口入口 | 公司资源维护后返回原工作 |
| “我需要讨论并做决定。” | CEO 工作台问题卡 / 会议 | Decision 和后续责任 |

## 20. 首个可感知价值契约

普通用户是否愿意继续使用 Curis，首先取决于他是否尽快看见“这家公司已经替我推进了一件事”，而不是是否看见完整的组织树或资源目录。因此每条新用户路径都必须先设计首个可感知价值：

```text
用户表达目标
→ Assistant 给出短预览和最少必要追问
→ 用户确认第一步边界
→ Curis 开始一项真实工作，或明确说明为什么不能开始
→ 用户看到第一个可检查的中间结果、外部反馈或清晰的人工下一步
```

首个可感知价值可以是一个研究结论、内容草稿、代码变更、分析报告、连接诊断或明确的阻塞解释，但必须：

- 与用户刚才的目标直接相关。
- 能看见来源、当前状态和下一步。
- 不把未验证的推测包装成结果。
- 不要求用户先学习 Company、Role、Runtime、Provider 或 Simulation 术语。
- 能继续进入 Workspace，而不是完成一次聊天就结束。

不能用“公司已创建”“员工已生成”“Workspace Draft 已保存”替代首个可感知价值；这些最多是内部准备事实，除非它们已经让用户能开始一项真实工作。

## 21. 最小完整产品闭环

母版不以“页面齐了”作为完成标准，而以普通用户能否完成一条真实、可追溯的经营闭环作为最小完整单元：

```text
说出目标
→ 看到 Business / Commitment / Workspace / 责任的工作预览
→ 确认边界和高影响动作
→ 通过 RoleSlot 能力供给、授权和人工回退的启动检查
→ Cycle 真实开始，责任通过 Handoff 被接住，并可在离开后继续
→ 收到状态、异常或真实结果
→ 查看 Evidence，并判断 Acceptance
→ 形成 CEO Decision
→ Commitment、业务、员工、能力或 Workspace 产生可追溯变化
→ 公司下一次工作可以复用这次结果
```

一条链只有同时满足以下条件，才算产品闭环成立：

| 检查点 | 最低要求 |
| --- | --- |
| 可开始 | 不要求用户先理解内部 Runtime 术语；缺能力时诚实说明 |
| 可运行 | 能看到谁在做、做到哪一步、正在等待什么 |
| 可介入 | 用户能修改、批准、暂停、接管或恢复，并知道影响范围 |
| 可验收 | 结果有来源、版本、状态和必要的人工确认 |
| 可决定 | 用户能把反馈变成继续、调整、暂停、替换或关闭 |
| 可回收 | 决定和结果回到公司、业务、资料库或 Workspace 的后续工作 |
| 可恢复 | 重开或失败后保留真实状态、责任、原因和下一步 |

以下情况不能被称为完成：只有 Draft、只有页面、只有接口、只有静态成功状态、只有候选组织、只有目录可见、只有一次性运行，或结果没有回到下一次公司行动。

普通用户最终应能用一句话理解当前状态：

> “我让公司做了什么，现在谁在做，结果是什么，我要不要决定下一步。”

## 22. 后续产品推导顺序

原 v2.0 之后，先按以下顺序继续，不直接进入全量页面开发；v3.0 在同一顺序上补充页面合同：

1. 确认七个主工作区域、头像菜单和全局 Assistant/搜索/通知模型。
2. 确认第一次使用：一句话 → 公司 → 第一业务 → 第一 Workspace。
3. 选择一条最能证明 Workspace 独立性的业务纵向链，例如研发或内容。
4. 确认 Workspace 接入契约和一个外部 Agent Provider 的最小真实路径。
5. 确认岗位/员工/执行能力替换与局部介入。
6. 确认一条真实结果 → 反馈 → CEO 决策 → Workspace 改造闭环。
7. 再补齐其他 Workspace、会议、资料库和头像菜单维护面的 UI 细节。

每一步都要从用户目标、真实工作、结果和下一步开始，而不是从数据库对象或 Runtime 页面开始。

## 23. 审查问题

CEO/Product Review 需要确认：

1. 六个主工作区域加左下角头像菜单是否足够，是否有任何主入口仍然多余。
2. 对于运行中的公司，CEO 工作台是否应该默认采用“简报 / 今日变化 / 问题处理 / Assistant 对话”，并允许首次打开状态接管首屏。
3. 组织中心是否同时承载公司、部门、业务、员工和汇报关系。
4. 业务空间是否明确与 Workspace Portal / Studio 的关系。
5. Workspace 是否接受“内嵌独立应用”的定义，而不是统一 Runtime 页面。
6. 空间搭建是否应该以“业务办公室预览”而不是“技术蓝图”作为用户确认对象。
7. Position、RoleSlot、AIEmployee、Executor 四层是否足以表达直接对话、局部介入、岗位复用和执行能力替换。
8. 人才与能力负责能力发现和扩展、设置负责连接授权、组织中心负责公司员工、业务空间负责实际工作，是否能保持普通用户简单，同时不削弱完整产品能力。
9. 竞品借鉴的 L1/L2/L3/L4 边界是否合理。
10. 是否同意先完成一条独立 Workspace 结果链，再扩展全部页面和业务。
11. 是否同意“先获得首个可感知价值，再渐进式成立公司”，而不是先完成组织和资源配置。
12. CEO Assistant 是否应按“观察 → 解释 → 建议 → 执行 → 跟进”承担普通用户的经营代理职责。
13. 按影响分级的行动权限，是否足以保护成本、权限、外部副作用和公司方向。
14. 是否同意 Curis 只建设公司上下文、接入契约、结果连续性和经营代理等差异层，不重写成熟 Agent 的工作界面与执行引擎。
15. 产品装配门是否足以阻止新 Workspace、员工能力和跨层功能重新滑向统一 Runtime / Workflow 平台。
16. Company → Business → (Commitment + Workspace) → Cycle → Handoff → Work object → Outcome / Evidence → Acceptance → Decision → Company Change 这条关系图，是否足以作为后续产品和实现的共同基准。
17. 上述用户可见生命周期是否足以阻止“目录可见 / Draft / Connected / 调用成功”被误报为可运行或已完成。
18. Company Meeting 与 Workspace Meeting 的升级边界，是否足以避免局部问题泛化成 CEO 会议，或公司决定沉没在 Workspace 内。
19. Truth / Assistant / Decision / Change 作为跨切运行面，是否足以覆盖所有 Workspace 的公司级回流，而不新增一级导航。
20. 是否同意将“四个 CEO 意图入口”与“六个 Desktop 工作区域”视为不同层级，避免通过增加重复导航解决概念差异。
21. Handoff 是否被作为责任转移的独立事实，而不是通知、聊天记录或页面跳转的别名。
22. DecisionPacket 是否明确是 Assistant 准备的判断材料，而 Decision 才是 CEO 的有效选择，且两者都能回写影响范围和后续责任。
23. Capability Supply Check 是否区分供给齐备、授权、激活和可运行，并在缺口、漂移或人工回退时保持真实状态。
