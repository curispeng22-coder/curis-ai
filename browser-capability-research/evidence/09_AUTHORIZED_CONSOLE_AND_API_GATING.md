# Evidence 09 — B 场景（自有后台数据读取）的官方通道与真实约束

Authority Class: EVIDENCE
Collected: 2026-09-18（Reconciliation 轮）
**性质**：本条是本轮 Reconciliation 的**核心证据**——它把"平台没有 API"这一前提修正为更准确的表述。

---

## 1. 决定性发现：抖音官方**存在**"用户授权第三方查看自己数据"的正式通道

Source（**官方文档**）：`https://open.douyin.com/platform/resource/docs/ability/open-data/video-data-solution`

> **功能介绍**：本文档面向期望以 open_api 的形式接入抖音视频相关数据（eg. 一段时间内抖音某只视频获取的点赞、分享数等公开数据）的第三方
> **应用场景**：第三方应用或系统的开发者，调用抖音视频数据 open_api，实现获取抖音视频数据的能力
> **抖音帐号运营者或普通用户完成授权后，可直接在第三方系统或应用内查看自己发布的抖音视频在一段时间内的统计数据**
> **使用限制**：需用户授权｜**适用平台**：移动应用，网页应用｜**权限范围**：针对审核通过的用户开通权限
> **产品优势**：抖音官方数据｜**唯一官方认证的对外开放的抖音数据，数据真实性高**｜可分阶段拉取用户视频在一段时间内的总计点赞、分享、评论、粉丝等数据
> **权限申请**：开放平台官网 — 管理中心 — 应用详情 — **抖音数据权限**

### 1.1 这条证据的含义（关键）

**"用户在自己的账号授权下，通过第三方系统查看自己的经营数据"这一产品目的，平台是官方承认并支持的。**

因此前置判断必须修正为：

| 旧表述（不准确） | 新表述（准确） |
|---|---|
| "平台没有 API → Curis 用 AI Browser 去抓取平台信息" | **"官方通道存在且被平台承认，但对个人主体系统性不开放（仅限企业开发者）；用户本人实际拥有的是自己的 Web Console。"** |

这与此前 **PHASE 2 Provider Feasibility** 的既有结论一致并相互印证：
> "国内电商对个人主体系统性排除"

## 2. 官方通道的具体门槛（决定 Browser 路径是否是"必需"而非"便利"）

Source（第三方技术解读，**需官方复核**）：`https://www.jzl.com/news/douyin-api-12`、`https://www.jzl.com/news/douyin-data-api`

| 项 | 内容 |
|---|---|
| 接口示例 | `POST /aweme/v1/video/self/get_user_video_list/`（授权用户发布的视频列表）、`POST /api/apps/v1/video/query/`（按 `item_id` 取播放/点赞/评论/分享） |
| **开发者资质** | **仅限企业开发者，个人开发者无法调用** |
| 授权范围 | **只能查询已授权用户自己发布的视频数据**，无法查任意视频 |
| 单次上限 | 视频列表每次最多 100 条，游标分页 |
| 数据延迟 | 用户首次授权后，**完整数据需等到第二天**才生成 |
| 隐私限制 | **仅返回用户公开的视频数据**，私密视频无法获取 |
| 时间窗口 | 部分接口（经营授权类）**仅能查询 30 天内创建的视频** |
| 能力结论 | "官方 API 适合 **'看自己的视频数据'**，不适合批量采集任意视频" |

### 2.1 ⚠️ 这一条对 Curis 是**路径级**约束

> **官方 API 的能力范围恰好只覆盖"用户看自己的数据"——这正与 Curis 的主场景吻合；但资质被限制在"企业开发者"。**
> → Curis v1 的定位是**个人单机自用**，因此**官方 API 通道在资质层面不可得**，而用户**本人的 Web Console 对其完全开放**。
> → **这就是 Browser Capability 成立的真实理由**：不是"绕过平台"，而是"使用用户实际拥有的、平台对其开放的那一个入口"。

## 3. 抖音经营号的双授权模式（补充）

Source（**官方**）：`https://partner.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/basic-capacities/douyin/`

| 维度 | 普通抖音号授权 | 经营抖音号授权 |
|---|---|---|
| 权限获取 | 需通过控制台**手动申请**相关能力权限 | **默认获取权限**，完成品牌号/员工号/合作号绑定后即可使用 |
| 授权方式 | 用户通过小程序 `tt.showDouyinOpenAuth` 完成授权 | 用户完成经营关系（品牌号/员工号/合作号）授权 |
| Token 接口 | `/oauth/access_token/` | `/business_token/` |
| 适用场景 | 获取普通用户公开数据或**经其授权的数据** | 获取与**经营账号**相关的视频数据、互动数据，常用于企业或品牌运营分析 |

→ **官方承认"经营账号数据"是被授权的数据类别**，并为此设计了专门的授权与 Token 通道。

## 4. 平台自述的风险边界（区分"明确违规"与"通常合规"）

Source（第三方，蝉妈妈，**平台观点转述，需官方复核**）：`https://www.chanmama.com/yunyingquan/question/4385.html`

平台侧表述的边界：

| 风险等级 | 行为 | 对应规则 |
|---|---|---|
| **风险极高（明确违规）** | 使用**需要你输入抖音账号密码**、或要求**扫码授权获取非公开数据**（订单详情、客户手机号、**后台精确成交数据**）的工具 | 直接违反"严禁**向第三方共享账号**"与"**协助第三方擅自获取平台商业信息**" |
| **风险较低（通常合规）** | 使用主要分析**公开数据**（达人直播数据、公开视频表现、热销商品榜）的工具 | 数据来自公开渠道监测 |

引用《不当获取/使用信息》细则口径：
> "未经许可**向第三方共享账号**、或授权其**采集平台非公开数据**，即构成违规"

### 4.1 Curis 的设计如何对应这两条

| 平台禁止的模式 | Curis 的架构是否触及 |
|---|---|
| 向第三方**共享账号**（交出密码 / 交由第三方代登录） | ❌ **不触及**。Curis 的设计是**用户在自己机器上的 Curis 专属 profile 中自行登录**；Curis 不接收、不代填、不导出密码或 Cookie。 |
| 授权第三方**采集平台非公开数据** | ⚠️ **需判断**。"非公开数据"与"用户自己后台中平台已向该用户展示的数据"是否等同 —— **官方材料未给出区分** → 见 §6 UNKNOWN。 |

## 5. 平台自身提供官方导出功能（第三条路）

Sources（第三方操作指南，**需官方复核**）：`https://www.80tg.com/news/56627.html`、`https://www.jzl.com/news/douyin-data-56`
以及 `https://shankongmao.com/content/news/1025`

| 入口 | 能力 |
|---|---|
| **creator.douyin.com**（抖音创作服务平台，电脑网页端） | 「视频数据」→「作品分析」等，右上角**「导出数据」**；支持 Excel，**含完整时间戳与字段明细**；可「导出全部数据」并选择字段（播放来源分布、用户停留时长、跳出节点等） |
| 抖音 App「数据中心」 | 「作品数据」/「账号数据」→ 选时间范围（**7 天 / 30 天 / 90 天或自定义**）→ 右上角**「导出数据」**（Excel） |
| seller.jinritemai.com（抖店后台） | 「数据中心」→「经营分析」→「交易数据」→ 设置查询周期（最小 1 天）→ **「批量导出」CSV**，与抖店财务系统实时同步 |
| App「个人信息与权限」→「导出个人数据」 | PIPL 项下**个人数据副本**（JSON + PDF 加密 ZIP，需短信二次验证） |

### 5.1 含义（对本轮 MVP 有直接影响）
**平台自己提供"导出 Excel/CSV"这条官方功能路径。**

→ 这意味着存在一个**此前未被显式列出**的中间档：
**"平台官方导出文件 + Curis Import"**，它比 Browser Automation **更少协议张力**（用户只是在用平台自己的按钮），且**不需要任何自动化**。

→ 但它的代价是：**无法自动定时**（需人点按钮）、**格式不统一**（跨平台字段名不同）、**不可回溯性差**。这正是用户要求"自动触发回收"的动因。
→ **须由 CEO 裁定**：优先自动化，还是优先最低协议风险。见 `CURIS_BROWSER_USE_CASE_RECONCILIATION.md` §9。

## 7. 本证据的净结论

1. **产品目的合法且官方承认**：用户查看自己的经营数据，平台**自身就提供官方通道与官方导出功能**。→ **不应再把主叙事表述为"抓取"**。
2. **官方 API 通道存在，但被资质门槛（企业开发者）挡在个人主体之外** → 这不是"平台没有 API"，而是"**用户拿不到那条通道的钥匙**"。**这才是 Browser Capability 的正当理由。**
3. **平台明确禁止的是**"向第三方共享账号"与"协助第三方采集非公开数据"；Curis 的架构（用户自持凭据、自机登录、不代填、不导出）**不触及第一项**，**第二项取决于 U3 的界定 → UNKNOWN**。
4. **第三条更干净的路存在**：平台官方导出（Excel/CSV）→ Curis Import。**须由 CEO 在"自动化收益"与"协议风险"之间裁定优先级。**
5. **U1–U6 必须在上线前闭环**，其中 U1/U3 需**法务或官方渠道**确认，不能由本研究报告自行裁定。
